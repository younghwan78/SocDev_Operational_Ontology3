# UX-D 선택지·이견·불확실성 구현 보고서

> 상태: 구현·검증 완료
> 기준일: 2026-07-17
> 범위: post-I7 UX redesign의 UX-D
> 다음 단계: UX-E 안전 조건·행동·결과 — 시작하지 않음

## 1. 결론

UX-D는 선택지를 같은 기준으로 비교하고, 다중 Role 검토의 일치와 핵심 이견을 먼저
파악하며, 사실·추론·가정·미확인을 서로 다른 확인 경계로 읽을 수 있게 구현했다. Role
Agent는 조언을 만들지만 Frontend가 투표나 decision logic을 만들지 않는다. Backend가
검증된 Dossier와 selected-Step observable boundary를 사용자용 projection으로 바꾼다.

```text
Observable case + selected Step + latest case-scoped Dossier run
  → Backend comparison and epistemic eligibility
  → agreement / key dissent / confirmation / challenge change
  → desktop comparison table or mobile option card
  → Role originals only on demand
```

## 2. Backend와 계약

### 2.1 Durable Dossier 합성

`ReviewRunRepository.latest_for_case`를 InMemory/PostgreSQL에 같은 계약으로 추가했다.
Workspace endpoint는 현재 case의 최신 dossier run을 읽고 status와 검증된
`DossierExecution`을 `decision-workspace.v2` builder에 전달한다.

- `QUEUED`, `RUNNING`, `PARTIALLY_COMPLETED`: `REVIEW_RUNNING`
- `COMPLETED`이며 Dossier 존재: `DOSSIER_READY`
- Dossier가 없거나 실패한 상태: persisted case phase로 안전하게 복귀

### 2.2 선택지 비교

각 선택지는 다음 필드를 같은 순서로 제공한다.

- 기대 효과
- 일정 영향
- 실패 영향
- 가역성·전환 비용
- 필요한 근거
- 안전 조건
- 남는 위험

전체 점수와 자동 순위는 없다. effective Role review가 한 선택지를 모호하지 않게 가장 많이
지지할 때만 `Role 검토 권고`를 표시한다. 동률이면 권고 badge를 만들지 않는다. 최종 승인을
의미하지 않으며 dissent는 별도로 계속 노출한다.

### 2.3 의견 종합과 Role 원문

Backend가 Dossier를 다음 사용자 단위로 투영한다.

- 같은 recommendation의 의견 일치 group
- 합의와 다른 핵심 이견
- 아직 확인할 불확실성
- Challenger 이후 권고 또는 이유의 변경
- Role별 최초 review와 revision detail

Role ID와 confidence enum은 한국어 label과 정성적 수준으로 바꾼다. provider, token, cost,
trace는 일반 사용자 projection과 기본 화면에 포함하지 않는다.

### 2.4 Epistemic boundary

`fact`와 `inference`는 selected Step에서 eligible한 source만 사용한다. 추론은 source title과
등록된 inference basis 개수로 사실과 구분한다. `assumption`은 owner와 재검토 Step을,
`unknown`은 모르는 이유와 다음 확인 Step을 표시한다.

과거 Step은 현재 Dossier, Role 원문, unversioned assumption/unknown을 반환하지 않는다.
따라서 현재 알고 있는 가정이나 나중에 생성된 Role 의견이 과거 화면으로 역류하지 않는다.

## 3. Frontend UX

### 3.1 Desktop

semantic table의 행은 선택지, 열은 동일한 비교 기준이다. 긴 설명을 여러 Agent card로 먼저
읽지 않고 가역성, 일정과 실패 영향을 한 번에 비교한다. 권고 행은 약한 배경과 명시적
`Role 검토 권고` badge로만 구분한다.

### 3.2 Mobile

390px에서는 표를 축소하거나 수평 scroll하지 않는다. 한 선택지 card와 `이전 선택지`/
`다음 선택지` control을 제공하고 같은 비교 필드를 세로로 읽는다. E2E에서 두 번째
선택지로의 이동과 page-level overflow 부재를 검증했다.

### 3.3 Deliberation과 detail

기본 순서는 `의견 일치 → 핵심 이견 → 확인 필요 → 반론 후 변경`이다. Role별 긴 원문과
revision은 `Role별 원문 보기` detail 안에 둔다. 지식 상태는 색만이 아니라 제목과 설명으로
구분하고, 각 group은 두 항목을 먼저 보여준 뒤 나머지를 접는다.

## 6. 남은 경계와 위험

- 선택지별 안전 조건은 검증된 decision safeguard와 연결되기 전에는 `미등록`으로 표시한다.
  Role prose에서 임의로 safeguard를 추출하지 않는다.
- 결정 이후 observed transition은 decision과 development event의 durable 연결이 없어 아직
  `available=false`다.
- 기존 역할 검토·Dossier·Chair·Outcome control은 기능적으로 유지했다. phase별 한 개의
  primary action과 안전 조건·rollback·결과 비교로 재구성하는 작업은 UX-E다.
- current Workspace는 최신 case-scoped dossier run만 합성한다. 사내 권한, source ACL,
  Confluence/Jira와 write-back은 여전히 C0 이후 별도 범위다.

## 7. 다음 단계

UX-E에서 decision safeguard를 선택지와 실행 계획에 연결하고, owner·기한·측정 기준·rollback을
한 행동 흐름으로 만든다. 이후 decision-linked observed transition과 기대 대비 실제 결과를
보여준다. UX-D 완료만으로 실제 승인 권한이나 사내 적용이 생기지 않는다.
