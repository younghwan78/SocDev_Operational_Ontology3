# Step 2 실제 개발 진행 Digital Twin 구현 보고서

> 상태: 구현 및 검증 완료
> 기준일: 2026-07-14
> 범위: local fixture-only PoC, I7 후속 구현 Step 2

## 1. 결과 요약

Step 2는 현재 상태를 나열하는 모델을 시간에 따라 원인과 영향이 이어지는 개발
Digital Twin으로 확장했다. 같은 event history로 과거 시점의 작업, milestone,
측정 근거, 결정 후속 행동을 복원하며, 당시 관측되지 않은 event와 미래 evidence는
Role Agent 입력에 포함하지 않는다.

이번 단계는 사내 데이터, Jira, Confluence, 인증, write-back을 포함하지 않는다.
기존 8개 평가 corpus도 수정하지 않았다. 새 개발 fixture는 구현 구조를 검증하기
위한 독립 corpus이며, 평가 corpus v2 설계는 Step 3 범위로 남긴다.

## 2. 구현 구조

### 2.1 Domain contract

- `development-event.v1`: event type, 발생 시점, 관측 시점, 요약, 원인,
  typed before/after change를 보유한다.
- 변경 대상: WorkItem, Milestone, Evidence, DevelopmentAction.
- event type은 작업 진행, blocker, 계획, dependency, evidence, rework,
  interface, resource, priority, 결정 후속 행동을 구분한다.
- WorkItem status 변경은 기존 canonical transition 규칙을 그대로 사용한다.
- entity별 event chain은 연속이어야 하며 마지막 `after` 값은 현재 snapshot과
  정확히 같아야 한다.

### 2.2 Historical reconstruction

현재 snapshot에서 요청한 `at_step` 이후에 관측된 event를 역순으로 되돌린다.
이 방식은 별도 initial snapshot을 두지 않아 fixture의 source of truth를 하나로
유지한다. API는 `development-timeline.v1`으로 복원 시점의 상태와 그때까지 관측된
event만 반환한다.

```text
Current snapshot
  -> reverse events with observed_at_step > at_step
  -> reconstructed work/milestone/evidence/action state
  -> visible event filter
  -> Timeline projection / ObservableCasePacket
```

`effective_at_step`과 `observed_at_step`을 분리했으므로 실제 변경이 먼저 발생하고
조직이 늦게 인지하는 상황도 표현할 수 있다. Agent의 역사 시점 packet에는
`observed_at_step` 이후의 event와 `available_at_step` 이후의 evidence가 들어가지 않는다.

### 2.3 Dependency impact

현재 blocker가 있는 WorkItem마다 dependency graph의 모든 후속 WorkItem을 탐색한다.
후속 작업의 track과 next milestone을 계산하고, 결정 deadline에 도달하는지도
projection에 명시한다. Frontend는 이 계산을 다시 하지 않고 Backend 결과만 표시한다.

### 2.4 Persistence and API

- migration: `0018_development_event_history`
- query: `GET /api/v1/decision-cases/{case_id}/timeline?at_step=N`
- developer packet query도 `at_step`을 받아 같은 역사 시점 경계를 적용한다.
- migration upgrade는 기존 JSONB payload에 빈 actions/events 배열을 보강한다.
- downgrade는 두 배열을 제거하므로 non-empty history는 사전 backup이 필요하다.

### 2.5 Korean UI

결정 workspace에 `개발 진행 타임라인`을 연결했다. event의 Step, 한국어 유형,
변경 요약, 원인과 blocker의 후속 작업/milestone 영향을 보여준다. 이 화면은 Step 2의
이해 가능성 확인을 위한 최소 projection이며 전체 UX 재설계는 이후 단계의 별도 범위다.

## 3. 독립 fixture matrix

|Case|구조|주요 변화|
|---|---|---|
|CASE-DT-001|HW/SW interface mismatch와 rework|interface 변경, HW block, SW rework, 통합 영향|
|CASE-DT-002|측정 지연과 freeze 충돌|측정 작업 block, evidence 공개 지연, freeze 일정 변경|
|CASE-DT-003|일정 workaround와 technical debt|workaround 완료, 통합 진행, 제거 작업 및 release 지연|
|CASE-DT-004|공유 자원 충돌|camera/NPU 자원 경합, 후속 release block, milestone 지연, arbitration action|

각 case는 기존 평가 fixture를 `extends`하지 않는 완전한 synthetic fixture다. 각 history는
최소 세 개 관측 시점을 가지며 초기·중간·현재 상태를 모두 복원한다.

## 5. 설계상 제한과 다음 경계

- event 입력은 현재 fixture authoring/import 경로뿐이며 실시간 external ingestion이 아니다.
- 동일 `observed_at_step`의 순서는 stable `event_id`로 결정한다. 조직별 세밀한 wall-clock
  순서는 local PoC 범위가 아니다.
- blocker 영향은 dependency와 track next milestone에 대한 deterministic reachability다.
  확률적 schedule 예측이나 resource capacity optimizer는 포함하지 않는다.
- Step 3 전에는 이 4개 case를 frozen evaluation release에 합치지 않는다.
- Jira/Confluence와 실제 승인 권한은 C0/C1 이후 별도 보안·권한 결정을 통과해야 한다.
