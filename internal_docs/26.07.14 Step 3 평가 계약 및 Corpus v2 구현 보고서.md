# Step 3 평가 계약 및 Corpus v2 구현 보고서

> 상태: 구현 및 검증 완료
> 기준일: 2026-07-14
> 범위: local fixture-only PoC, I7 후속 구현 Step 3

## 1. 결과 요약

기존 8개 release는 결과를 열어 분석한 뒤 prompt와 validator가 변경되었으므로 더
이상 fresh validation/sealed로 사용하지 않는다. Step 3는 이를 development regression으로
내리고, Step 2에서 만든 독립 구조 4개에 새 hidden outcome과 expected result를 작성해
`eval-2026-07-14.2`를 12개 case로 동결했다.

```text
development regression: 기존 CASE-VR/HO 8개
validation:             CASE-DT-001, CASE-DT-002
sealed-unseen:          CASE-DT-003, CASE-DT-004
```

사내 데이터, Jira, Confluence, 인증, write-back은 포함하지 않았다. v2 sealed는
home author가 만든 regression guard이며 독립적인 일반화 또는 business-value 증거가 아니다.

## 2. 평가 release source 계약

`evaluation-manifest.v2`는 각 case에 다음 경로와 hash를 명시한다.

- observable source
- hidden outcome source
- expected result source
- 각 source의 canonical SHA-256

이 구조를 통해 `CASE-VR-005`의 v2 expected result를 별도 파일로 둘 수 있다. 기존
`.1` expected와 manifest hash는 변경하지 않았다. validation은 manifest에 기록된 경로만
읽으며 absolute path, `..`, Windows separator를 거부한다.

Replay와 live runner는 이제 검증한 manifest의 case 목록과 partition을 실제 실행에
사용한다. 이전처럼 manifest와 별도 전역 목록이 달라질 가능성을 제거했다.

## 3. Escalation 정책

데이터 부족만으로 escalation하지 않는다. 최소 evidence 수집, trigger까지 defer,
guarded reversible trial을 먼저 비교한다. 다음 중 하나가 fixture의
`allowed_decision_types`로 명시된 경우에만 escalation 후보가 된다.

- 현재 역할 밖의 결정 권한
- 조직 간 우선순위 충돌
- 현재 역할이 통제할 수 없는 비가역 위험

`CASE-VR-005`는 고객 feature priority를 기술 Role이 결정할 수 없으므로 v2에서는
`ESCALATE`를 허용한다. 단, 대상·질문·due step·verification·fallback이 모두 있어야 한다.

## 4. Case별 평가 계약 v2

기존 Process/Outcome 평가에 다음 deterministic 항목을 추가했다.

|항목|검증 내용|
|---|---|
|Decision action type completeness|DecisionType별 action type과 subtype 필수 필드|
|Development history reconstruction|event가 있으면 최소 3개 관측 step 복원|
|Historical packet boundary|요청 step 이후 event와 future evidence content 미노출|
|Blocker impact traceability|현재 blocker가 이름 있는 milestone까지 추적됨|

새 결과는 `case-evaluation.v2`, summary는 `evaluation-summary.v2`를 사용한다. 저장된
v1 결과는 새 필드의 안전한 기본값으로 계속 읽을 수 있어 DB migration은 필요하지 않다.
