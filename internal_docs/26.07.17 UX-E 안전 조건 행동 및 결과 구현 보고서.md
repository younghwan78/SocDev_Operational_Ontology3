# UX-E 안전 조건·행동·결과 구현 및 검증 보고서

> 작성일: 2026-07-17  
> 상태: 구현 완료  
> 범위: local synthetic fixture와 ReplayProvider만 사용  
> 다음 단계: UX-F Responsive·접근성·사용성 Gate

## 1. 결론

UX-E는 가상 판단을 결과 카드 하나로 끝내지 않고 다음 폐루프로 연결했다.

```text
가상 역할 검토
  → 가상 최종 판단
  → Action Plan + Safeguard + Rollback
  → 명시적 Simulation Step 진행
  → 관측된 상태 변화 + 예상 대비 실제
  → Process 평가 + Outcome 평가
  → 다음 판단에 남길 학습
```

현재 사용자는 한 화면에서 다음 항목을 찾을 수 있다.

- 왜 이 판단을 했는가
- 어떤 선택지를 실행하는가
- 담당자, 기한, 시작 조건과 확인 방법은 무엇인가
- 어떤 측정 조건에서 중단하거나 되돌리는가
- 아직 남은 위험은 무엇인가
- 판단 이후 Action 또는 WorkItem이 어떻게 바뀌었는가
- 예상과 실제가 어떻게 달랐는가
- 판단 과정과 실제 결과를 각각 어떻게 평가하는가

집에서의 결과는 계속 `simulated`이며 사람의 실제 승인, 사내 action 또는 Jira/Confluence
write-back을 의미하지 않는다.

## 2. UX-E에서 닫은 문제

### 2.1 판단과 실행 정보의 분리

기존 화면은 Dossier, 결정, Safeguard와 Outcome이 서로 다른 개발자용 section에 놓여 있었다.
UX-E에서는 결정 이유에서 행동과 실패 시 대응까지를 한 흐름으로 연결했다.

```text
원인·판단 근거 → 다음 행동 → 안전 조건 → 실패 시 대응
```

Action 카드에는 owner, due Step, trigger, verification, fallback을 고정된 순서로 보여준다.
Safeguard 카드에는 metric, threshold, check Step, condition, rollback trigger, violation action,
owner와 expiry Step을 함께 둔다.

### 2.2 새로고침 후 판단 문맥 소실

`GET /api/v1/decision-cases/{case_id}/workspace`가 최신 case-scoped durable Dossier run,
simulated decision, Outcome과 Evaluation을 함께 읽는다. 따라서 PostgreSQL 실행에서는 브라우저
새로고침이나 재접속 후에도 현재 lifecycle phase와 다음 행동을 복원한다.

Phase 우선순위는 Backend가 소유한다.

|존재하는 durable 결과|Workspace phase|Primary action|
|---|---|---|
|Decision 없음, Dossier 실행 전|`READY_FOR_REVIEW`|가상 역할 검토 실행|
|Dossier 실행 중|`REVIEW_RUNNING`|진행 상태 보기|
|Dossier 완료|`DOSSIER_READY`|의견 종합 보기|
|Simulated decision|`OUTCOME_RUNNING`|다음 Simulation Step 진행|
|Outcome|`EVALUATION_READY`|판단 평가 보기|
|Evaluation|`CLOSED`|학습 요약 보기|

Frontend는 phase, readiness 또는 allowed action을 다시 계산하지 않는다.

### 2.3 브라우저가 decision authority가 되는 문제

정상 UX에서는 Outcome command body에 decision 전체를 다시 보내지 않는다. Backend가 최신
persisted decision을 읽어 사용한다.

- persisted decision 없음: `DECISION_NOT_READY`
- client가 다른 decision을 명시: `DECISION_MISMATCH`
- 기존 client가 같은 decision을 명시: 호환 허용

이 변경으로 화면 reload 뒤에도 Outcome 진행이 가능하며, browser state가 판단 원본의 권위가
되지 않는다.

### 2.4 예상과 관측의 혼합

결정 직후에는 Action의 `PLANNED → IN_PROGRESS`만 표시하고 Outcome 내용은 숨긴다. 사용자가
명시적으로 Simulation Step을 진행한 뒤에만 fixture Outcome을 공개한다.

- `expected_model`: 선택지에 미리 연결된 검증된 예상 상태 변화
- `observed_event`: persisted decision 또는 실제 Outcome event ID를 근거로 한 상태 변화 projection
- 실제 Outcome: 공개 근거, 측정값, consequence와 실행된 보호 조치

Outcome 이후 WorkItem/Milestone target은 선택한 option의 검증된 expected transition에 있는
entity만 사용한다. 실제 Outcome event ID를 basis로 연결하지만 observable case aggregate의
development history를 자동 변경하지는 않는다. 이 구분은 ADR-0009에 기록했다.

### 2.5 과정 품질과 결과 품질의 혼합

결과 화면은 다음을 별도 카드로 유지한다.

- 과정 품질: 당시 이용 가능한 정보에서 의존성, 이견, 안전 조건과 다음 행동을 갖췄는가
- 결과 품질: 공개된 위험 신호에 필요한 보호 조치가 작동했는가

결과가 나빴다는 이유만으로 당시 판단 과정을 자동 실패로 만들지 않으며, 결과가 좋았다는
이유만으로 불완전한 판단 과정을 정당화하지 않는다.

## 3. Backend 구현

### 3.1 Workspace projection

`workspace_projection_v2.py`에 다음 projection을 추가했다.

- decision-linked Action Plan
- option-specific Safeguard와 Rollback
- Action 상태 `in_progress/completed/blocked/cancelled`
- decision/outcome event 기반 observed transition
- expected, actual과 guardrail result 분리
- Process/Outcome evaluation과 lessons
- current-only dossier run identifier

사용자 흐름에 machine code가 직접 노출되지 않도록 선택지 ID를 title로 바꾸고,
`DDR_BANDWIDTH`, `lte` 같은 값은 `DDR 대역폭`, `≤`처럼 consumer label로 projection한다.

### 3.2 Durable latest reads

다음 repository port와 memory/PostgreSQL 구현에 `latest(case_id)`를 추가했다.

- `SimulatedDecisionRepository`
- `OutcomeAdvanceRepository`

Evaluation은 기존 latest query를 재사용했다. 별도 migration은 필요하지 않았다.

### 3.3 In-memory/PostgreSQL parity

In-memory Outcome은 case aggregate를 직접 갱신하지 않으므로 Workspace와 Evaluation readiness가
latest Outcome의 current Step을 함께 사용하도록 했다. PostgreSQL은 기존 transaction에서 case와
simulation state를 함께 전진시킨다.

In-memory run latest selection은 timestamp가 없는 run 두 개를 UUID로 선택하던 비결정성을
발견해 삽입 순서 기준으로 수정했다. Workspace reload가 최신 Dossier를 안정적으로 선택한다.

### 3.4 Historical fail-closed

과거 Step Workspace는 다음을 모두 제거한다.

- dossier run ID와 Role originals
- simulated decision과 Action Plan
- Safeguard와 observed transition
- Outcome, Evaluation과 lessons
- current workflow phase와 command

과거 화면에서 이후에 알게 된 판단이나 결과가 역으로 보이지 않는다.

## 4. Frontend 구현

### 4.1 하나의 Actioning layout

새 `DecisionExecution` component는 다음 순서로 구성된다.

1. 가상 판단과 선택지
2. 원인–행동–안전 조건–실패 시 대응 연결
3. 다음 행동의 담당·기한·trigger·verification·fallback
4. Safeguard와 Rollback
5. 관측된 상태 변화
6. 잔여 위험
7. 예상과 실제
8. 보호 조치 결과
9. Process/Outcome 평가
10. 다음 판단의 학습

판단이 생긴 뒤 UX-A~D의 검토 내용은 `결정 당시 검토 내용 보기` detail로 접어 두었다. 감사와
재검토에는 남겨 두되 현재 행동보다 먼저 보이지 않는다.

### 4.2 단계별 단일 Primary action

Decision Brief의 Backend-owned primary action만 강조 버튼으로 둔다. 정상 사용자 화면에서
single-Role 실행과 topology 비교 버튼을 제거하고 release topology B2 Dossier 한 경로만 남겼다.
취소, 재시도와 Dossier 완료 후 가상 최종 판단은 보조 action이다.

### 4.3 결과 hidden boundary

Decision 이후 Outcome 전에는 결과 예측값이나 hidden fixture 측정값을 렌더링하지 않는다.
화면에는 행동과 확인 시점만 표시하고, 결과는 명시적 Step 진행 뒤에만 나타난다.

## 5. Contract와 ADR

함께 갱신한 산출물은 다음과 같다.

- `decision-workspace.v2` JSON Schema
- `workspace-ux-fixture.v1` JSON Schema
- FastAPI OpenAPI
- generated TypeScript API types
- `ADR-0009-durable-workspace-decision-lifecycle.md`
- canonical API, Master Plan, Plan Index와 구현 상태판

DB physical schema는 변경하지 않았으므로 migration head는 `0019_agent_run_topology`를 유지한다.


|UX-E 완료 조건|판정|근거|

따라서 UX-E는 완료로 판정한다.

## 8. 남은 경계와 UX-F

UX-E 완료가 다음을 증명하지는 않는다.

- 실제 사람이 Safeguard와 Rollback을 이해하고 더 빠르게 판단하는가
- 768px, 200% zoom과 keyboard-only 흐름이 완전한가
- partial, stale, conflict 모든 조합의 화면 복구가 충분한가
- 실제 사내 development event가 Action/WorkItem transition으로 연결되는가
- Jira/Confluence read-only pilot에서 business metric이 개선되는가

다음 UX-F에서는 390px, 768px, desktop, 200% zoom, keyboard, screen reader semantics,
partial/stale/conflict E2E와 frozen CASE-VR-001의 canonical 8개 + Development Twin 5개 질문을
정식 task report로 검증한다. UX-F 전에는 실제 사용자 최적 UX 완료를 주장하지 않는다.
