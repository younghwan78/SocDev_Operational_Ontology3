# Step 1 실행 가능한 결정 계약 구현 보고서

> 날짜: 2026-07-14
> 상태: **완료**
> 범위: local fixture-only PoC, I7 usability hardening
> 다음 Step: 시작하지 않음

## 1. 완료 결과

Step 1의 목표였던 “데이터가 부족한 결정도 실행 가능한 다음 행동을 반드시 가진다”를
Backend domain contract, deterministic/Replay Chair, live provider schema, PostgreSQL,
API, Frontend, evaluation에 같은 규칙으로 구현했다.

이제 Chair는 단순히 “근거가 부족하다”거나 “상신한다”는 결론만 반환할 수 없다.
모든 `SimulatedDecision`은 다음 항목을 함께 반환한다.

- 누가 수행하는가: `owner`
- 무엇을 하는가: `action`
- 언제까지 하는가: `due_at_step`
- 무엇이 시작 또는 재검토 조건인가: `trigger`
- 어떻게 완료를 확인하는가: `verification`
- 실패하거나 기한을 넘기면 무엇을 하는가: `fallback_action`

최종 사람 승인 경계는 바꾸지 않았다. 로컬 Chair의 결과는 계속
`simulated=true`이며 실제 회사 업무 action, Jira/Confluence, 인증, write-back을
수행하지 않는다.

## 2. 결정 유형별 계약

새 계약은 `simulated-decision.v2`와 `decision-action-plan.v1`이다.

|DecisionType|action type|추가 강제 조건|
|---|---|---|
|`APPROVE`|`execute`|공통 실행 필드|
|`APPROVE_WITH_GUARDRAILS`|`execute`|기존 executable safeguard|
|`RUN_REVERSIBLE_TRIAL`|`execute`|기존 executable safeguard|
|`COLLECT_MINIMUM_EVIDENCE`|`collect_evidence`|`evidence_required`가 비어 있으면 거부|
|`DEFER_UNTIL_TRIGGER`|`defer`|trigger와 재검토 기한|
|`ESCALATE`|`escalate`|상신 대상과 해결 질문이 없으면 거부|
|`REJECT`|`reject`|재검토 조건이 없으면 거부|

`ESCALATE`는 데이터 부족의 기본 답이 아니다. 권한 경계 또는 현재 역할이 통제할 수
없는 비가역 위험에만 사용하며, 대상·질문·기한·fallback을 함께 요구한다. 이 정책의
근거와 호환성 결정은
`docs/decisions/ADR-0001-decision-action-plan-v2.md`에 기록했다.

## 3. 구현 구조

### 3.1 Domain과 Chair

- `backend/src/soc_ot/agents/multi_role.py`
  - `DecisionActionPlan` strict Pydantic model 추가
  - `SimulatedDecision`을 v2로 변경
  - DecisionType과 action type 불일치, 수집 근거 누락, 상신 대상/질문 누락,
    거절 재검토 조건 누락을 model validation에서 차단
- `backend/src/soc_ot/agents/chair.py`
  - packet의 현재 step, 다음 근거 시점, 결정 기한, uncertainty, option operability로
    deterministic action plan 생성
  - 모든 7개 DecisionType 지원
- `backend/src/soc_ot/agents/runtime.py`
  - live Chair 출력의 action 기한이 현재 step보다 과거이면 거부

Domain은 FastAPI, SQLAlchemy, OpenAI, UI label을 import하지 않으며 Agent 입력은 계속
검증된 `ObservableCasePacket`뿐이다.

### 3.2 Prompt와 평가 release

- `prompts.v1`은 변경하지 않고 `prompts.v2` 추가
- Role/Challenger 지시는 그대로 유지하고 Chair에 action-plan 규칙만 추가
- `eval-2026-07-11.1`은 과거 release로 보존
- 같은 8개 fixture와 새 prompt hash를 고정한 `eval-2026-07-14.1` 추가
- Process evaluation에 `decision_action_complete` 추가

새 release는 계약 회귀 기준이다. 새로운 독립 sealed-unseen corpus를 만들었다는 의미는
아니며 live model 안정성·비용 gate도 대체하지 않는다.

### 3.3 저장과 호환성

Alembic head는 `0017_decision_action_plan_v2`이다. 기존 v1 JSONB 결정은 실행 권한을
확대하지 않는 “v2 계약으로 재검토” action plan으로 변환한다.

변환 대상은 다음 네 경로다.

1. durable simulated decision
2. accepted Chair checkpoint
3. completed dossier run result
4. persisted outcome evaluation

upgrade와 downgrade 모두 실제 v1 row를 넣은 migration 검증으로 확인했다. downgrade는
action plan을 제거하므로 실제 운용 데이터 적용 전에는 백업이 필요하다.

### 3.4 API와 Frontend

Pydantic → JSON Schema → OpenAPI → TypeScript 타입을 다시 생성했다. Frontend는 새
판단을 계산하지 않고 API가 준 action plan을 한국어 `다음 행동` 카드로 표시한다.

표시 순서는 다음과 같다.

1. 모의 결정과 이유
2. 다음 행동: 담당, 할 일, 기한, 시작 조건, 확인 방법, 실패 시 조치
3. 합의와 반대 의견
4. 안전장치와 잔여 위험

근거 수집, 상신, 거절에만 필요한 추가 필드는 값이 있을 때만 표시한다. 390px 화면과
접근성 검사도 기존 E2E에 포함했다.

## 5. 남은 제한과 중지점

- OpenAI/Codex CLI live structured output의 v2 안정성은 이번 Step에서 실행하지 않았다.
- 실제 사내 권한자와 escalation target mapping은 fixture role ID만 사용한다.
- action plan은 조언과 simulation 입력이며 실제 Jira/Confluence action을 실행하지 않는다.
- 최종 UX 재구성 및 다음 구현 Step은 시작하지 않았다.

따라서 Step 1은 Replay와 local system 기준으로 완료다. 이 커밋 이후에는 사용자 지시에
따라 다음 Step을 별도로 시작한다.
