# ENT-E Security Operation Emulator 구현 보고서

> 작성일: 2026-07-27  
> 범위: ENT-E fixture-only security/operation policy verification  
> 판정: **ENT-E PASS, NEXT ENT-F**

## 1. 이번 단계가 해결한 문제

ENT-A의 `source_acl_ref`는 opaque reference일 뿐 권한 판정이 아니었다. ENT-D도 ACL reference가
검토 목록에 있는지만 확인했다. 따라서 실제 adapter를 만들기 전에 다음 동작을 고정할 필요가
있었다.

- principal이나 ACL 정보가 없으면 노출하는가?
- allow와 deny가 동시에 적용되면 무엇을 우선하는가?
- classification에 따라 Frontend/API/Model/Role packet/Log 노출이 어떻게 달라지는가?
- restricted source의 identity나 payload가 audit/log에 남는가?
- error message, header, nested payload와 URL에 섞인 credential을 제거하는가?
- source lag, stale, rate-limit, partial source와 unknown freshness를 current로 오인하는가?
- 장애별 recovery action과 health/readiness/metrics/audit가 재현 가능한가?

ENT-E는 이를 synthetic emulator로 검증한다. 실제 authentication이나 authorization을 수행하지
않는다.

## 2. 승인 계약

ADR-0016이 다음 contract를 승인한다.

```text
enterprise-security-operation-policy.v1
enterprise-security-operation-scenario-corpus.v1
enterprise-security-operation-report.v1
```

Report는 다음 두 값을 schema상 false로 고정한다.

```text
real_authorization_performed = false
credential_persisted = false
```

Synthetic `ALLOW`는 policy fixture의 동작을 검증할 뿐 실제 사용자의 접근 권한을 의미하지 않는다.

## 3. Exposure surface와 classification

```text
EnterpriseExposureSurface = FRONTEND | API | MODEL | ROLE_PACKET | LOG
EnterpriseExposureMode    = FULL | METADATA_ONLY | DENY
EnterpriseAccessDecision  = ALLOW | DENY
```

|Classification|Frontend|API|Model|Role packet|Log|
|---|---|---|---|---|---|
|PUBLIC|FULL|FULL|FULL|FULL|METADATA_ONLY|
|INTERNAL|FULL|FULL|FULL|FULL|METADATA_ONLY|
|CONFIDENTIAL|FULL|FULL|DENY|DENY|METADATA_ONLY|
|RESTRICTED|DENY|DENY|DENY|DENY|DENY|

표의 FULL/METADATA_ONLY는 ACL이 먼저 허용된 경우의 최대 노출이다. Classification이 허용해도
principal/ACL이 허용하지 않으면 결과는 DENY다.

## 4. Fail-closed ACL 순서

판정 순서를 고정했다.

1. source가 `RESTRICTED` 또는 inactive인지 확인
2. classification이 surface를 금지하는지 확인
3. principal이 synthetic registry에 있는지 확인
4. ACL reference가 synthetic registry에 있는지 확인
5. principal/group allow와 deny를 계산
6. allow/deny conflict면 DENY
7. allow match가 없으면 DENY
8. 허용된 경우에만 classification exposure mode 적용

```text
ACL_ALLOW
ACL_DENY
ACL_NO_MATCH
ACL_MISSING
ACL_CONFLICT
PRINCIPAL_UNKNOWN
CLASSIFICATION_DENY
SOURCE_INACTIVE
SOURCE_RESTRICTED
```

7개 exposure probe와 5개 surface가 35개 결정을 만든다. Frozen expectation과 실제 결과가 하나라도
다르면 emulator가 실패한다.

```text
total decisions  35
ALLOW            10
DENY             25
```

Missing ACL, unknown principal, explicit deny와 conflict는 모두 5개 surface에서 fail-closed다.
CONFIDENTIAL의 Model/Role packet은 ACL 계산 전에 classification으로 차단된다.

## 5. Restricted leakage boundary

Exposure report는 raw `EnterpriseSourceIdentity`, URL 또는 payload를 기록하지 않는다. 대신 stable
identity의 SHA-256 reference만 보존한다.

Restricted probe의 다음 값은 report와 audit에 나타나지 않는다.

```text
PAGE-RESTRICTED-SECRET
source URL
source_identity field
payload
```

Audit도 event type, timezone-aware time, hashed subject reference와 compact outcome만 갖는다.
따라서 denial 사실은 관측할 수 있지만 보호된 object identity/content는 노출하지 않는다.

## 6. Credential redaction

Redaction은 header key만 검사하지 않는다.

- configured sensitive field name
- nested JSON field
- Bearer value
- `token=`, `password=`, `secret=`, `api_key=` 형식
- URL user-info

Synthetic diagnostic의 message, Authorization/Cookie header, nested password, API key와 credential
URL에서 총 6개 path가 redaction된다. 안전한 request ID와 numeric count는 보존한다.

```text
[REDACTED]
```

집중 test는 fixture에 넣은 8개 synthetic credential fragment가 report/audit JSON 어디에도 없는지
검사한다.

## 7. Operation recovery

```text
EnterpriseIncidentType =
  HEALTHY | LAG | STALE | RATE_LIMITED | PARTIAL_SOURCE | UNKNOWN_FRESHNESS
```

|Incident|Health|Readiness/current|Recovery|
|---|---|---|---|
|HEALTHY|HEALTHY|READY / current|NONE|
|LAG|DEGRADED|NOT_READY / not current|WAIT_BACKOFF|
|STALE|NOT_READY|NOT_READY / not current|FULL_RECONCILIATION|
|RATE_LIMITED|DEGRADED|NOT_READY / not current|WAIT_BACKOFF|
|PARTIAL_SOURCE|NOT_READY|NOT_READY / not current|RETRY_MISSING_PARTITION|
|UNKNOWN_FRESHNESS|NOT_READY|NOT_READY / not current|ESCALATE_SOURCE_OWNER|

정상이며 completeness 1.0, freshness known, lag threshold 이내인 경우에만 current다. Freshness를
모르면 lag를 만들지 않고 source owner escalation을 요구한다.

## 8. Metrics와 audit

Report는 27개 metric record를 생성한다.

```text
enterprise_denied_exposure_total
enterprise_redacted_field_total
enterprise_partial_source_total
enterprise_source_freshness_known
enterprise_source_completion_ratio
enterprise_source_current
enterprise_source_lag_seconds
enterprise_rate_limit_retry_after_seconds
```

Global security count와 scenario별 operation metric의 `(metric_id, scenario_id)`는 유일하다.
Prometheus server나 production alert를 추가한 것은 아니다.

Audit event type은 다음 네 종류다.

```text
ACCESS_EVALUATED
REDACTION_APPLIED
HEALTH_EVALUATED
RECOVERY_PLANNED
```

현재 fixture는 47개 deterministic audit event를 만들며 raw payload나 credential은 포함하지 않는다.

## 9. CLI

```powershell
uv run soc-ot enterprise emulate-security `
  --output output/enterprise/ent-e-security-operation.json
```

명령은 policy/scenario YAML을 strict contract로 읽고 요청한 JSON report만 쓴다. Test는 runtime
database 함수가 호출되면 실패하도록 바꾼 상태에서 CLI를 실행해 database 미접근을 확인했다.

## 10. Fixture와 코드

|Artifact|역할|

|`enterprise_security_operations.py`|exposure, redaction, recovery, metric, audit 계산|
|`security-operation-policy.v1.yaml`|synthetic principal/ACL/classification/threshold|

실제 사용자/group 또는 credential은 없다.

## 11. 검증

집중 test 12개가 다음을 검증한다.

- 4 classification × 5 surface total policy
- frozen exposure expectation parity
- unknown/missing/conflicting/denied ACL fail-closed
- restricted identity/payload non-leakage
- recursive credential redaction
- 6 incident health/readiness/recovery
- unknown freshness non-current
- metric uniqueness와 exact security counts
- metadata-only audit와 deterministic report
- real authorization/credential persistence false invariant
- CLI runtime database 미접근
- synthetic fixture hash와 generated schema

최종 repository Gate는 ruff, mypy 57개 source file, non-PostgreSQL 228개 test,
plan/architecture/hidden/secret 검사, generated contract/OpenAPI/Frontend client freshness,
Markdown link와 `git diff --check`까지 모두 통과했다. Application/CLI/fixture만 변경했으므로
PostgreSQL, Frontend와 browser Gate는 변경 의존성이 없다.

## 12. 아직 하지 않은 것

- 실제 authentication과 SSO
- company principal/group와 inherited ACL
- vendor API credential, proxy, certificate와 secret manager
- API/Frontend enforcement middleware
- production logging/metrics/alert service
- canonical import와 durable quarantine
- company retention, approval과 write-back

따라서 ENT-E PASS는 사내 보안 승인이나 운영 readiness를 의미하지 않는다.

## 13. 다음 단계

ENT-F는 사내 적용 package를 작성한다.

- generic work-tracker/knowledge-base mapping template
- auth/network/secret/ACL/retention worksheet
- 한 Project allowlist와 rollback template
- `validate → dry-run → review → import → reconcile` runbook
- 예상 output과 합격/중단 기준
- 사외 검증과 사내 입력 항목을 구분한 handoff checklist

ENT-F도 실제 company value, credential 또는 write-back route를 repository에 추가하지 않는다.
