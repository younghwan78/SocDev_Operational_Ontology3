> 작성일: 2026-07-22

## 1. OPS-E가 해결한 질문

OPS-D는 사용자가 과제 전체 상태와 최상위 Risk를 먼저 찾게 했지만, 다음 질문은 한 화면에서
끝까지 답하지 못했다.

1. 이 Risk는 어떤 Issue, Event, Evidence 또는 다른 과제의 학습에서 나왔는가?
2. 관측 사실과 추론을 어떻게 구분하며, 왜 이 Risk가 먼저인가?
3. 어떤 WorkItem과 Milestone이 영향을 받는가?
4. 어떤 Decision과 Action이 위험을 제한하며, 검증·rollback 조건은 무엇인가?
5. Decision을 검토한 뒤 원래 Risk와 역사 시점으로 안전하게 돌아올 수 있는가?

OPS-E는 별도 score나 Agent 판단을 추가하지 않고 OPS-C가 제공하는 projection을 사용해 이
질문을 `source → inference/priority → impact → treatment`의 단일 읽기 경로로 연결한다.

## 2. 사용자 흐름

```text
Project Portfolio
  → Project Situation
    → Risk Detail
      1. 발생 근거
      2. 추론·우선순위
      3. 개발 영향
      4. Decision·Action
        → existing Decision Workspace
          → 같은 Risk Detail로 복귀
```

- 기본 경로: `/projects/:projectId/risks/:riskId`
- 과거 상태: `?at_step=<project-step>`
- Decision 진입 문맥: `from_project`, `from_risk`, 필요할 때만 `from_project_step`
- DecisionCase의 logical Step은 Project Step과 같다는 보장이 없으므로 Project `at_step`을
  Decision Workspace에 전달하지 않는다.

## 3. 구현 내용

### 3.1 Project Situation에서 모든 Risk 접근

- 최상위 Risk에 `근거·영향·대응 상세 추적` primary action을 추가했다.
- 두 번째 이후 Risk도 Backend rank 순서를 유지한 별도 목록에서 상세로 이동할 수 있다.
- 역사 Situation에서 들어오면 Risk Detail URL에 같은 `at_step`을 보존한다.
- Frontend는 Risk rank나 level을 다시 계산하지 않는다.

### 3.2 Risk Detail 정보 구조

Risk Detail은 한 화면에서 다음 네 section을 순서대로 제공한다.

|순서|사용자 질문|표시 내용|
|---:|---|---|
|1|어디에서 나왔는가|Issue, Event, Evidence, Evidence 한계, cross-project lesson|
|2|무엇을 추론했고 왜 먼저인가|epistemic status, inference basis, downside, blast radius, urgency, reversibility, ranking reason, missing Evidence|
|3|어디에 영향이 있는가|영향 WorkItem·Milestone과 현재 상태|
|4|어떻게 제한하는가|Decision, Action 상태·기한, verification Evidence, rollback 조건|

상단에는 Project, Risk rank/level/status, epistemic status와 관찰 Step을 표시하고, 네 section으로
바로 이동할 수 있는 짧은 trace navigation을 둔다. 알려진 inference rule과 Evidence limitation은
한국어 설명을 먼저 표시하며 canonical ID는 provenance 확인용 보조 정보로 유지한다.

### 3.3 역사 상태와 fail-closed 처리

- Risk Detail과 Project Situation은 동일한 `at_step`으로 병렬 조회한다.
- 선택 Step 이후의 Event, Evidence, Decision과 Action은 Backend historical projection에서 숨긴다.
- 범위를 벗어난 Step이면 이후 정보를 섞어 보여주지 않고 현재 시점 복구 action을 제공한다.
- 존재하지 않는 Project/Risk와 연결 실패도 불완전한 trace 대신 한국어 복구 화면을 표시한다.

### 3.4 기존 Decision Workspace 왕복

- Risk Detail은 OPS-C의 canonical Decision `href`에 origin query만 추가한다.
- 기존 Workspace는 query를 검증해 `← Risk 상세` link를 제공한다.
- Workspace의 Step 변경과 모바일 option 변경도 origin query를 보존한다.
- 임의 path가 back link가 되지 않도록 Project/Risk ID 형식을 검증한다.
- 현재 Risk와 역사 Step 20 모두 실제 fixture 브라우저에서 왕복을 확인했다.

## 6. Gate 해석과 남은 한계

OPS-E의 2분 source-to-impact-to-decision task는 화면 구조와 실제 fixture 왕복을 local Codex가
검토한 engineering proxy로 통과했다. 이는 사람이 실제로 2분 안에 이해했다는 측정 결과가
아니며, 의사결정 속도나 조언 품질의 business value 증거도 아니다.

남은 핵심은 기능 추가가 아니라 OPS-F 측정 전환이다.

- Project 중심으로 UX-H task와 baseline을 다시 동결한다.
- builder와 독립 proxy/domain reviewer를 구분한다.
- condition별 최소 표본과 정답·시간·복구·raw-detail 사용을 수집한다.
- human 결과 전에는 UX-I 정보 구조 축소나 business value 주장을 시작하지 않는다.
- Jira, Confluence, 인증, 권한 계승과 write-back은 계속 C0/C2 사내 범위로 남긴다.
