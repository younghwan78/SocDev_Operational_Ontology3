# Codex CLI I7-C 구현 및 평가 보고서

> 작성일: 2026-07-12  
> 범위: local fixture 기반 SoC Operational Ontology PoC  
> 평가 surface: ChatGPT 인증 Codex CLI  
> 모델: `gpt-5.6-luna`  
> reasoning effort: `high`

## 1. 결론

`gpt-5.6-luna + high`로 Role Agent, Challenger, simulated Chair를 직접 실행하는
I7-C 경로는 구현되었다. 별도 OpenAI API key 없이 ChatGPT 로그인 상태를 사용하며,
구조화 출력, hidden/도구 경계, token hard cap, canonical guardrail 검증, immutable
평가 artifact를 유지한다.

다만 현재 결과로 I7 전체 통과를 주장할 수는 없다.

1. 예비 B0-B3 ablation은 5/5 case에서 다중 역할의 추가 concern 또는 safeguard를
   확인해 계산상 `keep_b3`를 반환했다.
2. 최종 prompt/validator에 가까운 validation x5는 runtime policy 10/10을 통과했지만
   acceptable decision은 7/10으로 stability gate를 통과하지 못했다.
3. sealed-unseen x3는 ChatGPT Codex 사용량 한도 때문에 9/9가
   `PROVIDER_USAGE_LIMIT`로 기록되어 판단 품질을 평가하지 못했다.
4. canonical I7의 OpenAI Responses API 비용/latency gate는 Codex CLI로 대체되지
   않는다. I7-C는 별도 품질 진단 surface다.

따라서 현재 상태는 **I7-C 실행 경로 구현 완료, validation FAIL, sealed BLOCKED,
최종 topology 미확정**이다.

## 2. 왜 별도 I7-C인가

집에서는 Jira/Confluence나 회사 데이터 없이 fixture만 사용한다. 별도 API key와
token 단가를 준비하지 않아도 실제 모델 기반 판단을 관찰하기 위해 Codex CLI를
추가했다.

I7-C가 답할 수 있는 질문은 다음과 같다.

- Role별 concern이 단일 Architecture 역할보다 추가 가치를 만드는가?
- 데이터가 부족할 때 Agent가 가역 실험, 보류, escalation을 어떻게 trade-off하는가?
- Challenger와 Chair를 포함한 B3가 반복 실행에서도 정책과 판단 family를 유지하는가?
- grounded claim, dissent, guardrail, rollback 조건이 deterministic validator를
  통과하는가?

I7-C가 답할 수 없는 질문은 다음과 같다.

- OpenAI Responses API의 실제 USD 비용
- API latency와 rate-limit 특성
- 사내 Jira/Confluence connector의 권한, 품질, write-back
- 사람 승인 이후 실제 의사결정 속도 개선

## 3. 구현 범위

### 3.1 Provider

`backend/src/soc_ot/agents/codex_cli_provider.py`에 `CodexCliProvider`를 추가했다.

- Windows에서는 App Execution Alias를 피하고 Node.js와 설치된 Codex CLI entrypoint를
  직접 사용한다.
- `codex exec --ephemeral`과 임시 작업 디렉터리를 사용한다.
- 모델은 `gpt-5.6-luna`, effort는 `high`가 기본이다.
- apps, browser, multi-agent, memories, goals, web search를 비활성화한다.
- sandbox는 read-only, approval은 never다.
- 허용된 환경 변수만 전달하며 `OPENAI_API_KEY` 같은 secret은 전달하지 않는다.
- Pydantic schema를 Codex strict output schema로 변환한다.
- command, file, MCP, web, tool event가 발생하면 결과를 거부한다.
- ChatGPT subscription 사용량의 input/output token을 기록하고 USD는 `N/A`로 취급한다.

### 3.2 Grounding과 데이터 부족 결정

Role 입력에 다음 목록을 명시한다.

- `valid_claim_ids`
- `valid_option_ids`
- `valid_recommendation_types`

현재 step에 eligible claim이 없으면 실행형 결정인 `APPROVE`,
`APPROVE_WITH_GUARDRAILS`, `RUN_REVERSIBLE_TRIAL`을 Role 추천 후보에서 제외한다.
이때 Agent는 근거가 있는 것처럼 행동하지 않고 `DEFER_UNTIL_TRIGGER` 또는
`ESCALATE` 같은 risk-limiting 결정을 선택해야 한다.

이 변경은 `CASE-VR-005`에서 실제로 검증했다. 명시 전에는 Agent가 현재 packet에
없는 `CLM-SW-REVERSIBLE`, `CLM-BW-RISK`를 사용했으나, 명시 후에는 claim 배열을
비우고 보류 또는 escalation을 선택했다.

### 3.3 Chair 실행 계약

Chair 입력에는 다음 deterministic 계약을 명시한다.

- 모든 `required_dissent_role_ids`를 `dissent_acknowledged`에 보존
- canonical metric registry만 사용
- DDR/bandwidth risk는 `DDR_BANDWIDTH`, unit은 `GB/s`
- safeguard threshold는 `exact` mode와 단일 numeric value 사용
- role/challenger/chair hard cap은 각각 1,500/2,000/3,000 output tokens

`validate_decision_policy`도 metric registry, unit, exact threshold를 검사한다.
따라서 range threshold가 Outcome 단계까지 통과한 뒤 실패하지 않고 Chair clean
retry에서 먼저 교정된다.

### 3.4 Batch와 failure artifact

Codex CLI batch는 동시 실행 수를 설정할 수 있다. 실제 평가는 안정성을 위해
parallelism 2를 사용했다.

stability batch의 개별 case가 실패해도 성공 결과를 폐기하지 않는다. 실패는
`LiveEvaluationFailure`로 수집하고 artifact에 `runtime_failures.json`을 기록한다.
quota 소진은 schema repair나 transport retry로 소비하지 않고 terminal
`PROVIDER_USAGE_LIMIT`로 기록한다.

## 4. 실제 실행 결과

### 4.1 B3 종단 smoke

개발 case `CASE-VR-001`에서 실제 Role 4개, Challenger, 수정 Role, Chair 경로가
완료되었다.

|항목|결과|
|---|---|
|모델/effort|`gpt-5.6-luna` / `high`|
|결정|`APPROVE_WITH_GUARDRAILS`|
|provider attempts|7|
|token|input 77,019 / output 5,018|
|결정 family 수용성|통과|

이 smoke 과정에서 dissent ID 보존, eligible claim 0개 case의 추천 제약,
canonical metric 이름, exact threshold 누락을 순서대로 발견하고 deterministic
계약으로 보완했다.

### 4.2 예비 B0-B3 ablation

Artifact:
`output/evaluations/eval-2026-07-11.1/20260712T104356Z-codex-cli-6f156ba9/`

|항목|결과|
|---|---|
|대상|validation 2 + sealed-unseen 3 case|
|실행|20 topology runs, 예상 65 semantic calls|
|marginal cases|5/5|
|계산된 stop rule|`keep_b3`|
|token|input 670,011 / output 43,663|

주의: 이 artifact 이후 canonical metric과 exact threshold validator가 보강되었다.
따라서 이 결과는 **탐색 증거**이며 현재 code candidate의 최종 release evidence가
아니다. quota reset 후 현재 revision으로 ablation을 다시 실행해야 한다.

예비 결과에서는 B2가 5/5 process gate를 통과했지만 B3는 Chair guardrail metric
이름 때문에 process gate를 낮췄다. 즉 “여러 독립 Role의 가치”와 “Challenger+Chair의
가치”를 현재 stop rule이 충분히 분리하지 못한다.

### 4.3 Validation stability x5

Artifact:
`output/evaluations/eval-2026-07-11.1/20260712T111519Z-codex-cli-e9d020e4/`

|항목|결과|
|---|---|
|실행|2 cases x 5 = 10 B3 runs|
|runtime policy|10/10|
|acceptable decision|7/10|
|stability gate|FAIL|
|token|input 846,674 / output 58,408|

결정 분포:

|Case|분포|Acceptable|
|---|---|---:|
|`CASE-VR-004`|`RUN_REVERSIBLE_TRIAL` 4, `COLLECT_MINIMUM_EVIDENCE` 1|5/5|
|`CASE-VR-005`|`ESCALATE` 3, `DEFER_UNTIL_TRIGGER` 2|2/5|

`CASE-VR-005`는 eligible claim이 없고 고객 요구와 area/interface cost가 불확실하다.
Luna/high는 이 상황에서 escalation을 자주 선택했다. 시스템 계약을 위반한 것은
아니지만 frozen expected result는 `RUN_REVERSIBLE_TRIAL` 또는
`DEFER_UNTIL_TRIGGER`만 acceptable로 정의하므로 gate가 실패했다.

이 차이는 프롬프트 정답 유도로 덮지 말아야 한다. 다음 중 어느 것이 제품 정책인지
ADR로 결정해야 한다.

1. 고객 요구 미확정 + 정량 근거 0개이면 escalation도 합리적인 risk-limiting
   decision으로 인정한다.
2. local product owner agent가 사람 대행 역할을 하므로, reversible option이 남아
   있을 때 escalation보다 명시적 trigger를 둔 defer를 우선한다.

|항목|결과|
|---|---|


batch를 재실행해야 한다.

## 5. Topology 판단

현재 evidence만으로 B3를 최종 채택하면 안 된다.

- 단일 Role B1보다 다중 Role B2/B3가 추가 concern을 만든다는 예비 증거는 5/5다.
- 예비 ablation에서 B2 process는 5/5였고 B3가 오히려 guardrail correctness를
  낮췄다.
- validator 보강 후 validation B3 runtime policy는 10/10이지만 decision stability는
  실패했다.
- sealed 결과는 quota 때문에 없다.

따라서 현재 추천은 다음과 같다.

1. **독립 Role Agent 구조는 유지 후보**다.
2. **B3 최종 채택은 보류**한다.
3. B2를 명시적 release 후보로 선택할 수 있도록 stop rule을
   `keep_b3 / release_b2 / release_b1 / release_b0`로 확장할지 검토한다.
4. Challenger와 Chair의 독립 기여는 B3 vs B2 delta로 별도 계산한다.

이 변경은 평가 protocol 변경이므로 현재 sealed 결과를 본 뒤 즉시 코드에 반영하지
않고 ADR과 새 evaluation release를 먼저 만들어야 한다.

## 6. 재실행 순서

ChatGPT Codex 사용량이 다시 열린 뒤 다음 순서로 실행한다.

```powershell
uv run soc-ot agent preflight --provider codex-cli

$env:SOC_OT_CODEX_CLI_MODEL = "gpt-5.6-luna"
$env:SOC_OT_CODEX_CLI_REASONING_EFFORT = "high"
$env:SOC_OT_CODEX_CLI_PARALLELISM = "2"

uv run soc-ot evaluation ablate `
  --provider codex-cli `
  --partitions validation,sealed-unseen `
  --acknowledge-usage

uv run soc-ot evaluation stability `
  --provider codex-cli `
  --topology B3 `
  --partition sealed-unseen `
  --repeat 3 `
  --acknowledge-usage
```

validation은 이미 최종 semantic prompt에 가까운 결과가 있으므로 제품 정책 ADR 전에는
반복 실행으로 우연히 PASS를 고르지 않는다. ADR로 acceptable family를 유지하기로
결정한 경우에만 같은 frozen release에서 validation을 재확인한다.

## 7. 완료 조건

I7-C를 품질 gate까지 완료하려면 다음이 모두 필요하다.

- 현재 revision으로 B0-B3 ablation artifact 재생성
- sealed-unseen 3회 성공 결과 확보
- validation `CASE-VR-005`의 escalation 정책 ADR
- B2와 B3의 marginal value를 분리하는 stop rule 결정
- validation/sealed gate 결과와 최종 topology를 implementation status에 반영
- canonical OpenAI Responses API I7과 I7-C의 증거 범위를 계속 분리
