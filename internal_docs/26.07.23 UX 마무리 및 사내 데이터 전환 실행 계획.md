# UX 마무리 및 사내 데이터 전환 실행 계획

> 작성일: 2026-07-23
> 현재 위치: ENT-B mapping registry와 dirty fixture corpus 완료, 독립 관측 baseline 0/5·product 0/5에서 보류, 다음 단계 ENT-C
> 갱신일: 2026-07-25
> 실행 순서: **UX Release 1 완료 → 사외 Enterprise Preparation 완료 → 사내 C0/C1 read-only 적용**
> 범위 원칙: 사외 repository에는 synthetic fixture만 사용하며 회사 data, credential, 실제 ACL, vendor connector와 write-back을 넣지 않는다.

2026-07-23 owner 결정으로 OPS-F human observation은 0/5씩인 상태에서 보류했다. 따라서 UX-I/J/K는
engineering-proxy Gate로 진행하며 human task-time, 이해도 또는 business value 개선을 주장하지 않는다.

## 1. 결론

사내 data 연결 전에 현재 제품 UX를 먼저 마무리한다. 여기서 “마무리”는 화면을 더 많이 만드는 것이
아니라 사용자가 다음 핵심 질문에 빠르고 정확하게 답하고, 자신의 판단과 Agent 조언을 구분해 기록할
수 있는 **Local UX Release 1**을 동결하는 것이다.

그다음 사외에서 source-neutral ingestion 계약, mapping/dry-run 엔진, 지저분한 fixture, 품질·격리
도구와 사내 적용 package까지 구현한다. 사내에서는 코드를 처음부터 개발하지 않고 실제 Jira/
Confluence 환경의 field/status, 인증, ACL과 network를 설정하고 한 과제로 검증하는 데 집중한다.

```text
OPS-F human observation 보류
  → UX-I engineering-proxy 축소·개선 완료
  → UX-J 사람 판단과 Agent 조언 분리
  → UX-K Local UX Release 1 동결
  → ENT-A~ENT-F 사외 Enterprise Preparation
  → C0 사내 환경·schema-fit·read-only smoke
  → C1 한 과제 operational pilot
  → C2 별도 승인 후 controlled write-back
```

UX와 enterprise 준비를 병행하지 않는다. UX가 흔들리는 동안 source mapping을 시작하면 data 문제와
화면 문제를 구분하기 어렵고, 화면이 요구하는 projection이 계속 바뀌어 connector를 다시 만들게 된다.

## 3. UX 마무리

### 3.1 OPS-F Observation — UX 변경 전에 문제를 측정

현재 제품 release와 baseline/rubric은 이미 고정돼 있다. 이 단계에서는 UI를 수정하지 않고 다음을
수집한다.

- baseline과 product에 서로 다른 proxy/domain participant 최소 5명씩
- 11개 task의 시작·종료, 제출 답변, reviewer 판정
- Issue/Risk/Evidence와 관측/추론/미확인의 오분류
- wrong primary action, 불필요한 detail open, recovery 사용
- draft, excluded session과 고정된 제외 사유
- task별 시간 분포와 safeguard completeness

Gate:

1. 각 condition에 유효한 독립 완료 관측이 5개 이상이다.
2. participant-hidden rubric으로 같은 기준을 적용했다.
3. 제외·중단 관측이 보고서에 남아 있다.
4. 가장 느린 task, 가장 자주 틀린 경계, 불필요한 왕복을 우선순위로 정한다.
5. 작은 표본을 business proof로 표현하지 않는다.

### 3.2 UX-I — Engineering-proxy 정보 구조 축소·개선

원칙적으로 OPS-F 결과에서 확인된 문제만 수정한다. 현재는 owner 예외에 따라 browser·accessibility·
fixture task 근거로 사전 지정한 문제만 수정하며, 새 dashboard나 ontology object를 추가하지 않는다.

우선순위 규칙:

1. 잘못된 결정 또는 epistemic 오분류를 만드는 문제
2. 과제 우선순위와 최상위 Risk를 늦게 찾게 하는 문제
3. source → inference → impact → treatment 추적을 끊는 문제
4. Project와 Decision 사이에서 문맥을 잃는 문제
5. 모바일·키보드·화면 읽기에서만 발생하는 문제
6. 단순 미관 또는 개인 선호

구현 package:

- `UX-I1`: OPS-F summary로 change backlog와 변경하지 않을 항목 동결
- `UX-I2`: Portfolio/Situation의 중복 정보와 우선순위 표현 축소
- `UX-I3`: Risk provenance/impact/treatment progressive disclosure 조정
- `UX-I4`: Decision Workspace의 selected/current, 관측/예상/미확인 표현 정리
- `UX-I5`: 동일 task 재검증, release hash 갱신과 before/after report

검색, filter, pagination, virtualization은 실제 fixture 규모 또는 task 결과가 필요성을 보인 경우에만
UX-I에 넣는다. enterprise 규모를 예상했다는 이유만으로 제품 화면에 먼저 추가하지 않는다.

Gate:

- 사전 지정한 상위 3개 문제 중 적어도 하나 이상이 개선된다.
- 핵심 task accuracy와 no-future-leakage가 떨어지지 않는다.
- raw ontology/Role original을 열어야만 답할 수 있는 질문이 늘지 않는다.
- 변경이 개선되지 않으면 해당 변경을 유지하지 않고 원인을 기록한다.

### 3.3 UX-J — builder 판단과 Agent 조언 분리

프로젝트 목표가 “Agent가 대신 승인”이 아니라 “사람의 의사결정 속도와 품질을 돕는 것”이므로,
Local UX Release 1 전에 이 경계를 닫아야 한다.

권장 interaction:

1. 사용자가 source와 Risk를 검토한다.
2. Agent/Simulated Chair 결론을 공개하기 전에 builder의 초기 선택, 수용 Risk, safeguard와 이유를 기록한다.
3. Agent 조언과 dissent를 공개한다.
4. 사용자가 `accept`, `modify`, `reject` 중 하나와 변경 이유를 기록한다.
5. 초기 판단, 조언, 최종 response를 서로 다른 immutable record로 보존한다.

구현 package:

- `ReviewerResponse` evaluation-only contract와 ADR
- initial response와 advice reveal의 명시적 상태 전이
- Agent 조언이 builder 입력 field를 덮어쓰지 않는 API/repository 경계
- accept/modify/reject와 변경 이유 projection
- reload, conflict, retry와 historical Step 비오염 E2E
- simulated Chair, builder response, 향후 human response, 실제 company approval의 시각적·문구상 분리

이 단계는 실제 승인 객체, Jira transition 또는 write-back을 만들지 않는다.

Gate:

- advice 공개 전 builder의 초기 판단이 기록되며 `engineering_proxy_only`로 분류된다.
- advice 이후 변화와 이유를 비교할 수 있다.
- Agent output을 승인으로 오인할 UI가 없다.
- source 없는 Agent claim은 계속 canonical truth가 될 수 없다.

### 3.4 UX-K — Local UX Release 1 동결

UX-I/J 완료 후 전체 제품을 하나의 사용자 여정으로 다시 검증한다.

검증 여정:

```text
Portfolio
  → Project 전체 상황과 막힌 WorkItem/Gate
  → top/remaining Risk와 발생 근거
  → 영향 WorkItem/Milestone
  → Decision 선택지·이견·안전 조건
  → builder initial response
  → Agent advice reveal
  → accept/modify/reject
  → Action/Outcome/Evaluation
  → 원 Project/Risk 문맥 복귀
```

Release Gate:

- 한국어 우선 정보 구조와 canonical ID의 보조적 표시
- 390px, 768px, desktop, 200% zoom-equivalent reflow
- keyboard, focus, semantic landmark, Axe와 reduced motion
- loading, empty, partial, stale, conflict, network, unavailable history 복구
- current/historical Project와 Decision timeline 경계
- 전체 browser E2E, unit, contract, migration, hidden, secret 회귀
- product revision, UI/API contract, fixture, task/rubric hash 재동결
- “Local fixture UX Release 1”로만 표현하고 business value 완료를 주장하지 않음

## 4. 사외 Enterprise Preparation

UX-K Gate 뒤 새 ADR을 승인하고 시작한다. 이 단계는 실제 Jira/Confluence API를 호출하지 않는다.

### ENT-A. Source-neutral ingestion 계약

구현 상태: **완료**. ADR-0012가 `enterprise-source-record.v1`, stable identity, 네 가지
timezone-aware time, opaque ACL/classification, 삭제·접근 제한 payload 경계와
`SourceReader`/`IngestionSink` Protocol을 승인한다. 실제 adapter, mapping, persistence와 sync는
추가하지 않았으며 ENT-B가 다음 단계다.

산출물:

- `EnterpriseSourceRecord` envelope
- source system/tenant/object type/external ID/version identity
- effective/observed/source-updated/ingested time
- content hash, source URL, deletion state
- opaque ACL reference와 data classification
- `SourceReader`와 `IngestionSink` Protocol
- vendor SDK를 import하지 않는 application boundary

Gate:

- 같은 external object의 rename/update/delete를 stable identity로 표현한다.
- 수정 시각과 업무 발생 시각을 혼동하지 않는다.
- ACL/classification이 없으면 fail closed한다.

### ENT-B. Mapping registry와 dirty fixture corpus

구현 상태: **완료**. ADR-0013과 `enterprise-mapping-registry.v1`은 다섯 synthetic source profile,
mapping/status version, source span과 extractor provenance를 고정한다. Hash-pinned corpus의 normal
및 9개 dirty pattern은 모두 `ACCEPT`, `QUARANTINE` 또는 `REJECT`로 판정된다. Unstructured text는
`UNREVIEWED` CLAIM/RISK/ASSUMPTION candidate일 뿐 FACT가 아니다. 실제 canonical import, durable
quarantine와 sync는 추가하지 않았으며 ENT-C가 다음 단계다.

산출물:

- YAML/JSON mapping profile contract
- source status/field/type을 canonical Project/WorkItem/Issue/Evidence/Event candidate로 변환하는 registry
- Jira/Confluence를 모사하되 실제 회사 field를 사용하지 않는 synthetic export fixture
- 누락 field, unknown status, duplicate update, out-of-order event, moved page, deleted object,
  restricted object, conflicting source와 늦게 도착한 Evidence fixture
- unstructured text를 FACT가 아닌 candidate claim/risk/assumption으로 보존하는 contract

Gate:

- 정상 fixture뿐 아니라 모든 dirty fixture가 명시적으로 accept, quarantine 또는 reject된다.
- source span과 mapping/extractor version 없이 candidate를 만들지 않는다.
- 사람이 검토하지 않은 text extraction을 FACT로 승격하지 않는다.

### ENT-C. Idempotent sync와 reconciliation engine

산출물:

- cursor와 page token state
- content-hash idempotency
- retry/backoff와 bounded failure
- tombstone/delete 처리
- out-of-order Event 정렬과 late-arrival policy
- full reconciliation과 incremental sync의 결과 비교
- 같은 input을 재처리해도 같은 canonical candidate와 audit가 나오는 test

Gate:

- 중복 import가 Project version이나 Event를 부풀리지 않는다.
- 중단 후 재시작해 누락 없이 이어진다.
- 삭제·권한 축소를 stale content보다 우선 적용한다.

### ENT-D. Dry-run, quality와 quarantine

산출물:

- source validation CLI
- write 없이 실행되는 mapping dry-run
- 생성/변경/삭제 예정 canonical object diff
- dangling reference, time ambiguity, unmapped field와 ACL 누락 report
- quarantine queue와 사람이 입력할 resolution file
- freshness, mapping coverage와 rejected/quarantined count summary

Gate:

- dry-run이 canonical DB를 변경하지 않는다.
- 한 개 오류 때문에 전체 source를 조용히 버리지 않는다.
- 적용 전 사람이 변경량과 차단 사유를 이해할 수 있다.

### ENT-E. Security/operation emulator

실제 authentication은 구현하지 않지만 connector가 지켜야 할 경계를 fixture로 검증한다.

산출물:

- synthetic principal과 ACL allow/deny matrix
- classification별 UI/model/log 노출 정책 test
- credential이 payload/audit/error에 들어가지 않는 redaction test
- sync lag, stale source, rate-limit, partial source와 recovery fixture
- health/readiness, metrics와 audit event contract

Gate:

- 권한 정보가 없거나 충돌하면 노출하지 않는다.
- restricted source가 Role packet, API, log와 Frontend에 나타나지 않는다.
- source freshness를 모를 때 최신으로 표시하지 않는다.

### ENT-F. 사내 적용 package

산출물:

- Jira field/status mapping template
- Confluence space/page/label mapping template
- auth/network/secret/ACL/retention 확인 worksheet
- 한 Project allowlist와 rollback template
- `validate → dry-run → review → import → reconcile` runbook
- 예상 output example과 합격/중단 기준
- 사내에서 채워야 하는 값과 사외에서 이미 검증된 코드를 구분한 handoff checklist

Gate:

- 사내 작업이 vendor/environment 설정과 실제 data 검증으로 제한된다.
- 실제 credential과 company export를 repository에 commit하지 않는 절차가 있다.
- read-only pilot 전에 write-back route가 존재하지 않는다.

## 5. 사내 C0/C1 적용

### C0-A. 환경 discovery

- Jira/Confluence deployment/version과 허용 API 확인
- 인증, proxy, certificate, secret store와 rate limit 확인
- pilot Project/Space, data owner, security owner, human decision authority 지정
- source ACL, data classification, retention, deletion과 model provider 승인

### C0-B. Sanitized schema-fit

- 승인된 한 Project export를 ENT dry-run에 입력
- unmapped field/status, identity collision, time ambiguity, dangling relation과 ACL 누락 검토
- mapping profile만 수정하고 canonical/UX 계약 변경은 별도 review
- 예상 Project/Risk/Decision projection을 domain reviewer가 source와 대조

### C0-C. One-project read-only smoke

- allowlist 한 Project/Space만 live read
- 첫 full sync와 두 번의 incremental sync/reconciliation
- rename/update/delete/restricted source와 restart recovery 검증
- source freshness, mapping quality와 quarantine을 UI/운영 report에서 확인
- 실제 Jira/Confluence에 어떤 write도 발생하지 않음을 audit로 확인

C0 Gate:

- ACL 누출 0건
- silent drop 0건
- duplicate canonical Event 0건
- source time과 observed time의 검토 표본 일치
- quarantine과 freshness가 운영자가 이해 가능한 수준으로 표시
- Project 전체 상황/Risk provenance UX가 source 원문과 대조 가능

### C1. Read-only operational pilot

한 과제와 한 review workflow에서 실제 사용자의 baseline과 product 결과를 측정한다. UX Release 1은
사내 data에 맞춰 무조건 유지하는 고정물이 아니라, 실제 workflow 차이가 확인될 때만 변경하는
검증 기준점이다.

- 최소 historical 10 case와 prospective 10 case를 방향성 표본으로 사용
- Situation-to-Decision Time과 Evidence Pack Preparation Time
- Critical Impact Recall과 Safeguard Completeness
- advice accept/modify/reject와 변경 이유
- data quality 실패, UX 실패와 advice quality 실패를 별도 분류

## 6. 범위 밖과 중단 기준

다음은 C1 가치·보안 Gate 전까지 구현하지 않는다.

- Jira issue transition 또는 field update
- Confluence page/comment 작성
- 실제 승인 상태 변경
- 조직 전체 crawling
- 개인 email/chat 수집
- ACL을 우회하는 service account projection
- Agent가 source text를 근거 없이 FACT로 승격

즉시 중단 조건:

- restricted source가 API, Role packet, log 또는 UI에 1건이라도 노출
- 삭제·권한 축소 이후 stale content가 계속 노출
- source 없는 authoritative claim이 canonical truth로 저장
- dry-run과 actual import의 변경 집합이 설명 없이 달라짐
- UX가 source 원문과 다른 Project/Risk 상태를 현재 사실로 표시

## 7. 구현 순서 요약

```text
OPS-F Observation
  ├─ 5 baseline + 5 product independent sessions
  └─ 문제 우선순위 동결

UX-I Measured Simplification
  ├─ Portfolio/Situation/Risk/Workspace 최소 변경
  └─ before/after 재검증

UX-J Builder/Agent Separation
  ├─ initial builder response (engineering proxy only)
  ├─ advice reveal
  └─ accept/modify/reject

UX-K Local UX Release 1
  ├─ 전체 여정·복구·접근성·historical Gate
  └─ release hash 동결

ENT-A~F External Preparation
  ├─ source-neutral contract
  ├─ dirty fixture mapping
  ├─ sync/reconciliation
  ├─ dry-run/quarantine
  ├─ security emulator
  └─ internal handoff kit

C0/C1 Internal
  ├─ 실제 설정과 sanitized schema-fit
  ├─ one-project read-only smoke
  └─ operational value pilot
```

이 계획의 핵심은 사내 연결을 늦추는 것이 아니라, **UX 변경과 connector 변경을 동시에 하지 않도록
순서를 고정하고 사외에서 실제 data 없이 검증 가능한 코드를 최대한 완성하는 것**이다.
