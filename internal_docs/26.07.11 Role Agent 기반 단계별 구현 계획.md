## 1. 문서 목적

이 문서는 SoC 개발의 진행 상태와 불확실성을 모델링하고, 역할별 Agent와 가상의 최종 승인 Agent를 이용해 의사결정 과정을 실행·평가하는 시스템의 구현 순서를 정의한다.

집에서는 실제 Architect, HW/SW 개발자, Verification, PM, Management가 참여하지 않는다. 따라서 Role Agent는 보조 기능이 아니라 synthetic development world를 검토하고 의사결정을 실행하는 핵심 구성요소로 사용한다.

다만 Agent가 만든 주장이나 결정은 실제 회사의 engineering truth가 아니다. 모든 결과는 다음처럼 구분한다.

```text
source_fact          fixture에서 직접 확인되는 사실
human_defined_rule   사용자가 정의한 정책 또는 제약
agent_assumption     Agent가 추론한 가정
agent_advice         Role Agent가 제안한 의견
simulated_decision   Decision Chair Agent가 내린 가상 결정
simulated_outcome    숨겨진 fixture와 rule로 산출된 가상 결과
```

이 구분을 UI, API, 저장 데이터에서 유지한다.

## 2. 최종 목표

> **SoC 개발의 실제 진행 상태와 불확실성을 운영 온톨로지로 재현하고, 여러 전문 Role Agent가 독립적으로 판단한 뒤 Decision Chair Agent가 조건부·가역적·저후회 결정을 내리며, Outcome Engine이 그 결정의 결과를 진행시켜 의사결정 품질을 평가하는 시스템을 만든다.**

첫 PoC의 성공은 “Agent가 정답을 맞혔다”로 판단하지 않는다. 다음을 검증해야 한다.

1. Agent가 현재 개발 진행, dependency, deadline을 올바르게 읽는가?
2. 역할별로 실제로 다른 concern과 trade-off를 제시하는가?
3. Data 부족을 무조건 blocker로 처리하지 않는가?
4. 조건부 진행 시 guardrail과 rollback trigger를 제안하는가?
5. 비가역적 변경은 더 보수적으로 판단하는가?
6. Role 간 의견 충돌이 최종 결정에서 사라지지 않고 보존되는가?
7. Outcome이 나빴더라도 당시 정보에서 합리적인 결정이었는지 구분하는가?
8. 사용자가 한국어 UI에서 결정 이유와 다음 행동을 쉽게 이해할 수 있는가?

## 4. 전체 시스템 구조

```text
[Synthetic World Authoring]
World Builder Agent + Fixture Auditor Agent
        ↓ freeze
[Observable Development World]
Project / Track / Work / Dependency / Milestone / Evidence / Known Uncertainty
        ↓
[Agent Router]
질문에 필요한 Role Agent만 선택
        ↓
[Independent Role Review]
Product / Architecture / HW / SW / Verification / Program-Risk
        ↓
[Challenge Round]
반대 가정 / 누락 / 지나친 낙관·보수성 검토
        ↓
[Decision Dossier]
공통 사실 / 선택지 / 의견 일치 / 의견 충돌 / 불확실성 / deadline
        ↓
[Decision Chair Agent]
Approve / Conditional / Trial / Collect Evidence / Defer / Reject / Escalate
        ↓
[Outcome Engine]
Hidden State와 결정 rule을 사용해 개발 상태와 결과 진행
        ↓
[Evaluator]
의사결정 과정 품질 / 실제 결과 / regret / guardrail 효과 평가
        ↓
[한국어 Decision Workspace]
결정 이유 / 진행 상황 / 선택지 / 조건 / 결과 / 학습
```

### 4.1 가장 중요한 경계

```text
Role Agent가 볼 수 있는 것:
  observable fixture
  현재까지 공개된 evidence
  known uncertainty
  자신의 role contract

Role Agent가 볼 수 없는 것:
  실제 hidden root cause
  미래 measurement
  option별 실제 outcome
  expected evaluation answer
  다른 Role Agent의 1차 판단
```

이 경계를 코드와 test로 강제한다.

## 5. Agent 구성

### 5.1 Authoring Agent

#### World Builder Agent

목적:

- 실제와 비슷한 synthetic development case 후보 생성
- development track, work, dependency, evidence, option, hidden outcome 초안 작성

출력:

- observable fixture 후보
- hidden outcome 후보
- 주요 domain assumption
- case 난이도와 의도

금지:

- 생성한 case를 스스로 최종 검증했다고 선언
- 실제 회사 정보처럼 표현
- runtime Agent에게 hidden outcome 노출

#### Fixture Auditor Agent

목적:

- World Builder와 독립적으로 fixture의 모순·누락·편향 검사

검사 항목:

- timeline 불가능성
- 순환 dependency
- option이 사실상 하나뿐인 가짜 trade-off
- evidence와 hidden outcome의 직접 누출
- 특정 Role Agent만 항상 정답이 되는 편향
- data 부족 case가 전부 defer로 끝나는 편향
- 결정과 상관없이 outcome이 같은 무의미한 case

### 5.2 Runtime Role Agent

#### Product/Customer Agent — 선택적

판단:

- 고객 가치와 feature 필요성
- 경쟁력과 product timing
- 요구사항 불확실성
- option을 보존할 가치

금지:

- PPA 또는 구현 가능성 확정
- 실제 고객 의도를 사실로 생성

#### Architecture/System Agent — 기본

판단:

- cross-IP 영향
- 구조적 dependency
- PPA와 확장성 trade-off
- 비가역적 architecture 변경
- 차기 project reuse와 option value

금지:

- 실제 RTL effort 확정
- evidence 없이 root cause 확정

#### HW Agent — 관련 case에서 기본

판단:

- RTL/micro-architecture 변경 범위
- area/timing/power pressure
- 변경 가능 시점과 freeze 영향
- verification 및 rework 비용
- HW option의 reversibility

금지:

- 고객 우선순위 결정
- 준비되지 않은 측정값 생성

#### SW Agent — 관련 case에서 기본

판단:

- HAL/FW/driver/interface 영향
- feature flag, workaround, fallback 가능성
- SW integration과 maintenance risk
- rollback 가능성과 technical debt

금지:

- HW capability를 근거 없이 가정
- 임시 workaround를 영구 해결로 표현

#### Verification/Measurement Agent — 기본

판단:

- 관측 가능성과 test coverage
- 최소 판별 실험
- 측정 가능한 시점
- success/failure criterion
- rollback/review trigger로 사용할 metric

금지:

- 아직 실행하지 않은 test를 통과한 것으로 표현
- data 부족만을 이유로 무조건 defer

#### Program/Risk Agent — 기본

판단:

- decision deadline
- critical dependency
- milestone 지연과 resource impact
- decision을 기다리는 비용
- risk owner와 escalation 필요성

금지:

- 기술 root cause 확정
- 일정만을 이유로 safety/quality constraint 무시

### 5.3 Meta Agent

#### Agent Router

입력:

- Decision Case type
- affected component/track
- option 특성

출력:

- 실행할 Role Agent 목록
- 제외한 Agent와 이유
- 실행 순서 또는 병렬 그룹

원칙:

- 모든 case에서 모든 Role Agent를 호출하지 않는다.
- case당 선택 Role Agent는 최대 5개다.
- Architecture/System, Verification/Measurement, Program/Risk는 초기 기본 후보이다.
- HW 또는 SW 영향이 없으면 해당 Agent를 제외할 수 있다.

#### Challenger Agent

목적:

- Role 결과의 공통 맹점과 성급한 합의 탐지

검사 질문:

- 모두 같은 잘못된 가정을 공유하는가?
- 낮은 확률이지만 큰 downside를 누락했는가?
- 되돌릴 수 없는 선택을 너무 쉽게 권고했는가?
- data 부족을 과도하게 blocker로 사용했는가?
- schedule 때문에 technical debt와 verification gap을 숨겼는가?
- guardrail이 실제로 관측·실행 가능한가?

#### Decision Chair Agent

목적:

- 집에서 실제 최종 승인자를 대신해 simulated decision 생성

Decision Chair는 다수결로 결정하지 않는다. 다음을 종합한다.

```text
customer/product value
development deadline
technical impact
evidence completeness
uncertainty
reversibility
downside and blast radius
detectability and recoverability
guardrail strength
residual risk
dissenting role opinion
```

허용 결정:

```text
APPROVE
APPROVE_WITH_GUARDRAILS
RUN_REVERSIBLE_TRIAL
COLLECT_MINIMUM_EVIDENCE
DEFER_UNTIL_TRIGGER
REJECT
ESCALATE
```

Decision Chair도 항상 `simulated_decision=true`를 가진다.

### 5.4 Outcome/Evaluation Component

#### Outcome Engine

Outcome Engine은 LLM이 아니라 frozen hidden fixture와 명시적 transition rule을 우선 사용한다.

역할:

- 선택한 option에 맞는 hidden outcome path 선택
- action 완료에 따라 development state 변경
- 시간이 지나면서 measurement/evidence 공개
- guardrail/trigger 충족 여부 평가
- rollback, rework, milestone delay, technical debt 생성

#### Decision Evaluator

다음 두 축을 분리해 평가한다.

```text
Process Quality:
  당시 알 수 있는 정보로 합리적인 결정이었는가?

Outcome Quality:
  실제 simulated outcome이 좋았는가?
```

좋은 process가 우연히 나쁜 outcome을 낼 수 있고, 나쁜 process가 운 좋게 좋은 outcome을 낼 수도 있다. 두 점수를 합치지 않는다.

## 7. Repository 목표 구조

단일 기준은 `docs/readiness/01_MASTER_EXECUTION_PLAN.md`의 Canonical repository layout이다. Backend는 `backend/src/soc_ot`, Frontend는 `frontend/src`, Backend test는 `backend/tests` 아래에 둔다. 별도 top-level `src/soc_ot`, `ui`, `tests` tree를 만들지 않는다.

초기에는 별도 agent framework를 도입하지 않는다. 명시적인 Python orchestrator와 provider interface로 시작하고, 실제 복잡도가 필요성을 입증한 뒤 framework를 검토한다.

### 상태 모델

```text

  PLANNED → READY → IN_PROGRESS → DONE → VERIFIED
  READY/IN_PROGRESS → BLOCKED
  DONE/VERIFIED → REWORK

DecisionCase:
  DRAFT → CONTEXT_BUILDING → OPTIONS_READY → DECISION_REQUIRED
  → DECIDED → ACTIONING → VERIFIED → CLOSED
```

2. JSON Schema export/sync

- Architecture/HW/SW/Verification track이 서로 다른 상태를 가질 수 있다.
- 특정 시점의 observable state를 재현한다.
- hidden field가 observable serialization에 포함되지 않는다.

## Step 2. Synthetic World와 Hidden Outcome 구축

### 목표

Agent가 실제로 고민해야 하는 불완전한 개발 세계를 만든다.

### Project archetype

기존 Project U/V/W fixture를 복사하지 않고 다음 의미만 재설계한다.

```text
Reference Generation:
  이전 또는 상용 과제의 issue/evidence/lesson

Active Generation:
  Architecture/HW/SW/Verification이 동시에 진행되는 주 대상

Next Generation:
  현재 decision에서 보존하거나 넘겨야 할 architecture option
```

### 첫 5개 case

#### CASE-VR-001. UHD60 EIS power gap

- bandwidth measurement가 아직 없음
- SW control은 되돌릴 수 있음
- HW carry-over는 변경 window가 좁음
- 목표: 조건부 진행과 guardrail 판단

#### CASE-VR-002. 8K30 HDR 추가 요청

- architecture freeze가 임박
- 고객 가치는 높지만 sustained thermal data 없음
- 목표: option 보존, 최소 evidence, defer/escalate 판단

#### CASE-VR-003. ISP path 변경과 HW/SW mismatch

- HW interface는 변경됐지만 SW 선행 구현은 이전 contract 기준
- 목표: dependency와 integration risk, milestone 영향 판단

#### CASE-VR-004. Heavy recording thermal evidence 충돌

- 이전 lab data와 현재 model prediction의 방향이 다름
- 목표: 두 가설을 구분하는 최소 판별 실험 제안

#### CASE-VR-005. AI camera feature의 고객 요구 불확실성

- 고객 요청이 확정되지 않았고 NPU/ISP option의 비용이 다름
- 목표: full commitment 대신 option value 보존 판단

### 각 case 필수 구성

- observable state
- hidden root cause
- 2개 이상의 실제 선택지
- option별 hidden outcome path
- decision deadline
- delay cost
- reversibility
- detectability
- resource constraint
- expected acceptable decision types
- unacceptable decision type과 이유
- process evaluation rule
- outcome evaluation rule

### Authoring flow

```text
World Builder Agent 초안
  → Fixture Auditor Agent 비판
  → schema/rule validator
  → fixture freeze
  → runtime Agent 접근 차단
```

### Gate 2

- 각 case에서 option에 따라 outcome이 실제로 달라진다.
- hidden outcome 없이도 최소 2개의 plausible option이 존재한다.
- data 부족 case가 모두 같은 decision type으로 끝나지 않는다.
- Runtime input에서 hidden outcome leakage가 0건이다.
- case별 domain assumption register가 존재한다.

## Step 3. 단일 Role Agent Runtime

### 목표

다중 Agent 토론 전에 각 Agent가 자기 역할을 정확히 수행하는지 검증한다.

### 구현 순서

1. `RoleAgent` protocol
2. `LLMProvider` interface
3. prompt/version registry
4. structured output parser
5. Pydantic validation
6. forbidden claim validator
7. fact/assumption/source reference validator
8. replay provider
9. live provider adapter

### 첫 Agent 순서

```text
1. Architecture/System
2. Verification/Measurement
3. Program/Risk
4. HW
5. SW
6. Product/Customer — 필요한 case만
```

### 실행 모드

#### Regression Mode

- 저장된 Agent response 재생
- contract, UI, evaluation 회귀 test
- 외부 API 없이 실행 가능

#### Exploration Mode

- 실제 LLM 호출
- 복수 run으로 다른 관점 탐색
- model, prompt, provider가 지원한 parameter, timestamp 기록

### 단일 Agent test

- 같은 fact와 assumption을 구분하는가?
- 자기 role 범위를 벗어나지 않는가?
- development state와 deadline을 언급하는가?
- data 부족 시 최소 evidence 또는 guardrail을 제안하는가?
- hidden 정보와 일치하는 내용을 우연히 말해도 근거 없는 fact로 확정하지 않는가?

### Gate 3

- 모든 output이 Role Review Contract를 통과한다.
- unsupported authoritative claim을 validator가 차단한다.
- 역할별 forbidden behavior test가 통과한다.
- replay mode 결과가 deterministic하다.
- exploration mode 실행 metadata가 완전히 기록된다.

## Step 4. Multi-Role Deliberation과 Challenger

### 목표

역할별 독립 판단과 의견 충돌을 의사결정 dossier로 만든다.

### 실행 방식

#### Round 1. Independent Review

- 각 Agent는 다른 Agent의 결과를 보지 않는다.
- anchoring과 조기 합의를 방지한다.

#### Challenge pass

- Challenger가 공통 가정, 빠진 downside, 실행 불가능한 guardrail을 지적한다.
- 필요한 Role에만 재검토 요청을 보낸다.

#### Round 2. Bounded Revision

- Role Agent는 원 의견 유지 또는 수정 가능
- 변경 이유를 기록
- dissent는 삭제하지 않음

#### Synthesis

- Decision Dossier 생성
- 합의와 충돌을 별도 field로 유지

### Orchestrator 원칙

- 무제한 Agent 토론 금지
- 최대 2 review round
- revision 대상 Role은 case당 최대 2개
- 같은 질문 반복 금지
- 모든 message와 version audit
- role count보다 decision quality를 우선

### Gate 4

- Role별로 실제로 다른 concern이 나타난다.
- 모든 Agent가 같은 문장을 반복하면 실패로 처리한다.
- 주요 dissent가 Decision Dossier에 보존된다.
- Challenger가 최소 하나의 검증 가능한 blind spot을 찾거나 `none`의 근거를 제시한다.
- 토론이 정해진 round 안에서 종료된다.

## Step 5. Decision Chair Agent

### 목표

집에서 사람을 대신해 실제 선택과 조건을 갖는 simulated decision을 생성한다.

### 입력

- Observable Case Packet
- Decision Dossier
- Decision Policy
- 승인 가능한 risk boundary

### 출력

- decision type
- selected/rejected option
- accepted assumption
- dissent preservation
- conditions
- guardrails
- rollback/review trigger
- required action
- verification plan
- residual risk
- risk acceptance rationale

### Decision policy 예

```text
IF evidence incomplete
AND option reversible
AND downside contained
AND deadline before evidence availability
THEN APPROVE_WITH_GUARDRAILS or RUN_REVERSIBLE_TRIAL

IF evidence incomplete
AND option irreversible
AND downside high
AND failure detected after freeze/silicon
THEN COLLECT_MINIMUM_EVIDENCE, DEFER_UNTIL_TRIGGER, or ESCALATE
```

Rule은 결론을 하드코딩하기보다 Chair가 빠뜨리면 안 되는 검토 항목과 금지 결정을 정의한다.

### Gate 5

- Chair가 단순 다수결을 사용하지 않는다.
- 반대 의견을 rationale에서 다룬다.
- 조건부 결정에는 guardrail과 trigger가 존재한다.
- 비가역적/high-downside option에 더 높은 판단 기준을 적용한다.
- 결정 결과에 `simulated_decision=true`가 유지된다.

## Step 6. Outcome Engine과 Decision Evaluation

### 목표

결정을 내리는 demo에서 끝나지 않고 그 결정이 개발 진행과 결과를 어떻게 바꾸는지 검증한다.

### 실행

```text
Simulated Decision
  → Action 생성
  → DevelopmentEvent 진행
  → WorkItem/Milestone 상태 변경
  → Future Evidence 공개
  → Guardrail/Trigger 평가
  → Rollback/Rework/Continue
  → Outcome 생성
  → Decision Evaluation
```

### 평가 지표

#### Process Quality

- fact grounding rate
- assumption labeling rate
- critical risk recall
- development dependency coverage
- uncertainty handling
- reversibility awareness
- guardrail completeness
- rollback trigger executability
- dissent handling
- deadline awareness

#### Outcome Quality

- milestone delay
- quality escape
- rework cost
- technical debt
- residual risk realization
- option preservation
- recovery success

#### Agent System Quality

- role differentiation
- unsupported claim rate
- decision stability across repeated runs
- excessive blocking rate
- excessive proceeding rate
- Challenger contribution
- Chair policy compliance

### Hindsight bias 방지

Evaluator는 hidden outcome을 본 뒤 “틀린 결과였으므로 나쁜 결정”이라고 단정하지 않는다. 당시 observable state에서 합리적으로 알 수 있었던 범위와 decision process를 먼저 평가한다.

### Gate 6

- 최소 5개 case가 Decision → Outcome까지 완료된다.
- Process/Outcome 점수가 분리된다.
- 동일 decision이라도 guardrail 유무에 따라 outcome이 달라지는 case가 있다.
- 나쁜 outcome이지만 process는 합리적인 case가 최소 1개 있다.
- 좋은 outcome이지만 process가 부실한 case가 최소 1개 있다.

## Step 7. 한국어 Decision Workspace

### 목표

복잡한 ontology와 Agent log를 숨기고 사용자가 의사결정만 빠르게 이해하게 한다.

### 화면 1. 결정 목록

표시:

- 결정 제목
- 결정 필요 시점
- 현재 개발 단계
- 현재 상태
- 권고 유형
- 남은 위험

### 화면 2. 결정 검토

표시 순서:

```text
1. 지금 무엇을 결정해야 하나
2. 왜 지금 결정해야 하나
3. 현재 개발은 어디까지 왔나
4. 어떤 선택지가 있나
5. Agent 의견은 어디서 일치하고 충돌하나
6. 권고는 무엇인가
7. 안전하게 진행하려면 무엇이 필요한가
8. 어떤 조건에서 중단·재검토해야 하나
9. 결정 후 실제 결과는 어땠나
```

### 화면 3. Fixture/평가 관리

개발자용으로 분리한다.

- observable/hidden fixture validation
- Agent execution log
- prompt/model version
- evaluation detail
- raw ID/JSON

### UI 규칙

- 모든 navigation과 일반 label은 한국어
- ISP, RTL, KPI 등 통용 약어만 유지
- Role별 card 나열 금지
- 의견은 `일치`, `충돌`, `확인 필요`로 통합
- graph와 raw ID는 상세 보기
- risk는 색상과 함께 원인·행동 표시
- 화면당 primary action 하나
- 핵심 요약 최대 5개

### Gate 7

- 사용자가 raw JSON 없이 결정 질문을 설명할 수 있다.
- 결정 기한과 다음 action을 찾을 수 있다.
- Role disagreement를 한 화면에서 확인할 수 있다.
- guardrail과 rollback trigger가 일반 문장으로 표시된다.
- 한국어 label이 없는 사용자용 field가 없다.

## 12. 주요 위험과 대응

|위험|대응|
|---|---|
|Agent가 fixture의 hidden truth를 추측해 맞히는 것을 실력으로 오인|source grounding과 process quality로 평가|

## 14. 첫 end-to-end vertical 목표

첫 coding milestone은 `I0` scaffold gate다. I0~I5를 통과한 뒤 첫 end-to-end vertical은 다음 명령 흐름으로 검증한다.

```text
validate-fixtures
  → show-development-state CASE-VR-001
  → run-role-review CASE-VR-001 architecture_system
  → run-role-review CASE-VR-001 verification_measurement
  → build-decision-dossier CASE-VR-001
  → run-decision-chair CASE-VR-001
  → apply-outcome CASE-VR-001
  → evaluate-decision CASE-VR-001
```

첫 완료 결과는 다음 질문에 답해야 한다.

1. 현재 개발은 어디까지 진행됐는가?
2. 무엇이 결정을 기다리고 있는가?
3. 각 Role은 무엇을 다르게 우려하는가?
4. Data가 부족한데 왜 진행 또는 연기하는가?
5. 어떤 guardrail과 trigger가 필요한가?
6. Decision Chair는 어떤 residual risk를 수용했는가?
7. 그 결정 이후 개발 상태와 결과는 어떻게 바뀌었는가?
8. 결과와 별개로 의사결정 과정은 합리적이었는가?

이 흐름이 완성되기 전에는 portfolio dashboard, weekly report, general chatbot, 실제 connector를 구현하지 않는다.
