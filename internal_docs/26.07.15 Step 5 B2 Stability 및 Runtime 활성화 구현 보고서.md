## 1. 결론

Step 4에서 선택한 B2 candidate를 동일 frozen release에서 반복 평가했다. Validation은
10/10, sealed-unseen은 6/6이 acceptable 및 policy compliant였고 runtime failure도 없었다.
따라서 새 durable dossier의 기본 topology를 B3에서 B2로 활성화했다.

```text
Step 4: release_b2
  -> Step 5 validation B2 x5 PASS
  -> Step 5 sealed-unseen B2 x3 PASS
  -> new durable dossier runtime = B2
```

이 결과는 집에서 만든 synthetic fixture에 대한 local release 근거다. 실제 SoC 과제의
의사결정 속도, 조언 품질 또는 조직적 가치는 사내 read-only pilot에서 별도로 측정해야
한다.

## 2. 구현한 계약

### 2.1 명시적 stability topology

`evaluation stability`는 이제 `--topology B1|B2|B3`를 반드시 받는다. 실행 topology는
summary, failure, environment와 report에 저장된다. 예상 semantic call은 topology별로
B1=1, B2=4, B3=8 calls/case-run을 사용한다.

이 변경으로 B3 hard-code 결과를 B2 근거로 오인할 수 없고, 실행 전 사용량도 선택한
topology에 맞게 계산된다.

### 2.2 Durable run과 migration

`ReviewRun`과 `observable.agent_runs`에 topology를 추가했다.

- 새 dossier: B1, B2 또는 B3 중 하나를 반드시 저장
- single-role run: topology null
- retry: 원 run의 topology 복사
- idempotency fingerprint: topology 포함
- legacy dossier: migration `0019_agent_run_topology`에서 B3로 backfill
- DB check constraint: run kind와 topology 조합 강제

기존 run은 과거 hard-coded B3 동작을 그대로 의미하고, 새 run만 승인된 B2 기본값을
사용한다. 따라서 migration이 과거 실행 의미를 소급 변경하지 않는다.

### 2.3 B2 실행과 의사결정 생성

B2는 routing된 네 Role Agent만 실행하고 Challenger, revision, provider Chair는 실행하지
않는다. 네 role case의 사전 예약은 8 logical calls/14,000 output tokens에서
4 logical calls/6,000 output tokens로 줄었다.

기존 simulated-decision API는 Chair 결과를 필수로 요구했기 때문에 B2에서 UI workflow가
중단될 수 있었다. 이를 topology-aware하게 변경했다.

|Topology|최종 simulated decision|
|---|---|
|B1/B2|Dossier를 입력으로 한 deterministic core decision|
|B3|검증된 provider Chair decision|

API 응답과 generated OpenAPI/TypeScript contract에도 run topology를 노출한다.

- B2 기본 실행에는 Challenger/Chair/revision이 없음
- topology가 enqueue, retry와 idempotency에 포함됨

- stability artifact에 B2와 partition이 표시됨
- B2 dossier에서 simulated decision API가 정상 완료됨
- 명시적 B3 compatibility path와 crash checkpoint 복구가 유지됨

## 5. 남은 경계와 다음 판단

- B2는 local runtime default지만 사람의 승인 권한을 대체하지 않는다.
- Codex CLI 결과는 Responses API의 USD 비용·latency gate를 증명하지 않는다.
- 4개 fresh synthetic case는 통계적 일반화나 실제 비즈니스 가치를 증명하지 않는다.
- Jira, Confluence, 사내 데이터, 인증, ACL 상속과 write-back은 여전히 범위 밖이다.
- 사내 전환 시에는 별도 domain reviewer가 만든 fresh set과 human approval을 사용해야 한다.
- 다음 구현 Step은 사용자 지시 전 시작하지 않는다.
