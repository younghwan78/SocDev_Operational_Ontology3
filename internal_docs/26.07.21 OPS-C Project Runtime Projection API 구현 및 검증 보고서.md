# OPS-C Project Runtime Projection API 구현 및 검증 보고서

> 상태: 구현 완료, OPS-C Gate PASS
> 일자: 2026-07-21
> 범위: local synthetic Project runtime, deterministic projection, read-only API
> 다음 단계: OPS-D Project Portfolio/Situation UX

## 1. 결론

OPS-C는 OPS-B의 `development-project.v1` fixture를 durable runtime aggregate로 승격하고,
사용자가 Project 전체 상황과 Risk의 근거·영향·Decision 연결을 조회할 수 있는 Backend 계약을
완성했다.

현재 Project API는 실제 실행 가능하지만 Frontend는 아직 이를 사용하지 않는다. UI에서 전체
상황을 보여주는 작업은 OPS-D다. Agent도 ProjectAttention, RiskLevel 또는 Project truth를
결정하지 않는다.

## 2. Runtime과 persistence

`ProjectRepository`는 `StoredProject(project, aggregate_version, fixture_hash,
contract_version)`를 저장한다. In-memory와 PostgreSQL adapter는 동일한 optimistic version 규칙을
사용한다.

PostgreSQL migration `0020_development_projects`는 다음을 별도 aggregate로 저장한다.

- project identity, lifecycle와 current Step
- `development-project.v1` 전체 JSONB payload
- `fixture_version`, `aggregate_version`
- raw fixture SHA-256와 contract version

기존 `observable.decision_cases` table과 `observable-case.v1` payload는 변경하지 않았다. Project
fixture는 `soc-ot fixtures import-project --project-id PROJECT-U` 명령으로 검증 후 import한다.

## 3. Deterministic policy

### 3.1 Project attention

`project-attention.v1`의 우선순위는 다음과 같다.

```text
BLOCKED → AT_RISK → WATCH → ON_TRACK
```

- 실제 `BLOCKED` WorkItem이 있으면 `BLOCKED`
- active `CRITICAL/HIGH` Risk 또는 `AT_RISK` Milestone이 있으면 `AT_RISK`
- late Evidence나 그보다 낮은 active Risk가 있으면 `WATCH`
- 위 조건이 없으면 `ON_TRACK`

Projection은 항상 `attention_reasons[].code`, 한국어 요약과 `source_refs`를 반환한다. 현재
fixture에서 PROJECT-V/W는 blocker 때문에 `BLOCKED`, PROJECT-U는 high Risk와 Field Fix Gate
때문에 `AT_RISK`다.

### 3.2 Risk level과 ordering

`project-risk-order.v1`은 숫자 score를 만들지 않는다. 다음 raw ordinal과 상태를 순서대로
비교한다.

```text
derived RiskLevel
  → RiskStatus
  → urgency
  → downside
  → reversibility
  → blast radius
  → nearest affected milestone
  → risk_id tie-break
```

- `REALIZED`는 `CRITICAL`
- severe downside와 immediate/irreversible 조합은 `CRITICAL`
- severe, immediate 또는 cross-project 조건은 `HIGH`
- material 또는 before-milestone 조건은 `MEDIUM`
- closed 또는 limited 조건은 `LOW`

모든 Risk는 `ranking_reasons`, provenance `source_refs`, impact IDs, Decision/Action IDs와 부족한
verification Evidence를 함께 반환한다. Role Agent의 가설은 이 policy 입력을 직접 변경할 수 없다.

## 4. Read-only API

|Resource|응답 계약|질문|
|---|---|---|
|`GET /api/v1/projects`|`project-list-item.v1[]`|어느 Project를 먼저 봐야 하는가|
|`GET /api/v1/projects/{id}/situation`|`project-situation.v1`|현재 Issue/Risk/blocker/evidence/milestone은 무엇인가|
|`GET /api/v1/projects/{id}/risks`|`project-risk-summary.v1[]`|Risk 우선순위와 이유는 무엇인가|
|`GET /api/v1/projects/{id}/risks/{risk_id}`|`project-risk-detail.v1`|Risk가 어디서 왔고 무엇에 영향을 주며 어떤 Decision/Action으로 이어지는가|
|`GET /api/v1/projects/{id}/timeline`|`project-timeline.v1`|어떤 Event가 현재 상태를 만들었는가|

Risk detail은 source Issue/Event/Evidence, cross-project source, WorkItem/Milestone impact,
Decision href, treatment Action과 rollback condition을 구분해 제공한다.

## 5. Historical boundary

Situation, Risk list/detail과 Timeline은 같은 `reconstruct_project_fixture_at_step` 결과를 사용한다.

- 선택 Step 이후 Event는 반환하지 않는다.
- 이후 관측되는 Issue와 식별되는 Risk는 반환하지 않는다.
- Evidence가 도착하기 전에는 `source_ref`를 숨긴다.
- Risk의 과거 status와 부족한 verification Evidence를 해당 Step 기준으로 재계산한다.
- 이후 열린 Decision과 treatment Action은 반환하지 않는다.

잘못된 Step은 `PROJECT_STEP_OUT_OF_RANGE`, 존재하지 않는 Project/Risk는
`PROJECT_NOT_FOUND`/`PROJECT_RISK_NOT_FOUND`로 안정적으로 실패한다.

## 6. DecisionCase compatibility

기존 12개 DecisionCase payload에 required `project_id`를 추가하지 않았다. 그 변경은
`observable-case.v1`을 깨므로 새 major와 migration 없이는 허용하지 않는다.

OPS-C에서는 `development-project.v1.decision_case_refs`가 existing case ID를 검증하고, Risk
detail이 `/decisions/{case_id}` 링크를 반환하는 one-way compatibility bridge를 사용한다. OPS-D/E
사용성에서 reverse lookup이 실제로 필요하다고 확인될 때 optional compatible index 또는 새 major를
별도로 결정한다.

## 7. 검증 결과

|검사|결과|
|---|---|
|OPS-C focused non-PostgreSQL|7 passed|
|전체 non-PostgreSQL Backend|152 passed / 11 deselected|
|전체 PostgreSQL marker (격리 DB)|PASS, 11 passed / 152 deselected|
|빈 DB, 0001, legacy upgrade/downgrade migration|PASS|
|JSON Schema/OpenAPI/TypeScript generation|PASS|
|Frontend typecheck/lint/unit/build|PASS, unit 12 passed|
|Replay smoke|PASS, Project query 후 기존 Decision→Outcome→Evaluation 완료|

공유 local DB에서 smoke 직후 전체 PostgreSQL marker를 실행하면 smoke가 남긴 최신 simulated
decision과 기존 I6 test decision이 달라 1건이 `DECISION_MISMATCH`로 실패했다. 사용자 local
상태를 삭제하지 않고 새 임시 DB에서 schema/import를 다시 구성해 실행한 결과 11건이 모두
통과했다. OPS-C regression은 아니지만 기존 PostgreSQL test가 공유 DB 상태에 민감하다는 test
isolation debt는 남아 있다.

## 8. 보류 범위

OPS-C는 화면, Project mutation command, Agent 자동판정, Jira/Confluence, 인증과 write-back을
추가하지 않았다. OPS-D는 지금 생성한 consumer-shaped API만 사용해 Portfolio → Situation의
점진적 정보 공개와 30초 overall status/top-risk/source task를 구현한다.
