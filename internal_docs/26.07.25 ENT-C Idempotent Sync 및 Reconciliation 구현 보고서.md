# ENT-C Idempotent Sync 및 Reconciliation 구현 보고서

> 작성일: 2026-07-25  
> 범위: ENT-C fixture-only deterministic synchronization  
> 판정: **ENT-C PASS, NEXT ENT-D**

## 1. 이번 단계가 해결한 문제

ENT-B는 source record 한 묶음을 후보로 mapping할 수 있었지만 실행 도중 중단되거나 동일 export를
다시 읽는 상황의 상태를 소유하지 않았다. 따라서 다음 질문에 실행 가능한 답이 없었다.

- 어떤 page까지 안전하게 처리했는가?
- 동일 source version을 다시 받으면 후보 revision이 증가하는가?
- 동일 version의 내용이 바뀌면 어떤 상태로 격리하는가?
- 일시 실패 후 몇 번, 어느 간격으로 다시 시도하는가?
- 삭제 또는 접근 제한 뒤 늦게 도착한 active copy가 내용을 되살리는가?
- 한 번에 실행한 결과와 중단 후 재개한 결과가 같은가?

ENT-C는 이 문제만 해결했다. 실제 connector, persistence, canonical import와 사람 resolution은
추가하지 않았다.

## 2. 승인한 경계

ADR-0014가 다음 계약을 승인한다.

```text
enterprise-sync-checkpoint.v1
enterprise-sync-result.v1
enterprise-sync-fixture-corpus.v1
```

Checkpoint는 다음 page index/token, 마지막 확정 cursor, stable identity별 reconciliation state,
record audit와 retry audit를 포함한다. Page 전체 처리가 끝난 뒤에만 다음 page로 이동한다.

```text
EnterpriseSyncMode        = FULL | INCREMENTAL
EnterpriseSyncStatus      = COMPLETED | PAUSED | FAILED
EnterpriseSyncDisposition = APPLIED | NO_CHANGE | QUARANTINED | REJECTED
```

`APPLIED`는 ENT-B candidate state가 checkpoint에 반영됐다는 의미다. canonical Project import,
사람 승인 또는 domain Event 생성 권한이 아니다.

## 3. 구현 구조

|구성|역할|
|---|---|
|`enterprise_sync.py`|strict 계약과 persistence-independent reconciliation 함수|
|`sync-pages.v1.yaml`|4 page, 10 record synthetic 실행 corpus|
|`test_ent_c_enterprise_sync.py`|idempotency, resume, retry, delete/restricted, late/stale 검증|
|ADR-0014|sync policy와 ENT-D/C0 경계|
|generated schemas|외부 adapter가 따라야 할 checkpoint/result/corpus 구조|

Engine은 HTTP, FastAPI, SQLAlchemy, OpenAI, vendor SDK를 import하지 않는다. Retry는 실제로
sleep하지 않고 예정 backoff를 audit data로 기록한다. 이후 adapter가 clock과 transport를
소유할 수 있지만 결과 정책은 바꿀 수 없다.

## 4. Fixture 시나리오

|Page|입력|검증 목적|
|---:|---|---|
|0|Project v1, WorkItem v1|초기 candidate state와 revision 1|
|1|WorkItem v1 exact duplicate, v2 update|duplicate no-op, update 1회 반영, 2회 transient retry|
|2|48시간 이상 늦은 page, WorkItem delete v3, 역순 도착 Event 2건|`LATE_ARRIVAL`, metadata-only tombstone, effective-time Event ordering|
|3|delete보다 오래된 active WorkItem, page restriction|stale active 격리, access reduction 적용|

Source system 이름, tenant, URL과 ACL reference는 모두 synthetic이다. 실제 회사 field ID,
principal, credential 또는 vendor product 이름은 fixture에 없다. Manifest가 registry, dirty
corpus와 새 sync corpus의 SHA-256을 고정한다.

## 5. Reconciliation 규칙

Stable identity는 ENT-A의
`(source_system, source_tenant, source_object_type, external_id)`를 그대로 사용한다.

1. 같은 identity/version/hash는 `NO_CHANGE`다.
2. 같은 identity/version에 다른 hash가 오면 `QUARANTINED`다.
3. version만 바뀌고 content hash가 같으면 source metadata만 전진하고 mapping revision은
   증가하지 않는다.
4. changed active record가 최신 `source_updated_at`보다 오래되면 `STALE_SOURCE_UPDATE`로
   격리한다.
5. accepted changed record만 mapping revision을 정확히 한 번 증가시킨다.
6. `DELETED`와 `RESTRICTED`는 payload 없이 적용한다.
7. tombstone/access reduction 뒤 늦게 도착한 오래된 active record는 이전 내용을 복원하지
   못한다.
8. business-effective time과 capture time을 합치지 않으며 late evidence에는 ENT-B
   `LATE_ARRIVAL` reason을 남긴다.

여기서 `mapping_revision`은 checkpoint 내부 candidate 변화 횟수다. PostgreSQL Project
aggregate version이나 canonical Event 수가 아니다.

## 6. 중단·재개와 retry

Fixture policy는 page당 최대 3회 시도와 `[1, 2]`초 backoff를 고정한다. Page 1이 처음 두 번
실패하면 다음 audit가 남고 세 번째 시도에 성공한다.

```text
attempt 1 failed → retry after 1 second
attempt 2 failed → retry after 2 seconds
attempt 3 succeeds
```

세 번 모두 실패하면 status는 `FAILED`, `next_page_index`와 `next_page_token`은 실패한 page를
가리킨다. 호출자가 같은 checkpoint로 다시 시작할 수 있다. Engine은 wall clock을 기다리지 않아
test가 빠르고 결정적이다.

두 page 뒤 `PAUSED`한 incremental 실행을 같은 checkpoint로 재개한 결과는 one-shot incremental
checkpoint와 완전히 같다. 완료 checkpoint를 다시 실행하면 처리 page/record가 0이며 audit와
revision도 그대로다.

최종 repository Gate는 ruff, mypy 55개 source file, non-PostgreSQL 206개 test, plan consistency,
architecture/hidden boundary, secret scan, generated contract/OpenAPI/Frontend client freshness와
`git diff --check`까지 모두 통과했다. ENT-C는 API, PostgreSQL, Frontend 또는 browser runtime을
변경하지 않아 해당 stage-specific Gate는 요구하지 않는다.

## 8. 아직 하지 않은 것

- 실제 Jira/Confluence 또는 다른 vendor API
- 실제 cursor 형식, rate limit과 network clock
- database checkpoint와 process-crash transaction
- canonical Project/Event import
- dry-run CLI, canonical diff와 durable quarantine/resolution
- 실제 principal, group, inherited ACL과 retention
- credential, authentication, write-back

따라서 현재 결과로 “사내 data 연결 준비 완료” 또는 “운영 동기화 완료”를 주장할 수 없다.

## 9. 다음 고정 단계

ENT-D는 이 checkpoint와 ENT-B mapping result를 읽어 다음을 구현한다.

- source validation 및 no-write dry-run CLI
- 생성/변경/삭제 예정 canonical diff
- unmapped/dangling/time/ACL quality report
- quarantine와 사람이 작성하는 resolution file 계약
- freshness, coverage, reject/quarantine summary

ENT-D에서도 실제 company data, vendor API, credential, authentication, real ACL과 write-back은
허용하지 않는다.
