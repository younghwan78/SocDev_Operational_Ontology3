
## 이 과제의 목적 recap

- 지금 회사의 문제 중 하나를 다음으로 정의. 단순히 “DB와 dashboard가 많다”가 아니라, **SoC 개발 조직의 의사결정 단위가 데이터 시스템에 반영되어 있지 않은 상태** 
- 단순히 DB, dashboard를 통합한다고 AX가 완성되며 개발 효율이 높아지지 않음.
- 그래서 AX를 위해서는  LLM/Agent를 붙이는 것보다 먼저, “SoC 개발에서 반복되는 의사결정·이슈 해결·품질 판단”을 데이터 객체와 관계로 재구성해야 하는 것을 먼저 목표로함

큰 명제는 다음과 같음
```text
분산된 SoC 개발 데이터를 하나의 DB로 모으는 것이 아니라, 개발 TAT와 품질을 직접 개선하는 ‘SoC Development Operating System’을 만든다.
```

```text
데이터를 조사해서 만드는 방식이 아니라, 먼저 가상의 개발 세계를 만들고, 그 안에서 의사결정 cycle을 돌려보며, 필요한 실제 데이터를 역으로 정의한다
```

## Plantir 밴치 마킹한 운영 온톨로지

- Palantir Foundry/온톨로지 모델에서 중요한 점은 기존 데이터를 다 없애고 중앙 DB 하나로 통합하는 게 아닙니다. Palantir Ontology는 기존 dataset, virtual table, model 위에 올라가는 **조직의 operational layer**이고, 실제 세계의 자산·제품·주문 같은 객체와 연결됩니다. 또한 객체, 속성, 링크뿐 아니라 action type, function 같은 실행 요소를 포함해 의사결정과 업무 실행까지 연결하는 구조
- AI가 단순히 문서 검색을 하는 것이 아니라, 온톨로지와 개발 도구체인 위에서 production-ready workflow, agent, function을 만들게 하는 방향
- oC 조직에서 이걸 그대로 해석하면 **LLM 기반 질의응답 시스템**이 아니라, **SoC 개발 lifecycle의 디지털 트윈 + 의사결정 자동화 계층**이 되어야 함

## 현재 문제의 본질

```text
“데이터 파편화”보다 “맥락 파편화”가 더 크다
반도체 개발 조직의 fragmentation은 산업적으로도 흔한 문제입니다. Siemens의 반도체 PLM 자료에서도 반도체 기업의 60% 이상이 제품 데이터와 프로세스 관리를 위해 6개 이상의 시스템을 사용하고, 59%는 제품 개발 복잡도가 증가하고 있다고 제시
```

결국 AX의 걸림돌은 “AI가 똑똑하지 않아서”가 아니라, **AI가 읽을 수 있는 형태로 개발 세계가 모델링되어 있지 않다**는 점

## SoC 조직용 Palantir식 목표 모델

- SoC Development Ontology + Operational Cockpit


SoC 개발 온톨로지는 대략 아래 객체들을 중심으로 설계할 수 있습니다.

|객체|설명|
|---|---|
|**Project**|SoC 과제, 세대, milestone, target product|
|**Product / Customer Segment**|Android mobile, automotive, XR, edge AI, IoT 등|
|**Scenario**|Video recording, camera preview, gaming, modem+camera concurrency 등|
|**Variant**|FHD30, UHD60, 8K30, HDR, multi-camera, low-power mode 등|
|**IP / Subsystem**|ISP, GPU, NPU, CPU, DDR, Display, Codec, Sensor hub 등|
|**Requirement**|성능, 전력, bandwidth, latency, thermal, Android compatibility|
|**KPI**|power, BW, latency, FPS, memory, coverage, fail rate, defect density|
|**Issue / Risk**|architecture risk, verification bug, customer issue, silicon bug|
|**Evidence**|test result, log, waveform, Confluence page, JIRA, commit, report|
|**Decision**|spec 변경, workaround 승인, IP 변경, schedule trade-off|
|**Action**|assign, review, re-test, regression trigger, report generation|

이 구조의 중요한 점은 “데이터 저장”이 아니라 **관계**입니다.

```text
Requirement
  → affects Scenario
  → uses IP
  → measured by KPI
  → verified by Test
  → failed by Issue
  → explained by Evidence
  → resolved by Decision
  → changed by Commit / Spec update
```

Palantir 온톨로지도 기존 data source를 object, property, link로 mapping하고, 그 위에서 workflow와 application을 만들 수 있는 foundation으로 설명됩니다. ([Palantir](https://palantir.com/docs/foundry/ontology/overview/ "Overview • Ontology • Palantir")) SoC 버전에서는 이 object/link가 곧 개발 조직의 “공통 언어”가 됩니다.
