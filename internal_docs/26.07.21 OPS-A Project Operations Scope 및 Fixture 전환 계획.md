# OPS-A Project Operations Scope 및 Fixture 전환 계획

> 문서 상태: OPS-A 구현 보고서
> 날짜: 2026-07-21
> 결정: ADR-0010 Accepted
> 다음 단계: OPS-B Project 중심 fixture

## 1. 결과

OPS-A는 기존 Decision Workspace를 폐기하거나 UI를 먼저 확장하지 않고, 그 상위에
Project Operations와 Risk Provenance를 추가하는 범위를 확정했다.

```text
Project Portfolio
  → Project Situation
  → Issue/Risk Detail
  → existing Decision Workspace
  → Action / Outcome / Evaluation
```

이번 단계에서는 domain code, database, API, Frontend와 기존 fixture를 변경하지 않았다.
`development-project.v1`과 Project resource는 예약 계약이며 OPS-B/OPS-C Gate 전에는
구현 완료로 간주하지 않는다.

## 2. 확정한 의미 경계

- Blocker는 현재 WorkItem을 실제로 막는 관측 상태다.
- Issue는 이미 발생하거나 관측된 문제다.
- Risk는 Issue, Event, dependency 또는 Evidence gap이 미래 손실로 이어질 가능성이다.
- Evidence 부족만으로 모든 결정을 block하지 않는다.
- DecisionCase는 Risk treatment를 위한 bounded question이다.
- Agent는 Risk hypothesis와 mitigation을 제안하지만 Project truth를 직접 변경하지 않는다.
- Backend projection이 attention, ordering, causal path와 이유를 계산한다.
- Frontend는 Project/Risk 상태를 합성하지 않는다.

상세 결정은 `docs/decisions/ADR-0010-project-operations-and-risk-provenance.md`가 소유한다.

## 3. `world.yaml` event catalog receipt

참조 파일:

```text
E:\57_Claude_SoC_DigitalTwin\OperationalOntology\data\world.yaml
SHA-256: 108E5BFC2311B90E0264ED470D081920F4F414CBE3072F663DEC47ABEBA72759
```

이 hash는 어떤 참고본을 보았는지 기록하기 위한 것이며, OPS-B 입력 pin이나 반영 의무가
아니다. 참고 범위도 top-level `events` 항목으로 제한한다. `projects`, `roles`, `risk`와
`activity_log` 구조는 새 fixture 요구사항으로 사용하지 않는다.

### 3.1 Event가 제공하는 lifecycle 문맥

|Project archetype|Stage|주요 근거|대표 판단|
|---|---|---|---|
|U|Mass Production/Field|field-measured, customer-confirmed|현재 과제에서 즉시 완화할지 차기로 넘길지|
|V|HW Rev closure/pre-Si|pre-silicon, U lesson|commitment window 안에 HW 변경을 넣을지|
|W|Spec/Architecture|model, lesson, 초기 고객 요구|area/perf/power/business trade-off를 spec에 반영할지|

`events`에는 이 세 lifecycle 문맥을 포함한 24개 후보가 있다. OPS-B는 이를 전부 반영하지
않고 UX 검증에 서로 다른 답을 제공하는 event만 선택한다. Project를 세 개 두는 판단도
Portfolio/Situation UX에 필요한 비교 축에서 나온 것이며 `world.yaml`의 U/V/W를 복제하기
위한 것이 아니다.

### 3.2 Event 선택 기준

선택한 event는 다음 중 하나 이상의 새로운 UX 상태를 만들어야 한다.

- field에서 관측된 Issue와 즉시 mitigation
- pre-silicon 불확실성과 닫히는 HW commitment window
- model/lesson 기반의 Spec trade-off
- open, late 또는 received evidence에 따른 판단 변화
- Risk의 해결, 악화 또는 realization
- dependency, resource conflict, rework 또는 cross-project lesson

같은 화면 답과 같은 risk path만 반복하는 event는 제외한다. Event 수는 Gate가 아니며,
가장 작은 fixture set으로 Project overview, Risk origin과 historical delta를 검증한다.

### 3.3 Cross-project propagation

일부 event에는 다른 Project로의 propagation 후보가 있다. 대표 패턴은 다음과 같다.

```text
U field issue
  → U의 즉시 SW mitigation 또는 KPI trade-off
  → V의 HW/DVFS 개선 Risk와 commitment window

U product lesson
  → W의 차세대 spec/architecture option
```

이 패턴이 Project 간 lesson/영향 UX 검증에 필요할 때만 채택한다. 채택한 경우 동일 event를
여러 fixture에 복제하지 않고 source Event와 target Project의 Risk/WorkItem/Decision
reference를 명시해 lineage를 유지한다.

### 3.4 Evidence와 불완전성

유용한 패턴은 다음과 같다.

- evidence basis: `field-measured`, `customer-confirmed`, `pre-silicon`, `lesson`, `model`
- confidence cap: field/customer는 high 가능, pre-silicon은 medium, lesson/model은 low
- evidence request: system, owner, requested/due/received Step
- request status: open 또는 connected
- 늦게 도착하거나 끝까지 미측정인 evidence
- 동일한 evidence gap이 power, resource, schedule, business Risk를 다르게 낮춤

이 구조는 현재의 `available_at_step`을 유지하면서 request lifecycle과 freshness를 보강하는
근거로 사용한다. `connected`를 Evidence fact와 혼동하지 않고 received Step 이후에만 eligible로
만든다.

### 3.5 Option과 trade-off

Event 후보에는 option과 다음 정보가 포함될 수 있다.

- benefit
- risk
- cost
- confidence
- schedule impact
- Project/axis별 effect
- 비용과 위험을 수용하는 Project/Role

OPS-B는 numeric axis delta와 recommended flag를 정답처럼 복사하지 않는다. canonical
Alternative의 reversible/switching cost/claim reference와 expected transition으로 다시
표현하고, recommendation은 검증 가능한 policy/Agent run 이후에만 생성한다.

## 4. 가져올 것과 제외할 것

|항목|OPS-B 처리|
|---|---|
|lifecycle이 다른 event 문맥|UX 비교에 필요하면 local synthetic context로 재작성|
|situation/event 후보|중복되지 않는 UX 상태를 만드는 항목만 선택|
|cross-project propagation|Project 간 영향 UX가 필요할 때만 채택; source/target link 필수|
|evidence request lifecycle|Risk 근거와 판단 변화를 보여주는 경우 채택|
|근거별 confidence 차이|기존 epistemic contract와 정합화해 선택 채택|
|option의 cost/schedule/effect|선택지 비교 UX에 필요하고 근거가 있는 범위만 adaptation|
|`projects`, `roles`, `risk`, `activity_log`|참조 범위에서 제외|
|0~100 risk axis와 impact×likelihood score|제외|
|dice, exec jitter|제외|
|긴 Role LLM 문장과 `reasoning_src`|제외|
|외부 파일 runtime import|제외|

## 5. OPS-B fixture 목표

### Project P-U: Field/Mass Production

- 실제 측정으로 현재 Issue가 명확하다.
- 해결은 SW workaround, KPI/상품성 trade-off, 차기 HW 개선 사이에서 선택한다.
- field evidence는 강하지만 경쟁사 benchmark나 세부 breakdown은 부족할 수 있다.
- 일부 Risk가 V 또는 W로 전파된다.

### Project P-V: HW Closure

- pre-silicon evidence는 방향성만 제공한다.
- commitment window 이후에는 HW 변경 비용이 급증한다.
- U lesson을 반영하되 잘못된 수정과 일정 지연을 함께 다룬다.
- evidence가 부족해도 guarded/reversible option을 선택할 수 있는 case를 포함한다.

### Project P-W: Spec/Architecture

- model과 lesson 중심이라 confidence가 낮다.
- area/perf/power/business가 충돌한다.
- 고객 요구와 model accuracy가 늦게 도착한다.
- spec freeze 전에 지금 결정할 것과 다음 Gate로 미룰 것을 분리한다.

## 7. OPS-B 작업 순서

1. `development-project.v1` Pydantic authoring schema와 JSON Schema를 추가한다.
2. 세 Project의 identity, lifecycle, Track와 Milestone을 먼저 작성한다.
3. UX coverage matrix를 먼저 만들고 필요한 `events` 후보만 Issue/Risk/Decision 질문으로
   분류한다.
4. 선택한 event idea를 typed DevelopmentEvent before/after chain으로 새로 작성한다.
5. evidence request/arrival와 confidence boundary를 추가한다.
6. UX coverage에 필요하면 cross-project propagation link를 추가한다.
7. positive, invalid-reference, discontinuous-history와 future-leakage test를 추가한다.
8. fixture hash manifest와 adaptation receipt를 고정한다.
9. 기존 12 DecisionCase와 UX-H hash-pinned baseline 회귀를 실행한다.

## 8. OPS-B 검증 Gate

- Project별 lifecycle, evidence strength와 decision posture가 구별된다.
- Project overview, Risk origin, impact path, historical delta와 Decision 진입 task를 fixture로
  답할 수 있다.
- 선택한 event가 서로 다른 UX 상태를 만들며 중복 event가 없다.
- open/late/received evidence와 blocker/rework/resource conflict 중 Risk provenance와 상태
  변화를 설명하는 데 필요한 대표 사례가 존재한다.
- Issue → Risk → Milestone/Decision provenance가 끊기지 않는다.
- cross-project propagation을 채택했다면 source/target lineage가 끊기지 않는다.
- historical Step에서 이후 evidence, decision과 outcome이 노출되지 않는다.
- hidden fixture와 observable boundary가 유지된다.
- 기존 regression과 UX-H baseline이 의도 없이 변경되지 않는다.

OPS-B Gate 전에는 OPS-C domain/API, OPS-D UI를 시작하지 않는다.
