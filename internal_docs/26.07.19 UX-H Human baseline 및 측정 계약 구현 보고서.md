# UX-H Human baseline 및 측정 계약 구현 보고서

> 일자: 2026-07-19
> 범위: post-I7 UX-H, fixture-only human-study preparation
> 구현 판정: **session-ready**
> Human Gate: **NOT READY — 실제 완료 관측 0건**
> 2026-07-23 후속 결정: human observation은 0/5에서 보류. UX-I는 engineering-proxy로만 진행하며 human/value claim은 차단

## 1. 결론

UX-H의 소프트웨어와 연구 계약은 구현했다. 같은 `CASE-VR-001` observable fixture를 출발점으로
사용하는 Jira/Confluence형 baseline pack, canonical 8개와 Development Twin 5개 질문을 고정한
protocol, task timing·답변·오동작·상세 열기·복구·reviewer response를 기록하는 session 계약,
condition별 지표를 계산하는 summary 계약과 CLI가 동작한다.

그러나 실제 참가자 답변이나 시간을 생성하지 않았다. 현재 dry-run은 의도대로
`human_gate_status=not_ready`, `directional_target_status=not_evaluable`,
`interpretation=no_business_claim`을 반환한다. 따라서 이 보고서는 UX-H 실행 준비 완료 증거이지
human usability, 의사결정 속도 개선 또는 business value의 통과 증거가 아니다.

## 2. 구현 경계

UX-H는 제품 runtime이 아니라 별도 authoring/evaluation surface로 구현했다.

|포함|제외|
|---|---|
|synthetic observable fixture 기반 baseline|실제 Jira/Confluence connector|
|frozen human-task protocol|회사 data, 계정, 인증|
|익명 participant code와 session artifact|실명, 이메일, 사번|
|측정·검증·요약 CLI|제품 API telemetry endpoint|
|directional target 판정|자동 human 승인 또는 business pass|
|builder/proxy/domain 분리|simulated Chair를 실제 승인자로 사용|

Frontend에 자동 tracking을 먼저 넣지 않은 이유는 protocol이 실제 session에서 검증되기 전에
제품 telemetry schema와 UI 행동을 고착시키지 않기 위해서다. UX-H는 YAML session artifact로
측정 의미를 먼저 고정한다. 이후 자동 수집이 필요하면 같은 계약을 유지한 별도 단계로 추가한다.

## 3. 공정한 baseline

`fixtures/usability/CASE-VR-001.baseline-pack.v1.yaml`은 내용을 복사한 별도 truth가 아니다.
다음 세 surface가 observable fixture의 JSON pointer만 참조한다.

|Surface|형태|Source|
|---|---|---|
|검토 배경 문서|Confluence형 local fixture|제목, 현재 Step, 상태, 결정 질문, deadline|
|개발 진행 현황|Jira형 local fixture|track, WorkItem, milestone, action, event|
|측정·선택지 근거|evidence note|evidence, claim, uncertainty, alternative, role/type|

검증 시 observable model을 canonical JSON으로 정규화한 SHA-256
`dcceadd509d5cb9deddc757a68f3dedf105fdb8953581291eb3238849a55ec25`와 비교한다. fixture가
바뀌거나 selector가 사라지면 실행을 중단한다. baseline에는 hidden case, expected result,
Dossier, simulated decision, Outcome, Role review를 넣지 않는다.

이 구조는 두 condition이 같은 공개 source에서 시작했다는 점을 보장한다. 제품이 Agent 조언이나
projection으로 추가 가치를 만드는지는 human task 결과에서 별도로 확인한다. baseline에서 source로
답할 수 없는 질문은 추정하지 않고 “정보 없음/아직 확정되지 않음”으로 구분하는 것이 정답 rubric의
일부다.

## 4. Frozen protocol

`fixtures/usability/UX-H-20260719.protocol.yaml`은 결과를 보기 전에 다음을 고정한다.

- condition: `baseline`, `product`
- task: canonical 8개 + Development Twin 5개, 총 13개
- 독립 participant: `proxy`, `domain`; `builder`는 공학 dry-run으로만 집계
- 최소 표본: condition별 독립 완료 session 5개
- 제외 사유: session 미완료, 환경 장애, 다른 condition 결과 사전 노출, protocol 위반
- 질문 정확도·boundary 정확도·safeguard completeness 목표: 1.0
- Product/Baseline median elapsed-time 비율 목표: 0.8 이하
- 해석: 작은 표본은 `directional_only`

시간 목표는 baseline 값을 보고 임의로 바꾸지 않도록 “제품 median이 baseline의 80% 이하”라는
계산 규칙으로 고정했다. 표본이 작기 때문에 충족하더라도 통계적 일반화나 business proof로
승격하지 않는다.

## 5. Session과 measurement event 계약

`usability-session.v1`은 다음을 기록한다.

|영역|필드·event|검증|
|---|---|---|
|신원 경계|session ID, 익명 participant code, builder/proxy/domain|builder는 독립 표본에서 제외|
|시간|`task_started`, `task_ended`|timezone 필수, 종료가 시작보다 앞설 수 없음|
|답변|answer, `answer_submitted`, pass/fail|13개 frozen task 순서와 일치|
|오동작|`wrong_primary_action`|condition별 count 집계|
|정보 탐색|`detail_opened`|raw detail 의존성 확인|
|복구|`recovery_used`|오류 복구 비용 확인|
|검토|reviewer note, `reviewer_response_recorded`|완료 task마다 필수|
|경계 이해|observed/expected/unconfirmed|Q10/Q12/Q13 frozen rubric과 비교|
|안전성|safeguard completeness 0~1|condition 평균과 목표 비교|

Draft template은 빈 event와 `not_reviewed` result만 만든다. `status: completed` session은 모든
task의 시작·종료·답변·reviewer response와 실제 답변/note가 없으면 거부된다. 코드가 human
결과를 채우거나 정답을 가장하는 경로는 없다.

## 6. Summary와 과장 방지

`usability-study-summary.v1`은 condition별로 다음을 계산한다.

- 완료/독립/builder session 수
- 전체 session median elapsed seconds
- 질문 정확도와 expected/observed/unconfirmed boundary 정확도
- safeguard completeness
- wrong primary action, detail open, recovery count
- Product/Baseline median time ratio와 고정 목표 충족 여부

표본 수가 condition별 5개보다 적으면 모든 target check는 `null`이고 상태는
`not_ready/not_evaluable/no_business_claim`이다. 최소 표본을 충족해도 자동 결과는
`ready_for_directional_review`뿐이며 `passed` 상태는 schema에 존재하지 않는다. 실제 사람과
책임자가 해석해야 하며 회사 승인 권한과 연결되지 않는다.

## 7. CLI 사용

Material 검증:

```powershell
uv run soc-ot usability validate
```

Baseline session 준비:

```powershell
uv run soc-ot usability prepare-session `
  --condition baseline `
  --participant-kind proxy `
  --participant-code P001 `
  --session-id UXH-BASE-P001
```

Product condition은 `--condition product`로 준비한다. baseline condition에만 source selector로
렌더링한 `baseline-pack.md`가 생성된다. 실제 session 뒤 `session.yaml`을 기록하고 검증한다.

```powershell
uv run soc-ot usability validate-session `
  --session output/usability/UXH-BASE-P001/session.yaml `
  --require-complete

uv run soc-ot usability summarize `
  --sessions-root output/usability/UX-H-20260719 `
  --output output/usability/UX-H-20260719/summary.json
```

요약은 `summary.json`과 같은 디렉터리의 `report.md`를 함께 만든다. `output/`은 git ignored이며
실제 session artifact에는 회사 data나 개인 식별자를 넣지 않는다.
