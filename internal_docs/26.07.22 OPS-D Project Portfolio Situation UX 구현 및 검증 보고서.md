# OPS-D Project Portfolio/Situation UX 구현 및 검증 보고서

> 상태: 구현 완료, OPS-D local proxy Gate PASS
> 일자: 2026-07-22
> 범위: local synthetic Project Portfolio와 Situation read-only UX
> 다음 단계: OPS-E Risk Detail과 기존 Decision Workspace 연결

## 1. 결론

OPS-D는 OPS-C의 consumer-shaped Project API를 실제 제품 진입 흐름에 연결했다. 사용자는 이제
결정 목록부터 열지 않고 `/projects`에서 과제 전체의 주의 상태와 최상위 Risk를 먼저 보고,
`/projects/:projectId`에서 그 Risk가 어떤 Issue, Evidence와 Event에서 나왔으며 어떤 작업과
기준점에 영향을 주는지 확인할 수 있다.

Frontend는 Risk level, ProjectAttention, 우선순위나 provenance를 다시 계산하지 않는다.
Backend가 반환한 순서와 reason/source를 보존하고, 같은 historical Step에서 이미 보이는 객체의
제목을 연결해 읽기 쉽게 표현하는 역할만 한다.

## 2. 사용자 흐름

```text
/projects
  ProjectAttention + 왜 먼저 + 최상위 Risk + 가까운 기준점
    → /projects/:projectId
      전체 상황 + 가장 먼저 볼 Risk
      → source Issue / Evidence / Event
      → affected WorkItem / Milestone
      → blocker / Track / Gate / Evidence gap / recent Event
```

루트 `/`는 이제 `/projects`로 이동한다. 기존 `/decisions`와 Decision Workspace는 그대로 유지하고,
Portfolio 상단의 `결정 검토 목록`으로 접근할 수 있다. 특정 Risk에서 Decision으로 이동하는 기능은
OPS-E 범위이므로 이번 단계에서는 만들지 않았다.

## 3. Portfolio 정보 구조

Portfolio는 `/api/v1/projects`의 Backend 순서를 그대로 사용한다. 각 과제 카드에는 다음만 우선
노출한다.

- `ProjectAttention`의 한국어 상태와 lifecycle stage
- `attention_reasons[0].summary_ko`인 `왜 먼저`
- Backend 1순위 Risk의 statement, level, treatment status
- source와 affected work의 개수
- 열린 Issue, 활성 Risk, 막힌 작업과 가장 가까운 milestone

합산 score, 색상 기반의 숨은 등급 또는 Frontend 정렬은 없다. 색은 이미 반환된 canonical state를
보조하며 텍스트 label을 항상 함께 제공한다.

## 4. Situation과 Risk provenance

Situation은 30초 task proxy에 필요한 순서로 정보를 배치했다.

1. 지금 가장 먼저 확인할 Backend reason
2. 1순위 Risk statement와 ranking reason
3. source reference를 현재 Step에서 볼 수 있는 제목으로 연결
4. affected WorkItem과 Milestone
5. 막힌 작업, Track 진행, Gate/Checkpoint
6. 관측 Issue와 확보·지연·요청 Evidence
7. 최근 Project Event

source presentation join은 같은 response의 Issue/Evidence와 같은 Step의 Timeline Event만 사용한다.
현재 response에서 해석할 수 없는 cross-project source는 `다른 과제의 학습`으로 표시하고 canonical
reference ID를 남긴다. 이를 이용해 새 inference를 만들거나 Risk truth를 바꾸지 않는다.

## 5. Historical boundary와 복구

관찰 Step은 URL의 `at_step`에 저장된다. Situation과 Timeline query key 및 요청은 동일한 Step을
사용한다.

- 과거 화면은 `과거 상태`와 future-information exclusion 문구를 표시한다.
- 선택 Step 이후 Event, Evidence와 Risk state는 OPS-C API 경계에서 제거된다.
- `PROJECT_STEP_OUT_OF_RANGE`는 선택한 Step을 그리지 않고 `현재 시점 보기`를 제공한다.
- Timeline만 실패하면 현재 Situation 검토를 유지하고 이력 재시도만 제공한다.
- browser 검토에서 Step 20의 `READY` WorkItem이 current Track의 `BLOCKED` fallback을 물려받는
  future-state leak을 발견했다. Track status가 historical WorkItem state의 READY/PLANNED를 먼저
  사용하도록 고치고 회귀 테스트를 추가했다.

## 6. 반응형·접근성

- 390px에서는 카드와 Risk/source/Track grid가 한 열로 재배치된다.
- desktop에서는 전체 상황, count, source와 impact를 같은 시야에서 비교한다.
- 모든 navigation은 `Link`, 재시도와 Step 복구는 `button`, 관찰 시점은 label이 있는 `select`다.
- skip link와 단일 main landmark, heading hierarchy, visible focus와 reduced motion을 유지한다.
- source ID는 `translate="no"`로 표시해 자동 번역에 의한 추적성 손상을 막는다.
- 빈 Project, 빈 Risk, 빈 Event와 partial Timeline failure가 각각 설명된다.

## 8. Gate 해석과 보류 범위

OPS-D가 통과했다는 뜻은 local agent-substitute가 Portfolio에서 overall status와 top Risk를 찾고,
Situation에서 source와 affected work를 추적할 수 있으며 responsive/accessibility 자동 검사가
통과했다는 뜻이다. 실제 사람이 30초 안에 과제를 완료했다거나 의사결정 속도가 개선됐다는 뜻은
아니다.

다음 OPS-E에서만 Risk Detail route를 열고 source → inference/impact → treatment Decision/Action →
기존 Decision Workspace 흐름을 연결한다. Project mutation, 실제 승인, Agent-owned Project truth,
Jira/Confluence, 인증, write-back과 human observation은 계속 제외한다.
