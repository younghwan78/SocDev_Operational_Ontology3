
좋은 문제 정의입니다. 지금 상황은 단순히 “DB와 dashboard가 많다”가 아니라, **SoC 개발 조직의 의사결정 단위가 데이터 시스템에 반영되어 있지 않은 상태**로 보는 게 맞습니다. AX를 하려면 LLM/Agent를 붙이는 것보다 먼저, “SoC 개발에서 반복되는 의사결정·이슈 해결·품질 판단”을 데이터 객체와 관계로 재구성해야 합니다.

제가 보기엔 이 과제의 큰 명제는 이렇게 잡는 게 좋습니다.

> **분산된 SoC 개발 데이터를 하나의 DB로 모으는 것이 아니라, 개발 TAT와 품질을 직접 개선하는 ‘SoC Development Operating System’을 만든다.**

---

## 1. Palantir 벤치마킹의 핵심: 통합 DB가 아니라 “운영 온톨로지”

Palantir Foundry/온톨로지 모델에서 중요한 점은 기존 데이터를 다 없애고 중앙 DB 하나로 통합하는 게 아닙니다. Palantir Ontology는 기존 dataset, virtual table, model 위에 올라가는 **조직의 operational layer**이고, 실제 세계의 자산·제품·주문 같은 객체와 연결됩니다. 또한 객체, 속성, 링크뿐 아니라 action type, function 같은 실행 요소를 포함해 의사결정과 업무 실행까지 연결하는 구조입니다. ([Palantir](https://palantir.com/docs/foundry/ontology/overview/ "Overview • Ontology • Palantir"))

SoC 개발 부서에 적용하면 핵심은 다음입니다.

```text
기존 파편화 시스템
JIRA / Confluence / Git / Regression DB / Coverage DB / Power DB / Lab log / Dashboard / Excel
        ↓
SoC Development Ontology
Project / IP / Requirement / Scenario / Variant / Test / Issue / KPI / Evidence / Decision
        ↓
Operational Apps & AI Agents
Architecture Query / Issue RCA / Change Impact / Milestone Risk / Quality Cockpit
        ↓
Action & Feedback
Assign owner / create review item / update evidence / trigger regression / summarize decision
```

Palantir AIP도 “AI를 데이터와 운영에 연결해 operational process 자동화”하는 플랫폼으로 설명됩니다. 즉 AI가 단순히 문서 검색을 하는 것이 아니라, 온톨로지와 개발 도구체인 위에서 production-ready workflow, agent, function을 만들게 하는 방향입니다. ([Palantir](https://palantir.com/docs/foundry/aip/overview/ "Overview • AIP • Palantir"))

SoC 조직에서 이걸 그대로 해석하면 **LLM 기반 질의응답 시스템**이 아니라, **SoC 개발 lifecycle의 디지털 트윈 + 의사결정 자동화 계층**이 되어야 합니다.

## 2. 현재 문제의 본질: “데이터 파편화”보다 “맥락 파편화”가 더 크다

반도체 개발 조직의 fragmentation은 산업적으로도 흔한 문제입니다. Siemens의 반도체 PLM 자료에서도 반도체 기업의 60% 이상이 제품 데이터와 프로세스 관리를 위해 6개 이상의 시스템을 사용하고, 59%는 제품 개발 복잡도가 증가하고 있다고 제시합니다. 또한 fragmentation 감소, end-to-end digitalization, traceability 확보를 주요 가치로 설명합니다. ([Siemens](https://www.siemens.com/en-us/solutions/product-lifecycle-management-plm/semiconductors/ "Semiconductor PLM | Siemens"))

그런데 SoC 개발 부서에서는 단순 시스템 수보다 더 심각한 문제가 있습니다.

|파편화 유형|SoC 개발에서의 실제 모습|AX 관점 문제|
|---|---|---|
|**시스템 파편화**|JIRA, Confluence, Git, CI, regression, coverage, power dashboard, lab log가 따로 존재|Agent가 전체 상황을 못 봄|
|**식별자 파편화**|같은 IP가 문서마다 `ISP`, `IFE`, `Titan`, `CAM_IFE`처럼 다르게 불림|동일 객체 matching 실패|
|**시간축 파편화**|spec 변경, RTL 변경, SW workaround, bug close 시점이 서로 연결 안 됨|원인-결과 추적 불가|
|**조직 파편화**|architecture, design, verification, SW, system, PM이 각자 dashboard 보유|handoff 지연|
|**품질 근거 파편화**|“이 이슈가 해결됐다”는 결론은 있지만 test/evidence/log가 흩어짐|품질 판단 신뢰도 낮음|
|**의사결정 파편화**|왜 특정 IP spec이 바뀌었는지, 누가 승인했는지, 어떤 issue 때문인지 불명확|다음 과제 reuse 어려움|
|**시나리오 파편화**|Android camera/display/video use case별 workload, KPI, bottleneck 정보가 분산|architecture exploration 어려움|

결국 AX의 걸림돌은 “AI가 똑똑하지 않아서”가 아니라, **AI가 읽을 수 있는 형태로 개발 세계가 모델링되어 있지 않다**는 점입니다.

## 3. SoC 조직용 Palantir식 목표 모델

이 과제는 “SoC Data Lake”보다 **SoC Development Ontology + Operational Cockpit**으로 잡는 게 좋습니다.

### 핵심 객체

SoC 개발 온톨로지는 대략 아래 객체들을 중심으로 설계할 수 있습니다.

|객체|설명|
|---|---|
|**Project**|SoC 과제, 세대, milestone, target product|
|**Product / Customer Segment**|Android mobile, automotive, XR, edge AI, IoT 등|
|**Scenario**|Video recording, camera preview, gaming, modem+camera concurrency 등|
|**Variant**|FHD30, UHD60, 8K30, HDR, multi-camera, low-power mode 등|
|**IP / Subsystem**|ISP, GPU, NPU, CPU, DDR, Display, Codec, Sensor hub 등|
|**Requirement**|성능, 전력, bandwidth, latency, thermal, Android compatibility|
|**KPI**|power, BW, latency, FPS, memory, coverage, fail rate, defect density|
|**Issue / Risk**|architecture risk, verification bug, customer issue, silicon bug|
|**Evidence**|test result, log, waveform, Confluence page, JIRA, commit, report|
|**Decision**|spec 변경, workaround 승인, IP 변경, schedule trade-off|
|**Action**|assign, review, re-test, regression trigger, report generation|

이 구조의 중요한 점은 “데이터 저장”이 아니라 **관계**입니다.

```text
Requirement
  → affects Scenario
  → uses IP
  → measured by KPI
  → verified by Test
  → failed by Issue
  → explained by Evidence
  → resolved by Decision
  → changed by Commit / Spec update
```

Palantir 온톨로지도 기존 data source를 object, property, link로 mapping하고, 그 위에서 workflow와 application을 만들 수 있는 foundation으로 설명됩니다. ([Palantir](https://palantir.com/docs/foundry/ontology/overview/ "Overview • Ontology • Palantir")) SoC 버전에서는 이 object/link가 곧 개발 조직의 “공통 언어”가 됩니다.

## 4. 가장 먼저 해야 할 일: 파편화 수준을 계량화하는 진단 체계

지금은 “얼마나 파편화되어 있는지 모른다”가 가장 큰 문제라고 하셨는데, 이건 별도 phase로 분리해야 합니다.

### 4.1 SoC Data Fragmentation Assessment

각 조직/도메인별로 아래를 수집합니다.

|진단 항목|질문|
|---|---|
|Data Source|어떤 시스템/DB/dashboard/Excel/문서가 있는가?|
|Owner|누가 소유하고 누가 업데이트하는가?|
|Object|그 데이터가 어떤 개발 객체를 표현하는가? IP? Issue? KPI? Test? Scenario?|
|Freshness|얼마나 자주 갱신되는가? 수동인가 자동인가?|
|Trust Level|공식 source인가, 참고용인가, 개인 관리 자료인가?|
|Linkability|JIRA ID, IP name, project ID, variant ID 등으로 다른 데이터와 연결 가능한가?|
|Decision Use|실제 어떤 회의/리뷰/승인/디버깅에서 쓰이는가?|
|Pain Point|찾는 데 오래 걸리는가, 중복인가, 신뢰가 낮은가, owner가 불명확한가?|

### 4.2 Fragmentation Score

각 데이터 소스에 점수를 부여하면 top management 보고에도 좋습니다.

|지표|의미|
|---|---|
|**Findability Time**|원하는 정보를 찾는 데 걸리는 평균 시간|
|**Joinability Score**|다른 데이터와 key로 연결 가능한 정도|
|**Freshness Score**|최신 상태 유지 정도|
|**Trust Score**|공식성, 검증성, owner 명확성|
|**Reuse Score**|다음 과제/다른 팀에서 재사용 가능한 정도|
|**Decision Impact**|개발 TAT/품질 의사결정에 미치는 영향|
|**Automation Readiness**|API, schema, permission, metadata 보유 정도|

이걸 통해 “전체를 다 통합하자”가 아니라, **TAT와 품질에 영향이 큰 데이터부터 우선순위화**할 수 있습니다.

## 5. 개발 TAT 최적화 관점의 핵심 아이디어

### 아이디어 1. Architecture Decision Cockpit

목표는 architect가 과거 과제의 evidence를 빠르게 찾아 차기 SoC 의사결정을 단축하는 것입니다.

예시 질문:

```text
Q. Project A에서 4K60 video recording 관련 power issue는 몇 건이었고,
   어떤 IP에서 주로 발생했으며, 어떤 방식으로 해결했는가?

Q. 200MP sensor + 8K30 scenario를 넣으면
   ISP/DDR/thermal 관점에서 과거 어떤 bottleneck이 재발할 가능성이 높은가?

Q. Project B에서 camera preview latency가 늦어진 원인은
   HAL scheduling 문제였는가, ISP path 문제였는가, DDR contention 문제였는가?
```

필요 데이터:

```text
Scenario ↔ Variant ↔ IP ↔ KPI ↔ Issue ↔ Evidence ↔ Decision
```

효과:

|기존|개선|
|---|---|
|JIRA/Confluence/개인 기억 검색|ontology 기반 원인/결정/evidence 검색|
|회의 때마다 과거 사례 재조사|과거 issue pattern 자동 추천|
|architect 경험 의존|조직 지식 자산화|

---

### 아이디어 2. Change Impact Agent

SoC 개발 TAT를 늘리는 큰 원인은 “변경 영향 분석”입니다. 하나의 spec 변경이 architecture, RTL, firmware, HAL, Android framework, verification, power model, customer scenario까지 번집니다.

예시:

```text
Sensor interface bit width 변경
  → CSI bandwidth 변경
  → CSID/IFE input rate 변경
  → DDR traffic 변경
  → thermal/power KPI 변경
  → camera HAL buffer count 변경 가능
  → regression test set 변경
  → Android CTS/VTS 영향 가능
```

Agent가 할 일:

```text
1. 변경된 Requirement/IP/Interface 식별
2. 연결된 Scenario/Variant/KPI/Test/Issue 조회
3. 영향 가능성이 큰 영역 rank
4. 필요한 review owner 추천
5. regression/test checklist 생성
6. 관련 과거 issue/evidence 첨부
```

이건 단순 chatbot보다 훨씬 가치가 큽니다. Palantir AIP의 방향도 AI를 조직 데이터와 운영 프로세스에 연결해 자동화 workflow를 만드는 것이며, 보안·감사·lineage 같은 governance를 포함한다고 설명됩니다. ([Palantir](https://palantir.com/docs/foundry/aip/overview/ "Overview • AIP • Palantir"))

---

### 아이디어 3. Milestone Risk Early Warning

각 milestone마다 “정상인지 아닌지”를 판단하는 기준이 팀마다 다릅니다. 이걸 통합 risk model로 만들 수 있습니다.

입력 데이터:

```text
open issue trend
critical/blocker issue age
regression pass rate
coverage closure
PPA margin
scenario KPI violation
commit churn
spec churn
waiver count
customer issue count
owner response latency
```

출력:

```text
Project / Subsystem / Scenario별 risk heatmap
Risk reason summary
Next action recommendation
과거 유사 milestone 비교
```

예시 결과:

```text
UHD60 Video Recording: Risk High
- DDR BW margin이 Project A 동일 시점 대비 18% 낮음
- Camera HAL buffer issue가 3주 이상 open
- ISP power KPI waiver가 증가 추세
- 과거 Project B에서 동일 패턴이 EVT 직전 silicon debug 지연으로 연결됨
```

---

### 아이디어 4. Issue RCA Evidence Graph

SoC 개발 품질을 높이려면 issue close 자체보다 **왜 닫혔는지**, **진짜 검증됐는지**, **다음 과제에서 재발 가능성이 있는지**가 중요합니다.

Issue RCA graph는 다음 관계를 만듭니다.

```text
Issue
  → symptom
  → affected scenario
  → suspected IP
  → root cause
  → fix type
  → workaround
  → verifying test
  → evidence
  → residual risk
  → reusable lesson
```

예시 분류:

|RCA 유형|예시|
|---|---|
|Architecture miss|초기 bandwidth budget 누락|
|Spec ambiguity|HAL/firmware 책임 경계 불명확|
|Verification gap|특정 concurrency scenario test 없음|
|Power model error|pre-silicon power estimate 부정확|
|SW workaround dependency|Android framework/HAL workaround로 품질 보전|
|Customer scenario mismatch|실제 OEM use case와 내부 test scenario 차이|

이걸 쌓으면 다음 과제에서 **“비슷한 문제가 또 생길 확률”**을 예측할 수 있습니다.

---

### 아이디어 5. Scenario-Based Quality Cockpit

Android mobile SoC에서는 feature 단위보다 scenario 단위가 더 중요합니다.

예:

```text
Camera Preview
Video Recording
Video Call
Gaming + Thermal
Display + Camera concurrency
AI camera enhancement
Low-light capture
HDR video
8K recording
Multi-camera switching
```

각 scenario별로 다음을 연결합니다.

```text
Scenario
  → SW path
  → HW pipeline
  → IP dependency
  → bandwidth path
  → power domain
  → test coverage
  → known issues
  → customer relevance
  → KPI status
```

이렇게 하면 품질 보고가 “bug count”가 아니라 **사용자 경험/고객 use case 중심 품질**로 바뀝니다.

([McKinsey & Company](https://www.mckinsey.com/capabilities/quantumblack/our-insights/the-next-innovation-revolution-powered-by-ai "How AI is driving R&D productivity | McKinsey"))

## 7. Mobile SoC 중심이지만 확장 가능한 구조

지금은 Android향 mobile SoC가 가장 큰 고객이라고 했으니, 초기 온톨로지는 mobile scenario 중심으로 잡는 게 맞습니다. 다만 향후 확장을 고려하면 **product family / workload / constraint** 축을 분리해야 합니다.

```text
Product Family
  - Android Mobile
  - Automotive
  - XR / AR
  - Edge AI
  - IoT / Wearable
  - Robotics

Workload
  - Camera
  - Display
  - Video
  - AI / NPU
  - Graphics
  - Modem concurrency
  - Sensor fusion

Constraint
  - Power
  - Thermal
  - Latency
  - Safety
  - Reliability
  - Security
  - Real-time
  - Cost / Area
```

이렇게 설계하면 `Scenario DB`가 mobile camera/video 전용으로 끝나지 않고, 장기적으로는 **SoC platform intelligence layer**가 됩니다.

예를 들어 같은 `Video Recording` scenario라도 product family에 따라 우선순위가 달라집니다.

|Product|중요한 KPI|
|---|---|
|Android Mobile|power, thermal, latency, camera quality, Android compatibility|
|Automotive|reliability, safety, long-term support, thermal robustness|
|XR|motion-to-photon latency, sustained power, sensor fusion|
|Edge AI|NPU throughput, memory bandwidth, energy per inference|
|IoT|standby power, wake-up latency, BOM cost|

|Verification/System Engineer|test/evidence/quality semantics 정의|
|PM/Program Analyst|milestone, TAT, risk KPI 정의|

이 팀은 전사 플랫폼팀처럼 멀리 떨어져 있으면 실패할 가능성이 큽니다. Palantir식 벤치마킹의 핵심은 현업 문제 안에 들어가서 “작동하는 use case”를 빠르게 만드는 것입니다. 따라서 초기에는 대규모 플랫폼 구축보다 **고통이 큰 2~3개 문제를 실제 데이터로 해결**하는 게 좋습니다.

## 10. TAT/품질 KPI를 이렇게 잡으면 좋습니다

AX 효과를 주장하려면 “업무 편의성”보다 **측정 가능한 개발 성과**로 연결해야 합니다.

### TAT KPI

|KPI|설명|
|---|---|
|Issue RCA lead time|issue open → root cause 후보 도출까지 시간|
|Evidence collection time|회의/보고용 근거 수집 시간|
|Change impact analysis time|spec/IP 변경 영향 분석 시간|
|Review preparation time|architecture/system review 준비 시간|
|Regression triage time|fail 분석/owner assign 시간|
|Milestone risk detection lead time|risk를 milestone 전에 얼마나 빨리 발견했는가|

### 품질 KPI

|KPI|설명|
|---|---|
|Escaped issue rate|milestone 이후 발견된 critical issue|
|Reopened issue rate|close 후 재오픈 비율|
|Requirement-test coverage gap|요구사항 대비 test/evidence 누락률|
|Scenario KPI violation count|scenario별 power/BW/latency 위반|
|Repeated issue pattern|과거 과제와 동일 유형 재발 건수|
|Decision traceability|주요 결정의 evidence 연결률|

핵심은 “AI를 도입했다”가 아니라, **RCA 시간이 줄었는가, review 준비 시간이 줄었는가, 반복 issue가 줄었는가, milestone risk를 빨리 봤는가**입니다.

## 12. 가장 중요한 설계 원칙

이 과제는 다음 원칙을 지켜야 합니다.

1. **DB-first가 아니라 decision-first**  
    어떤 데이터를 모을지가 아니라, 어떤 의사결정을 빠르게 할지를 먼저 정해야 합니다.
    
2. **Dashboard-first가 아니라 ontology-first**  
    dashboard는 계속 늘어나도 파편화가 해결되지 않습니다. 객체와 관계가 먼저입니다.
    
3. **문서 검색이 아니라 evidence graph**  
    Confluence/JIRA 검색을 잘하는 것만으로는 부족합니다. issue, root cause, fix, test, decision이 연결되어야 합니다.
    
4. **AI 답변보다 confidence가 중요**  
    SoC 개발에서는 그럴듯한 답보다 근거, 최신성, owner, 검증 여부가 중요합니다.
    
5. **Mobile scenario로 시작하되 product-family 축을 열어둔다**  
    Android mobile 중심으로 시작하되 automotive/XR/edge AI로 확장 가능한 schema가 필요합니다.

## 결론

현재 문제를 한 문장으로 정의하면 이렇습니다.

> SoC 개발 조직의 데이터는 많이 존재하지만, 개발 TAT와 품질 의사결정에 필요한 형태로 연결되어 있지 않다.

따라서 목표는 “전사 통합 DB”가 아니라 다음이어야 합니다.

> **SoC 개발 lifecycle 전반의 scenario, IP, KPI, issue, evidence, decision을 연결하는 operational ontology를 만들고, 그 위에서 architecture query, RCA, change impact, milestone risk, quality cockpit을 실행한다.**

이 방향이면 기존에 추진 중인 **SoC Scenario DB / Architecture Query / Evidence Dashboard / Exploration Workbench**가 단순 도구가 아니라, Palantir식으로 말하면 SoC 개발 조직의 **운영 온톨로지 기반 AX 플랫폼**으로 발전할 수 있습니다.


-----------

네. **SoC 전체가 아니라 Multimedia IP로 scope을 좁혀 PoC를 한다면**, 가장 좋은 방식은 IP별 DB를 만드는 것이 아니라 **Multimedia Scenario 중심으로 IP·KPI·Issue·Evidence를 연결하는 vertical slice**를 만드는 것입니다.

즉 시작점은 이렇게 잡는 게 좋습니다.

```text
대상 도메인: Multimedia SoC
대상 IP: ISP, DPU, Codec, Audio
초기 Scenario: Camera / Video / Display / Audio가 얽히는 대표 use case
목표: 개발 TAT 단축 + 품질 리스크 조기 탐지
```

---

# 1. PoC의 핵심 방향

처음부터 “ISP DB, DPU DB, Codec DB, Audio DB”를 각각 만들면 안 됩니다. 그렇게 하면 기존 파편화가 다른 형태로 반복됩니다.

대신 아래처럼 가야 합니다.

```text
Scenario 중심
  → 관련 IP 연결
  → 관련 KPI 연결
  → 관련 Issue 연결
  → 관련 Evidence 연결
  → 관련 Decision 연결
```

예를 들어 `4K60 Video Recording`이라는 scenario를 기준으로 보면:

```text
4K60 Video Recording
  ├─ ISP: sensor input, CSID, IFE, IPE, noise reduction, HDR path
  ├─ Codec: encoder load, compression, latency, bit rate
  ├─ DPU: preview/display path, composition, refresh rate
  ├─ Audio: audio capture sync, A/V sync, low-latency path
  ├─ DDR/NoC: bandwidth, QoS, contention
  ├─ Power/Thermal: sustained recording power, thermal throttling
  ├─ SW: HAL, framework, buffer queue, scheduler
  └─ Evidence: JIRA, Confluence, regression result, power report, log
```

이렇게 하면 PoC가 단순 dashboard가 아니라 **scenario 기반 SoC 개발 intelligence layer**가 됩니다.

# 2. 추천 PoC Scope

## 2.1 처음부터 모든 multimedia scenario를 넣지 말고 3개만 선택

가장 좋은 초기 PoC scenario는 아래 3개입니다.

|우선순위|Scenario|이유|
|---|---|---|
|1|**Video Recording**|ISP + Codec + DDR + Power + Thermal이 모두 얽힘|
|2|**Camera Preview / Capture**|ISP + DPU + HAL + Latency 이슈가 잘 드러남|
|3|**Video Playback / Streaming**|Codec + DPU + Audio + DDR + Power가 연결됨|

초기에는 Audio를 독립 도메인으로 깊게 파기보다, video playback/recording에서 **A/V sync, latency, low-power audio path** 정도로 연결하는 게 좋습니다.

---

## 2.2 IP Scope은 얕고 넓게, Scenario는 깊게

초기 PoC에서는 IP 전체 내부 구조를 완벽하게 모델링하지 말고, 각 IP가 scenario에서 어떤 역할을 하는지만 잡습니다.

|IP|PoC에서 잡아야 할 최소 정보|
|---|---|
|ISP|input resolution, fps, bit depth, sensor mode, internal path, output format, bottleneck point|
|DPU|layer composition, refresh rate, panel path, bandwidth, display latency|
|Codec|encode/decode mode, resolution, fps, bitrate, memory traffic, latency|
|Audio|capture/playback path, sampling rate, latency, A/V sync, low-power mode|
|DDR/NoC|bandwidth, QoS, contention, peak/sustained traffic|
|CPU/DSP/FW|control path, firmware load, HAL interaction, scheduling risk|

중요한 건 IP block의 세부 spec을 모두 넣는 것이 아니라, **개발 의사결정에 필요한 연결 정보**를 먼저 넣는 것입니다.

# Phase 0. 문제/질문 정의

가장 먼저 해야 하는 것은 DB 설계가 아니라, **PoC가 반드시 답해야 하는 질문**을 정하는 것입니다.

초기 PoC는 아래 질문 5개에 답할 수 있어야 합니다.

```text
Q1. 특정 multimedia scenario에서 어떤 IP들이 관여하는가?

Q2. 과거 project에서 해당 scenario 관련 issue는 어떤 IP에 집중되었는가?

Q5. 현재 milestone에서 risk가 높은 multimedia scenario는 무엇이고 근거는 무엇인가?
```

# Phase 1. 데이터 파편화 진단

이 단계의 목적은 “어디에 어떤 데이터가 있는지”를 보이게 만드는 것입니다.

대상 데이터는 아래 정도입니다.

|데이터 종류|예시|
|---|---|
|Scenario 정의|YAML, Excel, Confluence, architecture 문서|
|IP 정보|ISP/DPU/Codec/Audio block spec, interface, capability|
|KPI 정보|power, bandwidth, latency, fps, thermal, memory|
|Issue 정보|JIRA, bug tracker, customer issue|
|Evidence|log, waveform, regression result, power report, Confluence page|
|Decision|architecture review 결과, waiver, workaround, spec 변경|
|Test 정보|regression suite, coverage, CTS/VTS, scenario test|

이때 중요한 것은 데이터를 바로 통합하는 게 아니라, 각 데이터의 상태를 평가하는 것입니다.

|평가 항목|질문|
|---|---|
|Owner|누가 관리하는가?|
|Freshness|최신 상태인가?|
|Trust|공식 source인가?|
|Linkability|Project/IP/Scenario/Issue ID로 연결 가능한가?|
|Automation|API나 export가 가능한가?|
|Decision Impact|개발 TAT/품질 판단에 중요한가?|

이 단계의 산출물은 **Data Fragmentation Map**입니다.

예:

```text
JIRA
  - Issue 정보는 풍부함
  - IP name 표기가 불안정함
  - Scenario와 직접 연결 안 됨
  - Root cause/decision은 comment에 숨어 있음

Confluence
  - Architecture decision 문서 존재
  - 검색은 가능하지만 구조화 약함
  - Evidence link가 누락되는 경우 많음

Power Dashboard
  - KPI 수치는 있음
  - Issue/Scenario/Variant와 연결 약함

Regression DB
  - fail/pass 결과는 있음
  - 실제 customer scenario와 연결 약함
```

# Phase 4. 실제 데이터 일부 연결

그다음 실제 데이터 source를 하나씩 붙입니다.

우선순위는 아래가 좋습니다.

|우선순위|Data Source|이유|
|---|---|---|
|1|Scenario YAML / architecture 문서|ontology의 기준점|
|2|JIRA issue|TAT/품질 개선 효과가 가장 잘 보임|

```text

KPI report → CSV import
Regression → fixture 또는 summary import
```

중요한 것은 ingestion 자동화보다 **연결 모델이 맞는지**입니다.

특정 scenario를 선택하면 관련 IP, KPI, issue, evidence가 한 화면에 보여야 합니다.

## Use Case 2. Issue RCA Graph

이슈 하나를 선택하면 root cause와 evidence 관계가 보여야 합니다.

```text
Issue: UHD60 recording thermal throttling

Symptom:
- 10분 이상 recording 시 fps drop

Affected Scenario:
- 4K60 Video Recording
- HDR Video Recording

Affected IP:
- ISP
- DDR
- Codec
```

## 결론

Multimedia IP로 scope을 좁힌 PoC는 다음 순서가 가장 좋습니다.

```text
1. Video Recording 중심 vertical slice 선정
2. ISP/Codec/DPU/Audio/DDR를 scenario 관점으로 연결
3. Scenario - IP - KPI - Issue - Evidence - Decision ontology 정의
4. Fixture 기반으로 먼저 schema/API/UI 검증
5. JIRA/Confluence/KPI 일부 실제 데이터 연결
6. Scenario Cockpit, RCA Graph, Change Impact, Risk Heatmap 구현
7. TAT/품질 KPI로 효과 측정
8. Camera Preview, Playback, Gaming, AI Camera, XR/Automotive로 확장
```

핵심은 **IP별 data mart가 아니라 scenario 중심 operational ontology**입니다.  
이렇게 해야 Palantir식 접근처럼 파편화된 데이터를 “검색 가능한 자료”가 아니라 **개발 의사결정을 빠르게 하는 실행 가능한 지식 체계**로 바꿀 수 있습니다.


-----------

완전히 동의합니다. 오히려 이 경우에는 **Phase 0을 사내 전수조사로 시작하면 안 됩니다.**  
말씀하신 것처럼 “무엇을 물어봐야 하는지”를 알고 있다면 이미 의사결정 체계가 어느 정도 정리된 상태일 가능성이 큽니다.

그래서 접근을 바꾸는 게 좋습니다.

> **Phase 0 = 조사 단계가 아니라, 풍부한 fixture data로 ‘가상의 SoC 개발 운영 모델’을 먼저 만들고, 그것을 기준으로 사내 현실과 차이를 검증하는 단계**

즉, 처음부터 조직별 DB/dashboard를 하나하나 조사하지 않고, **“이런 시스템이 있다면 개발 TAT와 품질 판단이 이렇게 좋아질 수 있다”**를 fixture 기반으로 먼저 보여주는 방식입니다.

---

# 1. 방향 전환: Survey-first가 아니라 Fixture-first

기존 접근이 이랬다면:

```text
사내 데이터 전수조사
  → 각 조직 dashboard 파악
  → 데이터 source 정리
  → ontology 정의
  → PoC 구현
```

이건 너무 무겁습니다.

대신 이렇게 가는 게 좋습니다.

```text
풍부한 fixture data 생성
  → 가상의 Multimedia SoC 개발 상황 구성
  → Scenario / IP / KPI / Issue / Evidence / Decision 관계 구현
  → 동작하는 PoC 화면 제작
  → 사내 이해관계자에게 보여주고 검증
  → 실제 데이터 source를 필요한 것부터 연결
```

핵심은 **조사를 먼저 하는 게 아니라, 가설을 먼저 만들고 검증하는 것**입니다.

---

# 2. Fixture data의 역할

fixture data는 단순 테스트 데이터가 아닙니다. 이 PoC에서는 fixture가 사실상 **업무 모델의 초안**입니다.

fixture data가 해야 하는 역할은 5가지입니다.

|역할|설명|
|---|---|
|**업무 가설 표현**|Multimedia SoC 개발에서 어떤 객체와 관계가 중요한지 표현|
|**PoC 데모 기반**|실제 데이터 없이도 dashboard, graph, query를 보여줌|
|**사내 피드백 유도**|“우리도 이런 issue가 있다/없다”를 끌어냄|
|**데이터 조사 범위 축소**|어떤 실제 source를 붙여야 하는지 명확해짐|
|**확장성 검증**|ISP에서 DPU/Codec/Audio로 확장 가능한지 확인|

이 방식이 좋은 이유는, 사람들은 추상적인 질문에는 잘 답하지 못하지만 **구체적인 화면과 예시를 보면 바로 반응**하기 때문입니다.

예를 들어 이렇게 묻는 것보다:

```text
“현재 multimedia issue data가 어디에 있나요?”
```

이렇게 보여주는 게 훨씬 낫습니다.

```text
“4K60 Video Recording에서 ISP M2M path 때문에 DDR BW가 증가하고,
Codec encoder power spike와 겹쳐 thermal risk가 high로 뜨는 모델을 만들었습니다.
이런 식의 issue/evidence 연결이 실제 개발에서도 의미가 있나요?”
```

그러면 담당자들이 바로 말할 수 있습니다.

```text
“맞다. 그런데 우리 쪽은 DDR보다는 NoC QoS가 더 중요하다.”
“Codec power issue는 JIRA보다 weekly report에 더 잘 정리되어 있다.”
“Audio는 recording보다 video call에서 더 중요하다.”
“DPU는 preview path보다 external display scenario에서 더 문제가 많다.”
```

이렇게 fixture가 **질문을 만드는 도구**가 됩니다.

반드시 포함해야 하는 요소는 아래입니다.

## 5.1 IP alias

같은 IP가 문서마다 다르게 불리는 상황을 넣습니다.

```yaml
ip_aliases:
  ISP:
    - ISP
    - IFE
    - IPE
    - VFE
    - Titan
    - Camera HW
  DPU:
    - DPU
    - Display
    - MDSS
    - MDP
  Codec:
    - Codec
    - VPU
    - Venus
    - Video Codec

    - Audio

```

이걸 넣어야 실제 문제인 **명칭 불일치**를 검증할 수 있습니다.

---

## 5.2 Scenario별 issue

예를 들어 `4K60 Video Recording`에는 이런 issue를 넣습니다.

```text
Issue 1.
- 증상: 장시간 recording 시 fps drop
- 관련 IP: ISP, DDR, Codec
- KPI: thermal, power, DDR BW
- 원인: ISP internal M2M path 증가 + Codec encoder load 증가
- Evidence: power report, DDR log, JIRA discussion
- Decision: sensor binning option 추가, thermal policy 변경

Issue 2.
- 증상: HDR video recording에서 latency 증가
- 관련 IP: ISP, Camera HAL
- KPI: latency, frame drop
- 원인: multi-frame processing path로 buffer queue 증가
- Evidence: HAL log, architecture review
- Decision: buffer count tuning, HDR mode constraint 추가

Issue 3.
- 증상: preview와 recording 동시 동작 시 display underrun
- 관련 IP: DPU, DDR, NoC
- KPI: display stability, BW
- 원인: DPU composition BW와 camera output BW contention
- Evidence: display log, NoC counter
- Decision: QoS setting update
```

이렇게 issue가 여러 IP와 KPI에 걸쳐 있어야 합니다.

---

## 5.3 Evidence 품질 차이

실제 회사 데이터는 evidence 품질이 일정하지 않습니다. fixture에도 그걸 반영해야 합니다.

```text
Evidence Level 0: synthetic assumption
Evidence Level 1: 담당자 comment 수준
Evidence Level 2: JIRA link 존재
Evidence Level 3: report 또는 log 존재
Evidence Level 4: regression/test로 검증됨
Evidence Level 5: owner 승인된 공식 decision
```

PoC에서 중요한 것은 “답을 생성하는 것”보다 **이 답이 얼마나 믿을 만한지 보여주는 것**입니다.

예:

```text
UHD60 thermal issue root cause confidence: Medium

근거:
- JIRA comment 존재
- power report 존재
- 하지만 regression 재검증 evidence 없음
```

이런 식으로 나와야 실제 개발자가 신뢰합니다.

---

## 5.4 일부러 불완전한 데이터 넣기

fixture가 너무 깨끗하면 의미가 없습니다. 실제와 비슷하게 아래도 넣어야 합니다.

```text
- IP 이름이 서로 다름
- issue에는 scenario tag가 없음
- Confluence 문서는 오래됨
- JIRA는 close됐지만 evidence link가 없음
- power report 수치와 dashboard 수치가 다름
- 같은 issue가 ISP team과 Codec team에서 중복 등록됨
- root cause가 comment에는 있지만 structured field에는 없음
- workaround는 있는데 decision 기록이 없음
```

이걸 넣어야 PoC가 단순 dashboard가 아니라 **fragmentation을 다루는 시스템**임을 보여줄 수 있습니다.

# 7. Fixture에 반드시 들어가야 하는 대표 issue archetype

Multimedia SoC PoC라면 아래 issue archetype을 넣는 것이 좋습니다.

## ISP 계열

```text
- 고해상도 sensor input으로 CSID/IFE bandwidth 증가
- HDR path에서 multi-frame latency 증가
- ISP internal M2M path 증가로 DDR traffic 증가
- low-light processing으로 power 증가
- sensor mode 변경으로 HAL buffer mismatch 발생
- tuning 변경 후 image quality regression 발생
```

## DPU 계열

```text
- camera preview + UI composition에서 display underrun
- UHD playback 중 layer composition bandwidth 증가
- high refresh rate panel에서 DPU power 증가
- external display 연결 시 memory path 증가
- DPU QoS 설정 부족으로 frame drop 발생
```

## Codec 계열

```text
- 4K60 encode에서 encoder power spike
- 8K30 encode에서 bitrate/latency constraint 위반
- HDR playback에서 decode bandwidth 증가
- thermal throttling 후 frame drop
- firmware scheduling 문제로 encode latency 증가
```

## Audio 계열

```text
- video recording 중 A/V sync drift
- video call에서 audio latency 증가
- low-power audio path 전환 실패
- Bluetooth audio path와 video playback sync 문제
- thermal 상태에서 audio underrun 발생
```

## DDR/NoC 계열

```text
- ISP + Codec + DPU 동시 동작으로 DDR peak BW 초과
- NoC QoS priority 부족
- memory compression 미적용으로 BW 증가
- concurrent scenario에서 latency spike
- power saving mode 진입 후 resume latency 증가
```

이 archetype들이 들어가면 실제 팀이 봤을 때 “우리도 이런 문제 있다/없다”를 빠르게 말할 수 있습니다.

# 8. Fixture 기반으로 먼저 만들 화면

처음부터 실제 연동보다 아래 화면을 먼저 만드는 게 좋습니다.

## 8.1 Scenario Cockpit

```text
Scenario: 4K60 Video Recording

Risk: High

관련 IP:
- ISP: High
- Codec: Medium
- DPU: Low
- Audio: Low
- DDR/NoC: High

주요 KPI:
- Power: Warning
- DDR BW: Critical
- Latency: Normal
- Thermal: Critical
- FPS stability: Warning

주요 Issue:
- ISP M2M path로 DDR BW 증가
- Codec encoder power spike
- Thermal throttling 후 fps drop

Evidence:
- Power report
- JIRA issue
- Architecture review
- Regression result
```

---

## 8.2 Evidence Graph

```text
Issue
  → Symptom
  → Scenario
  → Affected IP
  → KPI violation
  → Root cause
  → Evidence
  → Decision
  → Test verification
```

이 화면은 특히 중요합니다.  
단순히 “issue가 몇 개다”가 아니라, **왜 이 issue가 품질 risk인지**를 설명해야 합니다.

---

## 8.3 Change Impact View

예:

```text
변경: ISP 12bit HDR path 추가

영향 가능성:
- Scenario: HDR Capture, HDR Video Recording, 8K30 Recording
- IP: ISP, DDR, Codec, DPU
- KPI: BW, power, latency, thermal
- Test: HDR regression, video recording stress, thermal test
- 과거 유사 issue: Project B HDR latency issue
```

이 화면은 개발 TAT 단축 효과를 보여주기 좋습니다.

---

## 8.4 Fragmentation Map

fixture 기반으로도 fragmentation map을 만들 수 있습니다.

예:

```text
JIRA
- issue는 많지만 scenario tag 부족
- root cause가 comment에 숨어 있음

Confluence
- decision은 있지만 issue와 연결 부족
- 오래된 문서와 최신 문서가 혼재

KPI Report
- power/BW 수치는 있지만 JIRA와 연결 안 됨

Regression DB
- pass/fail은 있지만 customer scenario와 연결 약함
```

이걸 실제 조직에 보여주면, 각 팀에서 “우리 쪽은 이게 맞다/아니다”를 피드백할 수 있습니다.

# 9. 이 방식의 핵심 장점

## 9.1 질문을 모르는 상태에서도 시작 가능

처음부터 완벽한 질문을 몰라도 됩니다.  
fixture가 질문을 만들어줍니다.

```text
“이런 질문이 실제로 중요한가?”
“이런 issue 관계가 실제와 비슷한가?”
“이 KPI가 milestone risk 판단에 의미가 있는가?”
“이 evidence level이면 신뢰할 수 있는가?”
```

---

## 9.2 사내 인터뷰 시간이 줄어듦

추상적인 인터뷰 대신, 구체적인 PoC 화면을 보여주고 피드백을 받습니다.

```text
Before:
각 팀에 가서 어떤 데이터가 있냐고 물어봄

After:
가상 cockpit을 보여주고,
“이걸 실제로 만들려면 어떤 데이터가 필요하고 어디에 있나요?”라고 물어봄
```

이 방식이 훨씬 빠릅니다.

---

## 9.3 Top management 설득이 쉬움

처음부터 실제 데이터 연결을 기다리면 보여줄 게 없습니다.  
fixture 기반이면 빠르게 이런 메시지를 보여줄 수 있습니다.

```text
현재 문제:
Multimedia 개발 데이터는 IP별, 조직별, tool별로 분산되어 있음

제안:
Scenario 중심 ontology로 Issue/KPI/Evidence/Decision을 연결

효과:
- RCA TAT 단축
- Change impact 분석 자동화
- Milestone risk 조기 탐지
- 과거 과제 knowledge 재사용
```

# 10. 단, fixture-first의 위험도 있음

fixture-first는 좋은 방법이지만 위험도 있습니다.

## 위험 1. 너무 이상적인 모델이 될 수 있음

실제 데이터는 훨씬 더 지저분합니다.  
그래서 fixture에도 일부러 불완전성, 중복, alias, missing evidence를 넣어야 합니다.

## 위험 2. 실제 조직이 “우리 현실과 다르다”고 볼 수 있음

그래서 fixture에는 항상 confidence label을 붙이는 게 좋습니다.

```text
Assumed
Sampled
Owner-reviewed
Verified
Automated
```

예를 들어:

```text
ISP M2M path → DDR BW 증가
Status: Assumed fixture
Need validation: Camera architecture owner
```

이렇게 하면 fixture가 “가짜 정답”이 아니라 **검증해야 할 가설**이 됩니다.

## 위험 3. 실제 데이터 연결이 늦어질 수 있음

fixture만 계속 다듬으면 실제 integration으로 못 넘어갑니다.  
그래서 fixture를 만든 후에는 반드시 “최소 실제 데이터 샘플”을 붙여야 합니다.

예:

```text
- 실제 JIRA issue 10개
- 실제 Confluence page 5개
- 실제 KPI report 3개
- 실제 scenario YAML 3개
```

처음에는 이 정도만 붙여도 충분합니다.

# 11. 수정된 전체 접근

제가 추천하는 최종 접근은 이겁니다.

```text
Step 1. Multimedia SoC fixture universe 생성
Step 2. Scenario/IP/KPI/Issue/Evidence/Decision ontology 구현
Step 3. 가상 데이터로 cockpit, graph, query 구현
Step 4. 사내 담당자에게 보여주고 “맞다/틀리다/빠졌다” 피드백 수집
Step 5. 실제 데이터 source를 필요한 것부터 연결
Step 6. fixture와 real data를 비교하면서 ontology 수정
Step 7. Video Recording → Preview → Playback → Video Call로 확장
```

즉, Phase 0을 이렇게 재정의하는 게 좋습니다.

> **Phase 0: Discover by Building**  
> 조사해서 만드는 것이 아니라, 먼저 만들어서 무엇을 조사해야 하는지 발견한다.

# 13. 실제로는 이렇게 말하면 좋습니다

사내 보고나 제안서에서는 이렇게 표현하는 게 좋습니다.

> 초기 단계에서 전사 데이터 source를 직접 전수조사하는 방식은 비용이 크고 범위가 불명확하다.  
> 따라서 Multimedia SoC 개발 lifecycle을 대표하는 synthetic fixture dataset을 먼저 구축하고, 이를 기반으로 scenario 중심 ontology와 PoC cockpit을 구현한다.  
> 이후 실제 JIRA/Confluence/KPI 데이터와 비교하여 fixture 가설을 검증하고, 우선순위가 높은 데이터 source부터 점진적으로 연결한다.

이 표현이 좋습니다.  
“가짜 데이터로 하겠다”가 아니라, **synthetic fixture를 통해 discovery 비용을 줄이고 validation 중심으로 전환하겠다**는 메시지입니다.

# 결론

네, Phase 0부터 fixture data를 풍부하게 만드는 접근이 맞습니다.  
오히려 이 프로젝트에서는 그게 더 현실적입니다.

다만 fixture를 단순 mock data로 만들면 안 되고, 아래를 포함해야 합니다.

```text
- 실제 Multimedia SoC 개발에서 자주 나오는 issue archetype
- IP alias와 명칭 불일치
- scenario / variant / IP / KPI / issue / evidence / decision 관계
- 불완전한 evidence
- 중복 issue
- 오래된 문서
- JIRA/Confluence/KPI 간 연결 부재
- confidence level
- milestone risk 변화
```

이렇게 만들면 fixture 자체가 **SoC 개발 ontology의 초안**이 되고, 사내 데이터 조사의 기준점이 됩니다.

정리하면:

```text
존 방식:
조사 → 정리 → 설계 → PoC

추천 방식:
fixture → PoC → 피드백 → 실제 데이터 연결 → ontology 보정
```

이 방식이 훨씬 빠르고, PoC 설득력도 높고, 실제 AX 플랫폼으로 발전할 가능성도 큽니다.
