# OPS-F Project 중심 사용성 Protocol v2 구현 및 검증 보고서

> 작성일: 2026-07-22
> 범위: synthetic fixture 기반 local authoring/evaluation tooling
> 구현 판정: **PASS — protocol v2와 재현 가능한 실행 도구 준비 완료**
> Human Gate: **NOT READY — baseline 0/5, product 0/5**
> 다음 단계: 서로 다른 독립 참가자로 두 condition을 수집하고 책임자가 directional result 검토
> 후속 보강: `26.07.23 OPS-F Study Release 보강 및 사내 데이터 연결 준비도 보고서.md`에서
> 제품 release hash, reviewer-only rubric, attrition 집계와 Project E2E를 추가로 고정했다.

## 1. 결론

OPS-F는 OPS-D/OPS-E에서 구현한 실제 사용자 경로인 `Portfolio → Project Situation → Risk →
Decision`을 평가하도록 UX-H 연구 재료를 Project 중심 v2로 확장했다. PROJECT-U/V/W의 공개 가능한
fixture를 hash로 고정하고, Jira/Confluence형 baseline 6개 surface와 두 condition이 함께 수행할
11개 task, condition별 guide, session 검증·요약 CLI를 구현했다.

이 단계에서 실제 참가자 결과는 만들지 않았다. builder dry-run은 빈 draft만 생성하며 현재 요약은
의도대로 `not_ready`, `not_evaluable`, `no_business_claim`이다. 따라서 OPS-F의 소프트웨어 준비는
완료했지만 human Gate는 아직 통과하지 않았고, UX-I 및 의사결정 속도·조언 품질·business value
주장은 계속 차단한다.

## 2. 왜 별도 v2가 필요한가

UX-H v1은 `CASE-VR-001` Decision Workspace의 정보 이해를 측정했다. 이후 Project Operations
방향에서는 사용자의 첫 질문이 개별 Decision보다 다음 순서로 바뀌었다.

1. 여러 과제 중 지금 어디를 먼저 봐야 하는가?
2. 선택한 과제의 진행 상태와 최상위 Risk는 무엇인가?
3. 그 Risk는 어떤 Issue, Event, Evidence와 cross-project lesson에서 나왔는가?
4. 개발 영향과 Decision/Action, 검증·rollback은 어떻게 연결되는가?
5. 과거 Step에서는 그 시점 이후 정보를 보지 않고 같은 경로를 검토할 수 있는가?

v1 fixture와 결과 의미를 덮어쓰지 않고 `usability-study-protocol.v2`와
`usability-project-baseline-pack.v2`를 별도 추가했다. 시간·답변·reviewer 판정이라는 측정 의미는
변하지 않아 session/event/summary v1 계약을 재사용한다.

## 3. Frozen study material

### 3.1 Project source 고정

세 Project는 먼저 canonical `development-project.v1`로 검증한 뒤 정규화 JSON SHA-256을 비교한다.

|Project|lifecycle 역할|고정 SHA-256|
|---|---|---|
|PROJECT-U|진행 중이며 Evidence와 실행이 비교적 정렬된 과제|`5ed4cf56c362165c71d86986e4ef201035a7da0ff6671c235a410711472b120b`|
|PROJECT-V|현재 최고 우선순위 Risk와 Decision 연결을 추적할 과제|`d74b5933c3ba6dabe8a9a6d2d4a186d50635f06c2d66f632bf8507a2693880be`|
|PROJECT-W|아직 확정되지 않은 정보와 다른 epistemic posture를 구분할 과제|`415803216965af5d7383aeaac4714aefa2478ac23013268e43369f8a64bf4098`|

fixture 내용이나 selector가 변경되면 material 검증이 실패하므로, 결과를 본 뒤 source를 조용히
바꾸는 일을 막는다.

### 3.2 Baseline 공정성

baseline pack은 Project fixture의 observable field만 JSON pointer로 읽어 다음 6개 surface를 만든다.

- 과제 목록과 lifecycle 요약
- PROJECT-V 진행 현황
- PROJECT-V Issue·Risk·Evidence 현황
- PROJECT-V Decision·Action·Milestone 현황
- PROJECT-U/W 비교 자료
- PROJECT-V event 이력

모든 task의 답은 baseline에 노출된 source 안에서 찾을 수 있어야 한다. validator는 task가 참조하는
Project와 pointer가 baseline source selection에 포함됐는지 확인한다. hidden fixture, expected
outcome, Agent output, Dossier, simulated decision과 정답 문구는 baseline에 넣지 않는다.

## 4. Frozen task와 사용자 경로

두 condition은 동일한 11개 task와 순서를 사용한다. baseline 참가자는 생성된 문서 surface로,
product 참가자는 `/projects`에서 시작해 실제 UI로 답한다.

|번호|측정 질문|주요 경계|
|---:|---|---|
|1|지금 먼저 볼 과제와 이유|Backend-owned attention priority|
|2|PROJECT-V 전체 상황|lifecycle, progress, milestone|
|3|최상위 Issue/Risk와 Evidence gap|관측과 부족 정보|
|4|Risk 발생 근거|Issue/Event/Evidence provenance|
|5|PROJECT-U/V/W epistemic 차이|observed/inferred/unconfirmed 구분|
|6|Risk의 개발 영향|WorkItem/Milestone impact|
|7|Decision/Action/검증/rollback|안전 조건과 실행 연결|
|8|Project Step 20의 관측 상태|historical reconstruction|
|9|Step 20 이후 정보 비노출|no-future-leakage|
|10|cross-project lesson|출처와 적용 한계|
|11|Decision 검토 후 Risk 복귀|문맥 보존 round trip|

guide에는 task prompt, 시작 위치, 기록 절차만 포함하며 expected answer는 포함하지 않는다. baseline과
product 참가자에게 같은 task를 제공하되, 한 참가자가 두 condition을 모두 완료해 학습 효과를
만들지 못하도록 between-subjects 규칙을 validator가 강제한다.

## 5. 구현 경계와 과장 방지

|포함|제외|
|---|---|
|Project fixture hash/pointer 검증|실제 Jira/Confluence connector|
|baseline surface와 product guide 생성|회사 data, 계정, 인증|
|익명 participant/session artifact|실명, 이메일, 사번|
|동일 task·between-subjects 검증|AI가 사람 답변이나 시간을 생성|
|directional summary|자동 human 승인 또는 통계적 일반화|
|기존 v1 material 호환|제품 API telemetry/write-back|

condition별 `proxy` 또는 `domain` 독립 완료 관측이 최소 5개가 되기 전에는 목표 판정을 계산하지
않는다. 최소치를 채워도 자동 결과는 책임자 검토 준비 상태일 뿐 business pass가 아니다. builder
session은 도구 검증용이며 독립 표본에 포함되지 않는다.

## 6. CLI 실행 방법

Study material 검증:

```powershell
uv run soc-ot usability validate
```

Baseline session 준비:

```powershell
uv run soc-ot usability prepare-session `
  --condition baseline `
  --participant-kind proxy `
  --participant-code P001 `
  --session-id OPSF-BASE-P001
```

Product session 준비:

```powershell
uv run soc-ot usability prepare-session `
  --condition product `
  --participant-kind proxy `
  --participant-code P101 `
  --session-id OPSF-PROD-P101
```

두 condition 모두 `study-guide.md`와 빈 `session.yaml`을 만든다. baseline에만
`baseline-pack.md`가 추가된다. 실제 관측 후에는 다음과 같이 검증·요약한다.

```powershell
uv run soc-ot usability validate-session `
  --session output/usability/OPSF-BASE-P001/session.yaml `
  --require-complete

uv run soc-ot usability summarize `
  --sessions-root output/usability/OPS-F-20260722 `
  --output output/usability/OPS-F-20260722/summary.json
```

`output/`은 git ignored이며 참가자 code에는 개인 식별자를 사용하지 않는다.

## 9. OPS-F Gate를 끝내는 조건

OPS-F는 코드가 더 생긴다고 끝나는 단계가 아니다. 다음이 모두 충족되어야 human Gate를 닫을 수
있다.

1. baseline과 product에 서로 다른 독립 참가자 관측을 각각 최소 5개 수집한다.
2. 모든 completed session이 timing, answer, reviewer response와 frozen rubric 검증을 통과한다.
3. 제외 session과 사유를 보존하고 결과를 본 뒤 target/protocol/source를 바꾸지 않는다.
4. summary를 책임자가 검토해 가장 느리거나 오분류가 많은 task를 확인한다.
5. 그 근거만으로 UX-I의 축소·개선 범위를 정하고, 작은 표본을 business proof로 표현하지 않는다.

사내 적용 시 Jira/Confluence read-only connector, 권한 계승, 실제 과제 선정과 사용자 동의는 별도
C0 승인 범위다. 로컬 OPS-F 결과가 이를 자동 승인하지 않는다.
