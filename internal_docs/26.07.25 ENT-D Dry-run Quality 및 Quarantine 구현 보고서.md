# ENT-D Dry-run Quality 및 Quarantine 구현 보고서

> 작성일: 2026-07-25  
> 범위: ENT-D fixture-only no-write review preparation  
> 판정: **ENT-D PASS, NEXT ENT-E**

## 1. 이번 단계가 해결한 문제

ENT-C까지는 source record를 안정적으로 mapping하고 재처리할 수 있었지만, 실제 적용 전에
운영자가 답해야 할 질문을 한 화면 또는 artifact로 볼 수 없었다.

- 어떤 canonical 후보가 생성·변경·삭제될 예정인가?
- mapping하지 못한 record가 몇 건이고 왜 실패했는가?
- source에 mapping profile이 소비하지 않는 field가 있는가?
- 연결 대상이 없는 reference가 있는가?
- source time이 모호하거나 source가 오래됐는가?
- ACL reference가 이번 검토 범위에 등록됐는가?
- 문제 record 하나 때문에 정상 변경까지 사라지는가?
- 사람이 남긴 resolution이 현재 source version에 유효한가?

ENT-D는 이 질문을 no-write JSON report로 답한다. 실제 canonical import나 사내 연결은 하지
않는다.

## 2. 승인한 계약

ADR-0015가 다음 계약을 승인한다.

```text
enterprise-dry-run-input.v1
enterprise-resolution-file.v1
enterprise-dry-run-report.v1
```

Dry-run input은 synthetic canonical snapshot, candidate kind별 key field, 명시적 `as_of`,
freshness threshold, 알려진 opaque ACL reference 목록과 quality probe를 포함한다. 실제 DB dump나
권한 grant가 아니다.

Report는 항상 다음 값을 고정한다.

```text
write_performed = false
canonical_import_authorized = false
```

Schema validation으로도 두 값을 `true`로 바꿀 수 없다.

## 3. CLI

```powershell
uv run soc-ot enterprise validate-source
uv run soc-ot enterprise dry-run `
  --output output/enterprise/ent-d-dry-run.json
```

첫 명령은 registry, dirty corpus, sync corpus, dry-run input과 resolution file을 strict contract로
검증한다. 두 번째 명령은 ENT-C를 memory에서 실행한 뒤 요청한 report 파일만 쓴다.

집중 test는 runtime database 함수가 호출되면 즉시 실패하도록 바꾼 상태에서 두 명령을 실행했다.
두 명령 모두 database를 열지 않고 성공했다.

## 4. Canonical change proposal

```text
CanonicalChangeAction = CREATE | UPDATE | DELETE | NO_CHANGE
```

Candidate state와 source-linked snapshot을 비교한 결과는 다음과 같다.

|Action|수|예시|
|---|---:|---|
|CREATE|2|역순 도착 후 effective-time 정렬된 Event 2건|
|UPDATE|1|Project title 변경|
|DELETE|2|삭제된 WorkItem, restricted Evidence|
|NO_CHANGE|0|이번 fixture에는 없음|

각 change는 deterministic ID, candidate kind, canonical key, stable source identity, before/after
values와 mapping reason을 갖는다. 이 값은 domain `DevelopmentProject` validation을 통과한 aggregate가
아니며 import 명령도 아니다.

Restricted source는 payload를 다시 노출하지 않고 snapshot에 있던 before value만으로 delete를
제안한다.

## 5. Quality report

일곱 quality code를 별도로 보존한다.

|Code|의미|기본 blocking|
|---|---|---|
|`DANGLING_REFERENCE`|참조 대상이 snapshot이나 proposed target에 없음|예|
|`TIME_AMBIGUITY`|effective/observed 또는 updated/ingested 관계가 검토 필요|예|
|`UNMAPPED_FIELD`|payload field를 mapping profile이 소비하지 않음|아니오|
|`ACL_REFERENCE_UNKNOWN`|opaque ACL reference가 검토 입력에 등록되지 않음|예|
|`STALE_SOURCE`|source update가 freshness threshold 초과|아니오|
|`MAPPING_QUARANTINED`|mapping 또는 sync가 ambiguity를 격리|예|
|`MAPPING_REJECTED`|candidate가 생성되지 않음|원인별; exact duplicate는 정보|

Fixture quality probe 한 건은 의도적으로 다음 문제를 동시에 만든다.

- 존재하지 않는 `PROJECT-MISSING` reference
- observed time보다 미래인 effective time
- profile이 소비하지 않는 `project_ref`
- 알려지지 않은 `acl-ref:unknown`

이는 실제 company field나 ACL을 모사한 것이 아니라 report가 문제를 분리해서 보여주는지 검증하기
위한 synthetic probe다.

## 6. 정량 결과

현재 hash-pinned fixture의 deterministic 결과는 다음과 같다.

```text
source outcomes             25
mapped outcomes             19
mapping coverage            0.76
canonical change proposals  5
quality findings            15
rejected                    1
quarantined                 5
quarantine entries          8
open                        7
resolution proposed         1
freshness seconds           97140
```

Blocking source가 있어 report status는 `BLOCKED`다. 하지만 유효한 change proposal 5건은 버리지
않고 함께 보여준다. 이것이 “한 개 오류 때문에 전체 source를 조용히 버리지 않는다”는 ENT-D Gate의
구현이다.

## 7. Quarantine과 resolution

각 blocking finding은 deterministic `quarantine_id`를 가진다. Queue는 report 안에 있으며 아직
database table이나 운영 DLQ가 아니다.

Resolution file은 다음 네 action만 기록할 수 있다.

```text
EXCLUDE_SOURCE
SOURCE_FIXED
MAPPING_UPDATED
ACKNOWLEDGE_RISK
```

Fixture에는 dangling reference를 source에서 수정한 뒤 재실행하겠다는 `SOURCE_FIXED` 제안 한 건이
있다. 이 항목은 queue status를 `RESOLUTION_PROPOSED`로만 바꾼다. 나머지 7건은 `OPEN`이고 report
전체도 계속 `BLOCKED`다.

Resolution은 현재 `quarantine_id`와 선택적으로 source content hash를 고정한다. 존재하지 않는
ID나 바뀐 hash를 참조하면 dry-run이 실패한다. 오래된 사람이 입력한 파일이 새 source record에
자동 적용되는 것을 막는다.

## 8. Fixture와 코드 경계

|Artifact|역할|
|---|---|
|`enterprise_dry_run.py`|순수 diff, quality, quarantine, summary 계산|
|`dry-run-input.v1.yaml`|synthetic snapshot, policy와 quality probe|
|`resolution-template.v1.yaml`|hash-pinned reviewer proposal 예시|
|`test_ent_d_enterprise_dry_run.py`|no-write, quality, partial preservation, stale resolution 검증|
|ADR-0015|report와 authority 경계|

Fixture에는 vendor 제품명, company tenant, field ID, user/group, credential이 없다. Enterprise
manifest가 두 새 입력 파일의 SHA-256을 고정한다.

## 9. 검증

집중 test 10개가 다음을 검증한다.

- create/update/delete proposal과 before/after invariant
- 모든 quality code와 summary 수치
- blocking source가 valid change를 제거하지 않음
- resolution은 제안일 뿐 import approval이 아님
- unknown/stale resolution 거부
- dry-run 결정성과 입력 불변성
- CLI가 runtime database를 열지 않음
- `canonical_import_authorized=true` schema 거부
- synthetic fixture와 manifest hash
- contract registry와 generated schema

최종 repository Gate는 ruff, mypy 56개 source file, non-PostgreSQL 216개 test,
plan/architecture/hidden/secret 검사, generated contract/OpenAPI/Frontend client freshness와
`git diff --check`까지 모두 통과했다. Backend application/CLI와 fixture만 변경했으므로
PostgreSQL, Frontend와 browser-specific Gate는 필요하지 않다.

## 10. 아직 하지 않은 것

- 실제 company source validation
- vendor API와 실제 cursor/rate limit
- canonical domain aggregate validation과 import
- PostgreSQL quarantine queue와 transaction
- 실제 principal/group/inherited ACL 판정
- credential redaction, partial source recovery와 health/metrics
- 승인 workflow와 write-back

`READY_FOR_REVIEW`가 나오더라도 import가 승인되는 것은 아니다. 실제 사내 연결 가능성은 C0/C1
검토 전까지 NO-GO다.

## 11. 다음 단계

ENT-E는 synthetic security/operation emulator를 구현한다.

- principal과 ACL allow/deny matrix
- classification별 UI/model/log exposure policy
- credential redaction test
- sync lag, stale/rate-limit/partial-source recovery fixture
- health/readiness, metrics와 audit event contract

ENT-E도 실제 authentication, company identity, vendor credential 또는 write-back을 구현하지 않는다.
