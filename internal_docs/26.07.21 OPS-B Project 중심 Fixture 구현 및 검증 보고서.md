# OPS-B Project 중심 Fixture 구현 및 검증 보고서

> 상태: 구현 완료, OPS-B Gate PASS  
> 일자: 2026-07-21  
> 범위: local synthetic authoring fixture와 validator  
> 다음 단계: OPS-C Project domain/projection/API

## 1. 결론

OPS-B는 하나의 DecisionCase로 바로 진입하던 기존 구조 앞에 Project 전체 상황을 만들 수 있는
authoring source를 추가했다. PROJECT-U/V/W는 각각 양산 현장, pre-silicon HW closure,
spec/architecture 정의를 나타내며 lifecycle, evidence 강도, commitment window와 risk 처리 상태가
의도적으로 다르다.

이번 단계는 **fixture authoring과 validation만** 완료했다. Project Portfolio/Situation API, DB
aggregate, attention/risk ordering policy와 UI는 OPS-C 이후 범위다. 따라서 현재 화면이 새 fixture를
표시한다고 주장하지 않는다.

## 2. 구현 계약

`development-project.v1`은 다음 객체를 연결한다.

```text
DevelopmentProject
  ├─ Track → WorkItem
  ├─ Milestone(kind, commitment Step)
  ├─ Evidence(requested/expected/available Step)
  ├─ observed DevelopmentIssue
  ├─ future ProjectRisk + provenance + impact path
  ├─ DecisionCase reference / treatment Action
  └─ typed DevelopmentEvent before/after chain
```

Source fixture에는 `ProjectAttention`, `RiskLevel`과 composite score가 없다. Risk는 downside,
blast radius, urgency와 reversibility 같은 raw ordinal semantics와 source reference만 가진다. 실제
attention과 ordering은 OPS-C의 versioned deterministic policy가 계산해야 한다.

## 3. Project fixture 구성

|Project|Track/Work/Milestone|Issue/Risk/Evidence|Event/Decision|주요 상태|
|---|---:|---:|---:|---|
|PROJECT-U|3 / 3 / 2|2 / 3 / 3|7 / 1|강한 field evidence, mitigation, resolved issue, closed risk, late→received evidence|
|PROJECT-V|3 / 3 / 2|1 / 2 / 3|4 / 2|pre-silicon model uncertainty, 비가역 commitment, rework, resource conflict|
|PROJECT-W|2 / 2 / 2|1 / 2 / 4|6 / 1|model/lesson 기반 low confidence, late requirement, realized/accepted risk|

총 8 Track, 8 WorkItem, 6 Milestone, 4 Issue, 7 Risk, 10 Evidence, 17 Event와 4개
DecisionCase reference다. Event 수를 목표로 늘리지 않고 Project Situation, Risk provenance,
historical comparison에 다른 상태를 만드는 최소 thread만 유지했다.

## 4. Risk provenance와 cross-project lineage

대표 경로는 다음과 같다.

```text
PROJECT-U field measurement / observed power issue
  → KPI loss risk → Field Fix Gate → CASE-VR-004 / guarded mitigation
  → long-run evidence arrival → next-silicon lesson
  → PROJECT-V cross-project source → wrong HW commitment risk
  → Architecture Freeze → CASE-HO-002 / bounded change

PROJECT-W early model + historical lesson
  → late customer requirement risk
  → observed requirement gap / realized risk
  → Spec Freeze → CASE-VR-005 / minimum-spec posture
```

Cross-project source는 source Project와 source Event ID를 모두 가지며 corpus validator가 실제 Event
존재를 확인한다. 기존 12개 DecisionCase 중 fixture에 존재하는 case만 참조할 수 있다.

## 5. Historical boundary

`reconstruct_project_fixture_at_step`은 현재 상태에서 선택 Step 이후 event의 before state를 역적용한다.
그 뒤 다음 대상을 제거하거나 가린다.

- 아직 request되지 않은 Evidence
- 아직 available하지 않은 Evidence의 `source_ref`
- 아직 observed되지 않은 Issue
- 아직 identified되지 않은 Risk
- 아직 opened되지 않은 DecisionCase
- 선택 Step 뒤 Event와 cross-project source

예를 들어 PROJECT-U Step 34에서는 장시간 결과가 `LATE`지만 그 source와 결과 기반 claim,
Step 35 Event와 next-silicon Risk는 보이지 않는다. PROJECT-W Step 5에서는 Step 7 requirement
Issue와 DecisionCase가 없고 나중에 `REALIZED`가 되는 Risk는 아직 `OPEN`이다.

## 6. `world.yaml` adaptation

외부 참고본은 top-level `events`의 field observation, pre-silicon commitment, model trade-off,
evidence delay, rework와 resource conflict **상황 아이디어만** 사용했다. 원본 Project/Role/Risk,
activity log, 점수, dice와 긴 role reasoning은 복사하지 않았다. 외부 파일은 runtime과 test 입력이
아니며 참고 revision의 SHA-256만 manifest에 기록했다.

각 Project YAML의 SHA-256도 `fixtures/projects/manifest.yaml`에 고정했다. 변경 시 fixture와
manifest를 함께 갱신하지 않으면 test가 실패한다.

## 8. OPS-C 입력과 보류 범위

OPS-C는 이 fixture 계약을 source로 사용해 다음만 구현한다.

1. runtime `DevelopmentProject` aggregate와 persistence compatibility
2. deterministic Project attention/Risk ordering policy와 reason/source projection
3. `/api/v1/projects` Situation/Risk/Timeline read API와 `at_step` parity
4. 기존 DecisionCase의 project/source/risk reference migration 또는 versioned compatibility

OPS-C Gate 전에는 Portfolio/Situation UI를 구현하지 않는다. 회사 Jira/Confluence, 인증,
write-back, 실제 사람 승인과 business value 측정도 여전히 제외한다.
