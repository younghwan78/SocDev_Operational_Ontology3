# UX-B Decision Inbox 구현 및 검증 보고서

> 상태: 구현·검증 완료
> 기준일: 2026-07-17
> 범위: post-I7 UX redesign의 UX-B
> 다음 단계: UX-C Decision Brief와 Development Twin — 시작하지 않음

## 1. 결론

UX-B는 사용자가 결정 목록에서 첫 확인 대상을 빠르게 찾도록 목록의 데이터 경계와 화면을
함께 바꿨다. Frontend가 기한·위험·우선순위를 추론하지 않도록 Backend 전용
`decision-list-item.v1` projection을 만들고, `/decisions`를 이 projection의 한국어
Decision Inbox로 교체했다.

```text
StoredCase
  → Backend list projection
     → action-needed group
     → deadline attention
     → critical blocker propagation
     → milestone impact
     → why-now
     → next action
  → ordered collection API
  → React는 순서와 업무 의미를 그대로 표시
```

UX-B는 목록만 완성한다. 기존 상세 화면은 `decision-workspace.v1`이고, UX-A에서 정의한
`decision-workspace.v2`를 실제 API와 React에 연결하는 일은 UX-C 범위다.

## 2. Backend와 계약

### 2.1 소비자 형태의 목록 projection

`backend/src/soc_ot/application/projections.py`에 다음 read model을 추가했다.

- `DecisionListItemProjection`
- `DecisionListDeadline`
- `DecisionListBlocker`
- `DecisionListGroup`
- `DecisionAttention`

각 item은 routing용 `case_id`, 질문과 문맥, 한국어 현재 상태, 업무 그룹, 기한 attention,
why-now, 막힌 개발과 milestone 영향, 한 개의 다음 행동만 제공한다. Workspace에서만 필요한
track 전체, evidence, claim과 alternative는 collection 응답에서 제거했다.

### 2.2 Backend-owned priority

Backend 정렬은 다음 순서를 사용한다.

1. `ACTION_REQUIRED`, `IN_REVIEW`, `ACTION_AND_OBSERVATION`, `COMPLETED`
2. `OVERDUE`, `DUE_NOW`, `DUE_SOON`, `NORMAL`
3. deadline까지 남은 Step
4. blocker 수
5. 안정적인 case ID tie-break

Frontend는 API 순서를 보존하고 명시적인 `group`만 묶는다. urgency, blocker propagation,
milestone impact와 다음 행동 label을 다시 계산하지 않는다.

### 2.3 API와 생성 계약

`GET /api/v1/decision-cases`는 전체 `decision-workspace.v1` 배열 대신
`decision-list-item.v1` 배열을 반환한다. 상세 endpoint는 바꾸지 않았다.

- `contracts/generated/decision-list-item.v1.schema.json`
- `contracts/generated/openapi.json`
- `frontend/src/api/schema.d.ts`

이 collection 교체는 외부 소비자가 없는 로컬 PoC의 의도적인 계약 변경이며
`docs/decisions/ADR-0006-consumer-shaped-decision-inbox.md`에 근거와 호환성 경계를 기록했다.

## 3. Frontend UX

### 3.1 정보 계층

결정 card는 다음 순서로 읽힌다.

1. 남은 Step과 `가상 판단` 표시
2. 업무 문맥과 결정 질문
3. `왜 지금` 설명
4. 한 개의 primary action
5. 현재 상태, 막힌 개발, 영향 기준점

raw case ID, ontology thumbnail, evidence 개수 KPI, Agent confidence와 여러 primary button은
표시하지 않는다. `/dev/fixtures`도 일반 사용자 navigation에서 제거했으며 route 자체는
개발자 도구로 유지한다.

### 3.2 상태와 반응형 동작

- Loading: 상태 문구와 세 개의 card skeleton
- Empty: 현재 검토할 결정이 없다는 업무 문구
- Error: 기술 code 대신 재시도 행동
- Desktop: 좁은 읽기 폭과 차분한 밝은 review 화면
- Mobile 390px: 단일 column, 가로 overflow 없음, 첫 viewport에 질문·why-now·primary action 노출
- 접근성: semantic heading/article, 44px action, focus outline, reduced-motion 대응

## 6. 남은 경계와 위험

- 상세 Decision Workspace는 아직 긴 `decision-workspace.v1` 화면이다. UX-C에서만 v2로
  교체한다.
- `IN_REVIEW` group은 계약에는 있지만 최신 case-scoped durable run을 안전하게 조합하는
  projection이 없어 아직 생성하지 않는다. Frontend heuristic으로 대신하지 않는다.
- collection은 요청 때마다 현재 aggregate로 생성되므로 persisted list projection의 stale
  판정은 없다. Workspace의 version conflict 복구와 별개이며, list cache freshness 정책이
  필요해질 때 source version 계약과 함께 추가한다.
- 8개 수준의 로컬 fixture에는 검색·filter를 추가하지 않았다. case 규모와 사용성 측정이
  필요성을 보여주기 전에는 화면 복잡도를 늘리지 않는다.

## 7. 다음 단계

다음 단계는 UX-C다. `decision-workspace.v2`를 실제 Backend projection과 React 상세 화면에
연결하고 Context Bar, phase-adaptive Brief, selected Step 재구성, causal chain,
commitment window, expected/observed 전환 경계를 구현한다. UX-B 완료만으로 Workspace UX나
사내 적용 준비가 완료됐다고 판단하지 않는다.
